# docs: skill のグローバル配布で他リポジトリの Issue 記法が混在する

## 背景

[ISSUE-14](<../closed/ISSUE-14_in-repo Issue の識別子が GitHub の番号空間と衝突する/issue.md>) は
識別子を `ISSUE-<N>` へ分離し、背景に「他リポジトリの移行は本 Issue の範囲外で、各リポジトリの
判断に委ねる」と書いた。**この委譲は機構上成立しない。**

ロールアウトの実測で分かった配布の形:

- 消費側の宣言は 1 つで、deploy 先もホーム直下の 1 箇所しかない。そこを複数の設定ディレクトリが
  symlink で共有している
- したがって「特定のリポジトリにだけ配らない」経路が無い。配った時点で、その開発機の全リポジトリで
  新版の skill がロードされる

委ねる先が存在しないので、選べるのは「配る」か「配らない」だけになる。配らなければ canonical と
消費側が乖離したままになり ISSUE-14 が完了しない。よって配る以外の選択肢が無く、その帰結として
旧記法と新記法が同居する。本 Issue はその同居を追跡する。

## 実測 (2026-08-24)

`issue-id.py` の `issue_dirs()` をそのまま呼んで計上した。

| 区分 | 件数 |
|---|---|
| 旧記法 (`<N>_<title>`) | 913 |
| 新記法 (`ISSUE-<N>_<title>`) | 22 |
| 旧記法を持つリポジトリ | 12 |

分布は偏っている。上位 3 つが 223 件・218 件・144 件で、これだけで旧記法全体の 64 パーセントを
占める。残り 9 リポジトリは 1 件から 125 件に散らばる。

### 計上を 2 回外した

この数字は 2 度の訂正を経ている。どちらも「エラー」ではなく、もっともらしい小さい値として
返ってきた。

1. **走査の深さ**。`docs/issues/` 直下だけを数えて 319 件と出た。`issue_dirs()` は直下と
   `docs/issues/closed/` の両方を見るので、closed を落とすと 3 分の 1 になる
2. **リポジトリ集合**。`find -maxdepth 2` でリポジトリを列挙したため、1 段深く置かれた
   リポジトリの `.git` が depth 3 になって漏れた。落ちた 1 つが 90 件を持っていた。
   12 のうち 11 を数えた結果は、それ自体では欠けていることが分からない

集合を自分で作ると、作った側の想定がそのまま観測の上限になる。件数だけを見ても気づけない
ので、集合の作り方の側を疑うしかない。

### 混在しても採番は壊れない

`ANY_ISSUE_DIR` が接頭辞を optional にしているので、`--next` は旧記法のディレクトリも同じ
番号空間として数える。`docs/issues/` を持つ 14 リポジトリすべてで `--next` が rc=0 を返し、
番号を出した。

この rc=0 は陽性対照付きで確かめてある。同じ番号でタイトル部だけが違うディレクトリを 2 つの
ref に持つ fixture を作ると、`--next` は重複を名指しして rc=1 で止まった。つまり検出器は
生きていて、14 リポジトリの緑は「検査が動いた上での緑」である。

### 検査は取り付けたリポジトリでしか走らない

`--check` は旧記法のディレクトリ名を違反として報告する。ただし pre-commit と CI へ取り付けて
いるのは本リポジトリだけなので、他リポジトリでは走らない。混在は静かに続く。

## 判断: 混在を受け入れ、既存は rename しない

理由は 2 つある。

1. rename は採番を止めうる。`issue-id.py` の docstring が「既知の限界」として、番号もタイトル部も
   保存しない rename は同じ番号の別 Issue と判定され、以降どの Issue も起票できなくなると書いて
   いる。913 件すべてでタイトル部を保存し切る保証は無い
2. 件数が現実的でない。3 リポジトリで 585 件が集中しており、相対リンクの補正 (skill の D.3 が
   挙げる 3 方向) も同じ件数だけ発生する

既存は履歴としてそのまま残し、新規起票だけが新記法になる。

## タスク

- [ ] 配布後に旧記法のリポジトリで新規起票を 1 件通し、混在下で採番とディレクトリ作成が
      壊れないことを実測する (今回の `--next` はディレクトリを作らないので、起票の全経路は
      まだ通っていない)
- [ ] `--check` を旧記法のリポジトリへ取り付ける場合のコストを見積もる。取り付けると既存の
      ディレクトリ名がすべて違反として報告されるので、取り付けと rename は同時にしか選べない
- [ ] rename を選ぶ場合の手順とリスクを整理する。番号とタイトル部の保存を機械的に保証する
      方法が要る

## 関連

- ISSUE-14 の「他リポジトリの移行は各リポジトリの判断に委ねる」という前提の訂正にあたる。
  委ねる単位が存在しないことは、ロールアウトを実際に走らせるまで見えなかった
- 検査を取り付けていないリポジトリでは混在が検出されない。これは ISSUE-14 が「検査は自分の
  取り付けを自分では検証できない」として挙げた限界と同型で、取り付けの有無そのものを見る層が
  どこにも無い
