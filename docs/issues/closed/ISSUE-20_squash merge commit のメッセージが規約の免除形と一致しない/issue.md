# docs: squash merge commit のメッセージが規約の免除形と一致しない

## 背景

**この話題の一部は ISSUE-14 の「既知の限界」に既出である。** そちらが受容しているのは
「GitHub 上で生成される squash merge commit はサーバ側生成なので commit-msg hook を通らず、
この経路を塞ぐには CI 側の機構が要る」というところまでで、限界として明文化されている。

本 Issue が扱うのは、その上に乗る新規の観測である。

### 新しく分かったこと

GitHub が squash merge の subject へ自動で付ける括弧付きの数字記法は、規約の免除形の
どちらにも一致しない。免除は直前が `PR ` のとき (自リポの PR) と `owner/repo` のとき
(他リポ) の 2 本しかなく、直前が開き括弧の形はどちらでもない。

つまり **squash マージするたびに、規約違反のメッセージが機械的に生成される**。書き手の
不注意ではなく、経路の性質としてそうなる。

### 実測

| 観測 | 結果 |
|---|---|
| マージコミットのメッセージ全文へ `--check-text` | 371 行走査 / 違反 1 件 (1 行目) / rc 1 |
| 起票時 (2026-08-23) の該当コミット数 | 12 件 |

12 件はそのときの squash マージの回数と一致する。1 件の例外もなく、**成功した
squash マージは必ず 1 件の違反を生む**。

違反が報告されるのは常に 1 行目 (subject) である。本文側は各コミットのメッセージがそのまま
連結されたもので、そちらは commit-msg hook を通ってきているため違反を持たない。

### 誰も検査しない

- commit-msg hook はサーバ側生成のコミットに届かない
- CI に `--check-text` の surface は無い。`.github/workflows/ci.yml` の該当 step のコメントが
  「コミットメッセージを見る `--check-text` は CI にその surface が無いので置かない」と
  明示的に宣言している
- `--check` は追跡ファイルしか見ないので、コミットメッセージは走査集合に入らない

したがって現状は「違反が定常的に生成され、どの経路も赤くならない」状態にある。

### 論点は 2 つ

- **(a) 規約側で末尾の括弧付き数字記法を免除に加える。** 生成される形が規約に合うようになる。
  ただし免除は届きすぎる方向へ広がっても違反 0 件の緑にしかならず、出力を見ても気づけない。
  範囲を確かめる対照が要る
- **(b) 検査しないまま受け入れる。** ISSUE-14 の「既知の限界」を 1 行伸ばして、通らないだけ
  でなく**機械的に違反が生成される**ことまで書く。塞がないと決めるなら、何が起き続けるかを
  書いておかないと次に読む人が同じ発見をやり直す

## 裁定 (2026-08-27)

**(a) でも (b) でもない (c) を採る。マージ時に subject を明示し、免除形を自分で書く。**

```bash
gh pr merge <N> --squash --subject "<PR タイトルと同じ 1 行> (PR #<N>)"
```

規約は 1 つのまま、免除も広げない。塞ぐのは「生成される形」の側である。

### 再計測が裁定を変えた

起票時 12 件だった件数を数え直した。

| リポジトリ | 該当コミット | 全コミット |
| --- | --- | --- |
| agentic-coding-tools | 26 | 34 |
| 消費側リポジトリ | 161 | 256 |

消費側は誰も数えていなかった。**この規約は skill 経由で配られるので、影響は配布元だけでは
測れない。**起票時の 12 件という数字は、母集団を配布元に限った値だった。

### (a) を落とした決め手

配布元では **5 つの番号が PR と in-repo Issue の両方に実在する**。したがって括弧付きの
数字記法は本当に曖昧で、読み手はどちらを指すか判別できない。ISSUE-14 が消そうとした衝突が
そのまま生きている状態にある。

**曖昧な形を免除に加えるのは規約の目的を裏切る。**免除は届きすぎても違反 0 件の緑にしか
ならないので、広げたあとで気づく手段が無い。

### (b) を落とした理由

上の番号衝突が実在するので、受容すると曖昧なまま増え続ける。増加が止まらないことは
再計測が示している (起票時 12 件から 26 件へ)。

### (c) が使えると分かった根拠

- `gh pr merge` は `--subject` を持つ。既定の生成に任せない経路が最初から存在する
- 配布元には既に免除形で終わるコミットが 4 件ある。手で書いたクローズコミットがそれで、
  **規約に合う形は既にこのリポジトリで使われている**

### 代償と、その置き場

(c) の代償は「毎回忘れずに渡す」規律が要ることである。忘れても赤くならないので、
これは本 Issue が指摘した構造と同型の弱さを残す。

規律の置き場は 2 つに分けた。値を 2 箇所に書かないため、形の canonical は 1 つに寄せてある。

| 置き場 | 持つもの |
| --- | --- |
| `dev-workflow:in-repo-issue` の `## PR / コミット規約` | 書くべき形と、(a) を採らなかった理由 |
| `dev-workflow:commit-and-pr-message` の受け渡し表 | `--subject` を省略しないこと。形は再掲せず参照 |

免除の定義そのものは `issue-id.py` が canonical なので、どちらの skill にも再掲していない。

### CI での検出は入れない

main への push で新しい subject を検査する job は技術的に置ける
(トリガに `push` の main があり、surface は存在する)。採らなかったのは、
**マージ後に赤くなっても履歴は直せない**ため。直せない違反を報告し続ける検査は、
恒久的に赤いか、恒久的に無視されるかのどちらかになる。

「surface が無い」というこれまでの記述は正確ではなかった。無いのは surface ではなく、
検出したあとに取れる行動である。

### 既存の履歴は受容する

配布元 26 件、消費側 161 件は履歴なので直せない。過去分は受容し、以後のマージから適用する。
