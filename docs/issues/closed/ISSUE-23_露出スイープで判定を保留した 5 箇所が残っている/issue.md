## 裁定 (2026-09-16)

5 箇所すべてを直した。判断は案を並列に生成して横断検証にかけ、通った案を採っている (生成 4 体 /
検証 1 体)。落ちた案は 5 件で、検証が出した代案の側を採った。

### A. 出所を落としても主張は成立した

A1 は話題名 2 つを落とし、代わりに「別々の話題で 2 本」「識別子は衝突しないまま」を足した。名前が
担っていた情報は (a) 実際に起きたこと (b) 2 本という件数 (c) 2 件が別々の話題だったこと の 3 点で、
(c) は「1 つの話題での偶発ではない」を支えている。単に名前を削ると罠の射程が狭く読めるので、
言い換えて明示的に残す必要があった。

同じファイルに残した記述のうち、例の列挙の一員であるものはそのままにした (本 Issue の棄却基準)。
ただし「実際に」付きで実運用側の読みを固定していた 1 行は、A1 を直しただけでは片方が他方を裏付ける
形が残るので、仮定形へ一般化した。**落とす作業は 1 行ずつでは閉じない。**個々が棄却基準に合致して
いても、生き残った行の組み合わせが落とした情報を復元することがある。

A2 は日付を落とし、「止まった時点は後から遡って特定できた」を足した。日付が実際に担っていた情報
(停止点が特定可能な粒度で分かっている) を、年表を出さずに残すためである。

closed の Issue を編集した。本文の主張・機序・決定を変えず出所だけを落とす変更なのでスナップ
ショットとしての同一性を壊さない、という判断 (ユーザーの裁定)。reopen はしていない。この日付は既に
push 済みで履歴からは消せないので、減るのは現ツリーの面だけである。

### B1. 判定条件はプロジェクト側へ追い出した

`e2e-scenario-impact-check` の 4 用途すべてでディレクトリ名を落とした。用途ごとに向きが違う。

| 用途 | 向き | 直した形 |
|---|---|---|
| 早期 skip の判定条件 | 緑の向きを間違える | 「画面を構成するコードの変更が無い」と能動的に判定できたときだけ skip。既定は skip しない側 |
| E2E テストの置き場の判定 | fail-closed (無駄に agent が立つ) | 同じ条件へ統合 |
| 入力収集と出力の例 | 表記のみ | 置き場の決め方を節として足し、例はプレースホルダへ |
| 改善余地の第三ケース | 解決済みの記録が未対応欄に残る | 統合で消えたので残余費用だけ書き直した |

1 つ目が最も重い。ディレクトリ名を持たない配布先では条件が恒真になり、検査せずに Skip OK を
返す。0 件は「変更が無い」と「そこを見ていない」を区別しない。

先例 (`pre-merge-quality-gate` の Phase 3 が検証コマンドの入口をプロジェクトの CLAUDE.md へ
委譲した形) は、そのままでは足りなかった。あちらは分からなければ実行できず失敗が loud に出るが、
こちらは分からないことが「マッチ 0 件」から「変更なし」へ化けて silent に緑になる。だから参照化に
加えて「決まらないときは skip しない」という向きの規定と、根拠を書く出力欄を足している。

### B2. skill の責務を「書き出し」へ縮めた

`session-handoff` は hook の挙動 (経路の数・経路ごとの締め・注入の規則) を再掲していた。再掲を
全部落とし、hook を同梱しないことを宣言し、hook が無い環境を正規の縮退モードとして書いた
(ユーザーの裁定)。

手順 4 は「実体の有無」ではなく「settings.json の登録の有無」で判定する形にした。実体があっても
登録が無ければ読み手が居ないので、実体を見る形では「実体は有るが登録が無い」状態を通してしまう。

副次的に、経路の数の drift が構造的に消えた。この skill は発動経路を 3 つと書いていたが、hook 側は
4 経路でこの skill を名指ししている。数を再掲しなければ数はずれない。

配布対象から外して機構ごと hook の隣へ戻す案も出たが採らなかった。設計としては筋が通る (検知 /
手順 / 書式の 3 層が 1 機構で、ファイル種別の境界で 2 リポジトリに割ったのが drift の原因) が、
実現に未実測の前提を含むため別 Issue へ切り出した。

### C. 語を置き換えた

組織的な運用を前提にした語を落とすだけでは、規格の出所が無指定になって読み手が探しにいく。実測
すると 3 つの規格はいずれも同じファイル内の節が canonical なので、出所を本 skill 自身へ名指しする
形にした。露出の是正と同時に正確性の是正でもある。

### 起票時の記録に取り違えを 1 件見つけた

着手時に「B の `:79` は既に一般化済みなので解決している」と判断したが、これは誤りだった。見ていた
のは隣接する別の行 (URL path をプレースホルダへ直した箇所) で、`:79` が指していたのはルート定義
ファイル名と画面パスを例に使った別の行である。前者は ISSUE-15 の PR で直っており、後者は残って
いた。

同じ節の中で、直った行と残った行が隣り合っていた。保留リストの行番号だけを頼りに現物を確かめると、
この取り違えは「解決済み」という妥当に見える結論で返る。次のスイープでは行番号ではなく、記録された
「種類」の側と現物を突き合わせること。

### 検査で捕捉できる形だったか

ISSUE-15 が設計した 3 層に当てると、機械検査で捕まるものは 1 件も無い。

| 箇所 | 層 1 (`.gitleaks.toml`) | 層 2 (禁止語リスト) | 層 3 (ゲートの観点) |
|---|---|---|---|
| A1 の話題名 | 形が決まらない | 一方は禁止語リストへ載せられない種類の語 | 届く |
| A2 の年月日 | 漏洩の形でない | 固有名詞でない | 文脈を読めば届く |
| C の語 | 対象外 | 一般名詞で誤検出が増える | 届く |
| B1 / B2 | 対象外 | 対象外 | 届かない |

B 面はどの層も見ていない。層 1 と層 2 は漏洩の形を見るので対象外で、層 3 の観点は「公開してよい
状態か」を見るので「配布先で動くか」には届かない。この Issue が B を「露出ではなく別の欠陥」と
分類したことが、そのまま「担当する検査層が存在しない」ことを意味していた。層 3 へ観点を足すかは
別 Issue とする。観点を増やすとゲートの体数が増えてリミットに直接効くので、配分の判断が要る。
