# fix: --next が規約外の名前の Issue ディレクトリを数えず同じ識別子を返す

## 背景

出所は dotfiles のセッションから受けた skill の欠陥報告 (受け箱経由、2026-11-10)。

- 報告 (実測): 規約の形 (`<ID>_<タイトル>`) でないディレクトリを `--next` が Issue として数えず、既存と同じ識別子を返した。報告者の提案: 初期化の前に既存の Issue ディレクトリを規約の形へ移す手順か、規約外のディレクトリを検知して止まる仕組み

### 本リポジトリでの再現 (2026-11-10)

`docs/issues/` 直下に名前の形だけを変えたディレクトリを置いた git リポジトリを作り、skill 同梱の `issue-id.py` の `--next` と `--check` を回した。

| 置いたディレクトリ | `--next` の出力 | `--next` の rc | `--check` の rc |
|---|---|---|---|
| `ISSUE-1_a` `ISSUE-2_b` (対照) | `ISSUE-3` | 0 | 0 |
| `1-a` `2-b` | `ISSUE-1` | 0 | 1 |
| `1` `2` | `ISSUE-1` | 0 | 1 |
| `foo` `bar` | `ISSUE-1` | 0 | 1 |
| `ISSUE-1_a` `2-b` `3` | `ISSUE-2` | 0 | 1 |

最後の行では、番号 2 を持つ `2-b` があるのに `--next` が `ISSUE-2` を rc 0 で返す。`--check` は規約外のディレクトリを全件「ディレクトリ名が形式でない」と報告して rc 1 になる。

つまり検知する仕組みは `--check` に既にある。欠けているのは、採番の経路 (`--next`) と初期化の手順がその検知を通らないこと。`--next` が数えるのは接頭辞を任意にした `<N>_` の形 (`ANY_ISSUE_DIR`) だけで、それ以外の名前は番号を持っていても黙って飛ばす。

## 決定 (2026-11-10)

(a) を採った。止める条件は `--check` と同じ `ISSUE_DIR` ではなく、採番が数える `ANY_ISSUE_DIR` に当たらないこととした。`ISSUE_DIR` で判定すると、旧記法 (`<N>_<title>`) のディレクトリが残るリポジトリ (ISSUE-22 が数えた混在) で採番が全部止まる。旧記法は番号を読めるので衝突しない。入口は増やさず、`--next` の止まる条件を 1 つ足すだけにした。

止める範囲は番号の重複と同じく現ツリーと全 ref にした。番号を読めない名前は、どの番号を持つ Issue なのかを採番の側では判定できないので、番号を持たない名前 (`foo`) も止める。

ref にしか無い名前でも止める。止めないと、そのブランチがあとでマージされたときに番号が衝突しうる。代わりにエラー文で、出所が ref のものは作業ツリーの改名では解けないことと、ref の側の直し方を示す。同じディレクトリが複数の出所にあるときは 1 行にまとめる (gate で ref の数だけ同じ行が並ぶと指摘された)。

配布先への影響: `--next` は skill に同梱した `issue-id.py` から呼ばれるので、配布先が `scripts/` へ写した版や `--check` の取り付けの有無に関係なく、pin を上げた時点で次の 2 系統で止まり始める。リリースノートでは、消費側の呼び出しが壊れる変更として扱う。

- 現ツリーの `docs/issues/` 直下か `closed/` 直下に、採番が数えられない名前のディレクトリがある。規約外の名前の Issue (`2-b` など) と、`templates/` 以外の補助ディレクトリ (未追跡の空ディレクトリ、隠しディレクトリ、`closed/<年>/` のようなまとめを含む) の両方が当たる。どちらも `--check` が以前から命名違反として報告していた
- ローカルか remote のブランチにだけ規約外の名前が残っている。こちらは `--check` が見ないので、`--check` が緑のまま `--next` だけが止まる
