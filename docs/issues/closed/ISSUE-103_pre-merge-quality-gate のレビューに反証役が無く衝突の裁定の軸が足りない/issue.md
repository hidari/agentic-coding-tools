# docs: pre-merge-quality-gate のレビューに反証役が無く衝突の裁定の軸が足りない

## 背景

出所は dotfiles の採否台帳の K133-107 で、Hidari が「採る」と判断した知見 (2026-11-10 に dotfiles のセッションから受けた)。置き場の案は、`dev-workflow:pre-merge-quality-gate` の Phase 1 に「観点ごとの reviewer と反証役」の形を足し、観点どうしが正面衝突したときの裁定を足すこと。

現在の Phase 1 は観点ごとに reviewer を並列で起動するが、指摘を独立に検証する役を持たない。観点どうしの衝突については、Phase 2 に「観点どうしが正面衝突したときの裁定」節が既にあり、「その変更で検証力が増えるか減るか」の 1 軸で裁定する。下の報告のうち、規約の canonical を先に引く軸と、パッケージ間の参照の向きの軸はこの節に無い。

以下はどれも別のリポジトリのセッションの申告で、本リポジトリでは再現していない。

### 観点ごとの reviewer と反証役

- 報告 (実測): 最終レビューを、観点ごとの reviewer と観点ごと 1 体の反証役の Workflow にした。反証役がその観点の指摘をまとめて判定する形にすると、体数は観点数の 2 倍で済む
- 報告 (実測): 指摘ごとに 1 体の反証役を付ける形と、確信度の閾値を超えた指摘ごとに独立の検証役を付ける形も回した。前者では指摘の ID を Workflow のスクリプト側で採番した。後者では検証役が、reviewer の指摘の取りこぼしと修正案自体の欠陥を補った。修正案の欠陥の例は、複数の呼び出し元を持つ共有部品のコメントを 1 つの呼び出し元への参照に縮めると、他の呼び出し元から読んだときに参照先がずれるというもの
- 報告 (実測): 反証役は指摘を「事実か」と「実害があるか」の 2 軸で検証し、両方とも反証されたものだけを落とした

### 観点どうしが衝突したときの裁定

- 報告 (実測): 説明の canonical をテストに置くかプロダクトに置くかで観点が割れたときは、パッケージ間の参照の向き (プロダクトからテストを指さない) で裁定した
- 報告 (実測): 「その変更で検証力が増えるか減るか」を裁定の軸にした。これは Phase 2 の既存の節と同じ軸で、報告は既存の規定と同じ結論に独立に至った記録として残す
- 報告 (実測): simplify の観点の中で「関連節を識別子だけにする」と「リンクに戻す」が衝突したときは、規約の canonical (`dev-workflow:in-repo-issue` の「Issue 間の参照」節) で裁定した

### 複数の観点が同じ重複を指したとき

- 報告 (評価は推測): reuse・簡素化・altitude の観点が独立に同じ重複を指したら、共通の helper へ寄せる価値が高い
- 報告 (実測): 寄せた後は「helper の絞りを外す」「呼び出しを外す」「失敗どうしの一致で緑にならないか」の変異を入れ、取り付けまで赤くなることを確かめた

### boy-scout sweep の brief (追記 2026-11-10)

dotfiles のセッションから追加で受けた報告。

- 報告 (提案、実測の事例に基づく): boy-scout sweep の brief に「触ったファイルを全部通して読む」と「読めなかった範囲を報告に書く」を明記する

## 本リポジトリでの試行 (2026-11-10)

この Issue を起票した PR のマージ前ゲートを、観点ごとの reviewer 4 体と観点ごとの反証役の Workflow で回した。この形は gate の手順のレーン構成 (`Agent` tool のレーンと `Skill` tool のレーン) とは違う。指摘の無かった観点は反証役を起動しないので 7 体だった。反証役は指摘ごとに「事実か」「実害があるか」「修正案に欠陥が無いか」を判定した。reviewer は Bash を持つ agent 型にし、diff はファイルで渡した (ISSUE-102 を避けるため)。指摘は 5 件で、反証役は 5 件とも事実かつ実害ありと判定した。修正案に欠陥ありとした件は無かったが、5 件中 4 件で修正案に足りない手順 (タイトルを直すならディレクトリ名も揃えて改名する、など) を補った。

## 決定 (2026-11-10)

- 反証役は、`Agent` tool で起動するレーンのうち指摘を返したものごとに 1 体にした。指摘ごとに付ける形は、指摘数に比例して体数が読めなくなるので採らなかった。体数の上限は、タスクの「数で書く」から変えて、導出の形 (`Agent` tool で起動する側はレーンの数の 2 倍を超えない) で書いた。`Agent` tool で起動するレーンの数は PUBLIC 漏洩スイープの有無で変わり、数で写すとレーンを増減するたびに写しが取り残される。総数を literal で書くかの扱いは ISSUE-47 に残した
- Hidari の裁定で、手順は `Agent` tool だけで組める形で書き、Workflow tool は利用者が起動を許している環境で同じ形を組む選択肢にとどめた
- `simplify` と e2e skill には反証役を付けない。どちらも `Skill` tool で起動するレーンで自分の手順を持ち、`simplify` は修正の適用まで行う
- 衝突の裁定は、規約の canonical、参照の向き、検証力の増減の順に引く形にした。既存の節を書き換え、節は増やしていない
- 複数の観点が同じ重複を指したときの扱いと、寄せた後の変異の確認は書かなかった。前者は報告自身が評価を推測としており、どちらも出所が 1 件の報告しかない
