# feat: jev-lint の採用方式を決めて取り込む

## 背景

mizchi/jev-lint は、コメントや識別子の名前が直下のコードと食い違っている箇所を LLM で採点する lint である。このリポジトリは「コメントは WHY を書く」「WHAT は識別子で示す」を規約に持つが、どちらも機械検査に落ちておらず、レビューだけが防衛層になっている。この層を自動化できるかを確かめるために試用した。

試用の実測は次のとおり (2026-09-21 から 09-22 にかけて、npm の 0.5.0 で測った)。

- 費用と速度: `scripts/` 全体で61リクエスト、約216万トークン、0.079ドル、10秒。リポジトリ全体の dry-run では367リクエスト、約905万トークン、0.38ドル
- 検出の質: `scripts/` に対する findings 6件のうち、有用が3件 (いずれも識別子の名前が中身と合っていないという指摘)、誤検出が3件。ただし 0.5.0 には、言語をまたいで同じ id を持つ rule が最後に読み込んだ TypeScript 版へ解決される不具合があり (0.6.6 で修正)、この試用は Python のファイルを TypeScript 版の問いと cutoff で採点していた。Python の rule の測定にはなっていない
- 日本語コメントの扱い: 嘘のコメントを仕込んだ写しで陽性対照を取ったところ、日本語でも英語と同等に拾った (嘘は0.84から0.96、正しい主張は0.06から0.15。どれも3回の試行でばらつきはほぼ無い)。ただし拾えるのは露骨な矛盾に限る。射程はコメントとその直下のコードで、ファイルをまたぐ散文の真偽は見ない
- 依存は2つだけ (`@ast-grep/cli` と `yaml`)

そのまま採用できない理由が4つある。

- 上流の SKILL.md と command 4本が `npx -y jev-lint` で書かれており、版が固定されていない。加えて `npx` はこの開発環境では許可されていない
- pnpm 12 では `@ast-grep/cli` の postinstall が `ERR_PNPM_IGNORED_BUILDS` を起こすので `--allow-build=@ast-grep/cli` が要る。postinstall の中身はプラットフォーム別パッケージの実行ファイルを置くだけで、読んで無害を確認してある
- 上流の `commands/prose.md` は `node_modules/jev-lint/rules/markdown` が存在する前提で書かれているため、dlx 経由の呼び出しでは成立しない
- API キーは環境変数から読まれて外部の採点 API へ Bearer で送られる。送り先は環境変数と設定ファイルの両方で差し替えられる。エージェントがキーを読んで第三者へ渡す形は classifier が止めるので、実行はユーザーが行う必要がある

提案済みの方向は「版の固定と `pnpm dlx` の呼び出しとキーの扱いだけを持つ薄いラッパを自前で持ち、ルールの書き方は上流の skill を参照する」。採用方式そのものはまだ裁定を受けていない。

## 0.7.0 で測り直した結果 (2026-09-25、`scripts/`)

`check scripts --no-config --cache none --retry 3` で、送り先を `--base-url` で固定して測った。

- 1761件の subject を3回ずつ聞き、指摘は7件 (var-name-describes-value が4件、fn-name-promises が3件)。0.265ドル、201リクエスト、40秒
- コードを読んで判定すると、有用が2件、誤検出が5件。有用な2件はどちらも改名で済む軽いもので、`scripts/check-issue-closure.py` の `children` は分割する前の文字列を、`scripts/test_check_related_refs.py` の `INHERITED` は子プロセスで走らせるテスト ID を持っている。fn-name-promises の3件はすべて誤検出だった
- cutoff のすぐ下にあった10件は、有用0件、境界1件、誤検出9件。cutoff を下げると誤検出だけが増える
- `scripts/test_check_issue_closure.py` は `max_tokens_exceeded` で146件の subject に答えが返らなかった。このファイルの指摘0件は、見ていない分を含む
- 上の「そのまま採用できない理由」4つは 0.7.0 でも残っている。加えて Node 24以上が必要になった。設定ファイルの `baseUrl` による送り先の差し替えは、`--base-url` を明示すれば上書きできる

## 決めたこと (2026-09-25、ユーザー裁定)

- 採用方式を決める前に、上流の最新版で測り直す。試用の数字は上の注記のとおり使えないため
- 測り直しは本リポジトリの Python だけで終えず、他の言語のリポジトリでも行う
- 実行は手動の advisory に限り、送るのはコミット済みの範囲にする。未公開の差分を外部 API へ送る経路 (pre-commit への取り付けを含む) は作らない
- 同じ作者の jev-test-filter は ISSUE-71 で扱い、今回は取り込まない

## 他の言語のリポジトリでの測定 (2026-09-25)

TypeScript と Rust の private リポジトリ 3 つを、同じ手順 (0.7.0、`--retry 3`) で測った。指摘は合わせて 647 件で、rule の群ごとに件数を決めて抜き出した 95 件をコードを読んで判定すると、有用 32%、境界 22%、誤検出 46% だった。1 つのリポジトリは途中で API のクレジットが尽き、subject の約半数に答えが無い。rule ごとの内訳と、残す rule と外す rule の根拠は `ISSUE-65-spec.md` の「厳選する rule」節にある。

## 決めたこと (2026-09-26、ユーザー裁定)

- 採用方式は、厳選した rule を持つ薄いラッパを自前で持ち、上流の版上げに追従できるようにする。単体 skill `skills/tooling/jev-lint-curated/` として取り込んだ
- 送る範囲、置き場、消費側の調整、版の追従、モード、rule の選び方の裁定と、設計は `ISSUE-65-spec.md` が持つ。実装の計画は `ISSUE-65-plan.md`
- moonbit の 7 項目は一覧に載せて compat で追従するだけにし、parser の対応は ISSUE-73 に切り出した
- 最終レビューの指摘のうち、設計の判断が要るものと挙動を変えるものはマージの前には直さず、ISSUE-74 に切り出した。どれも送る範囲とキーの隔離には関わらない
