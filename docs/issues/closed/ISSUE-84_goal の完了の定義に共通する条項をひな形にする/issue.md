# agent: /goal の完了の定義に共通する条項をひな形にする

## 背景

ISSUE-81 と ISSUE-82 は、Claude Code の `/goal` に貼る完了の定義を本文に持つ。`/goal` の判定役は会話に出た出力しか読まずツールも呼ばないので、条件文は自己完結させる必要がある。そのため、証拠の出し方 (rc の表示、ログの抜き方)、3 通りの終わり方、「未完了:」の目印、公開面に載せない形、といった条項を 2 本がそれぞれ持っている。起票の PR の中で、同じ条項を 2 本で歩調を揃えて直す手間が既に起き、片方にだけ入った条項 (Bash のタイムアウト、`docker run` に `-t` を付けない) も出た。

判定役は条件文の外を読まないので、canonical は参照先ではなく貼るためのひな形になる。置き場は dev-workflow の component skill が候補になる。in-repo-issue やその Issue テンプレートは、`/goal` を使わない配布先にも届くので向かない。

事例はまだ 2 本で、起票の時点ではどちらも実行していなかった (ISSUE-81 は 2026-09-28 に実行した。下の節)。一度も走っていない条項を canonical にしないため、ISSUE-81 を `/goal` で回した結果を見てから着手する。

## ISSUE-81 の実行から拾った材料

### 実行役の側

2026-09-28 の実行から拾った。

- 条件 3 の「ログに postinstall script did not run が無い」は、その文言がどこかに実在することを示す対照を求めていなかった。実行役は registry の tarball を読む対照を足した。一方、コンテナの中で回したもう 1 つの対照 (astgrep-marker.sh) は、文言を持つ唯一のファイルを除外していて判別力が無かった。これはマージ前ゲートに足した一次資料との突き合わせで見つかった。0 件を条件にする条項は、対照を置くことと、その対照が判別できることまで条件に書く候補になる
- スクリプトの rc で段の成否を示すとき、rc が何を覆うかを条件は決めていなかった。ISSUE-81 の stage1.sh の rc が見たのは、前提の項目のうち 3 つだけだった。`pnpm store path` の rc は終了コードに反映せず、取れなかったときも rc=0 になりうる形だった
- 「pnpm はネットワーク無しでも起動できる形にする」は、手段を指定していなかった。実行役は pnpm 12.3.4 の配られ方を調べ、`@pnpm/exe.<platform>` の tarball を integrity で照合して置いた。取得と照合を共通化した `scripts/ci/download-and-verify.sh` はあるが、契約が sha256 だけなので使っていない。そのスクリプトが付ける `--proto '=https' --tlsv1.2` も、Dockerfile には付いていない。ひな形が取得の段を持つなら、このスクリプトを sha512 へ広げて参照するかを決める材料になる
- 「ホスト側のパスは $PWD で書き、$(...) を使わない」は射程が曖昧だった。実行役は、コンテナの中のスクリプトでもコマンド置換を避け、一時ファイルと `read` を往復させた。一方で、Bash 呼び出しの先頭の `cd` にはホストの絶対パスを書いていた。公開面に載せた記録 (ISSUE-81 の結果節) では、ホスト側のパスを相対パスか $PWD で書いた
- 完了の定義の外で実行役が足したもの: 結果節の記録をマージ前ゲートで、一次資料と突き合わせるレーンに通した。別々の観測を 1 つの因果に結んだ記述 (上の astgrep-marker.sh の件) と、tarball の中身の不正確な記述が、そこで見つかった

### 判定役の側

`/goal` が終わった後に、そのセッションの transcript (JSONL) から拾った。`/goal` の判定の記録は、transcript に 2 種類の行で残る。`type` が `attachment` で `attachment.type` が `goal_status` の行と、`subtype` が `stop_hook_summary` の行である。ISSUE-81 の回では次のとおりだった。

- `goal_status` は 2 行あった。1 行目は条件を置いたときの `met: false`、2 行目は達成したときの `met: true` で、後者は `reason` (判定の理由の文)、`iterations: 1`、`durationMs: 3177504`、`tokens: 483024` を持っていた
- `/goal` の hook が判定したのは最後の 1 回だけだった。実行役がバックグラウンドの subagent を待ってターンを終えた 12 回の停止では、`stop_hook_summary` に出る hook は handoff-sentinel の 1 本だけで、`/goal` の hook は記録に現れない。バックグラウンドの作業が残っている間は判定しない作りなのかは、確かめていない
- `met: true` の行の `reason` は、実行役の最後のメッセージ (完了の定義との対応表と、その前後の PR の行と「ゲートで直したこと」の節) をほぼそのままなぞっていた (`reason` の中の句の例: 「verified against registry tarball」「additional primary-source verification lane」「all 4 CI jobs passing」。どれも `reason` に 1 回ずつある)。途中のツールの出力を読み直したかは、記録からは分からない (ISSUE-82 の回では読んでいた。下の節)。実行役の最後のメッセージの書き方が判定を大きく左右する、という見立てになる
- `reason` は「満たすこと」の 1〜5 を順に挙げていて、「進め方の決まり」(上の `cd` の絶対パスの件など) には言及していない。判定役が進め方の決まりを見たうえで問題なしとしたのか、見ていないのかは、記録からは区別できない。選言の条件 (1〜5、失敗したときの出口、ターンの上限) の外に置いた決まりは、判定されると当てにできないので、守らせたい決まりは満たすことの側に入れる候補になる
- 条件文の長さには上限がある。ISSUE-83 の仕上げで置いた条件文は `Goal condition is limited to 4000 characters (got 4818)` で拒まれた (2026-09-29)。前提・進め方・制約をファイルへ出し、条件文からはそのファイルを指して 4000 文字に収めた。ひな形の条項を条件文に写す形だと、この上限に当たりやすい
- 条件文の読み違いの候補: ISSUE-83 の判断のために回した判定役 (Fable) は、ISSUE-82 の条件 5 の「job の数が 3 で抽出した runs-on の数と一致」を「job の数が 3」と読んだ。番号を参照する句は、「完了の定義の N で」のように参照だと分かる形で書く (ISSUE-82 は直した)

## ISSUE-82 の実行から拾った材料

2026-09-29 (UTC) に ISSUE-82 の完了の定義を `/goal` で回し、PR 75 を作って達成した。

### 実行役の側

- 条項どうしの順序が衝突した。ISSUE-82 の完了の定義の 4 は CI (26.04) の python3 の版を結果節に書いたうえでタスクの [x] 化とクローズを 1 コミットにすることを求め、完了の定義の 5 は PR を作ってから CI の run を確かめることを求める。CI の版は PR の run からしか取れない (ci.yml の trigger は `pull_request` と main への push だけ) ので、4 のクローズは 5 の PR を作った後になった。実行役は PR を作ってから版を足し、クローズのコミットを積んで 2 回目の push をし、5 の検証は最後の run で行った。条件文はこの順序を決めていなかったので、判定に響く抜けではなかったが、クローズ経路の「PR を作る前に同梱すれば run が増えない」とは合わなかった
- 件数を根拠にする条項で、取得の失敗が 0 件に化けた。完了の定義の 5 の「/home/runner が現れるかも grep する」の最初の実行は `gh api .../actions/jobs/<id>/logs` でログを取ったが、ログに端末のエスケープ系列があると gh は 1 行のエラーを返して rc=1 になり、4 job とも出現数 0 になった。実行役はログの rc と行数を並べて出していたので気づき、`gh run view <run> --log --job <id>` で取り直した (20〜21 回)。0 件や件数を根拠にする条項は、見た量 (rc と行数) を並べて出すことまで条件に書く候補になる
- マージ前ゲートは今回も条件の外で効いた。一次資料と突き合わせるレーンとコードレビュー、ボーイスカウトの 3 観点が、完了の定義の 3 のための分類表から 1 ヒット (ISSUE-83 の関連節の行) が漏れていることを独立に見つけた。実行役は「全ヒットを示す」を満たしたつもりでいた。判定役が判定したのはゲートの修正の後だった (下の節)
- この Issue の材料を拾う作業でも同じ形を踏んだ。transcript の `stop_hook_summary` に `/goal` の hook があるかを「goal」という文字列で探して 0 件と読んだが、hook の command は日本語の条件文そのもので、この文字列を含まない。クローズの前のゲートで一次資料と突き合わせるレーンが見つけ、hook の数 (`hookCount`) で数え直した

### 判定役の側

このセッションの transcript から拾った。

- `goal_status` は ISSUE-81 と同じく 2 行で、達成の行は `iterations: 1`、`durationMs: 1376317`、`tokens: 72112` だった。条件を置いてから達成の判定までの `stop_hook_summary` は 8 行で、`/goal` の hook (command に条件文そのものが入る) が現れるのは達成の判定の直後の 1 行 (`hookCount: 2`) だけだった。ほかの 7 行は、subagent かバックグラウンドのコマンドの完了を待ってターンを終えた停止で、hook は handoff-sentinel の 1 本だけだった。今回も、待っている間の停止では判定されていない
- `reason` は、実行役の最後のメッセージには無く、ツールの出力にだけある形を引いていた (「/home/runner の出現数: 20-21 回」の「/home/runner の出現数:」は、完了の定義の 5 を確かめるスクリプトの出力の文言で、最後のメッセージにも結果節にも PR のコメントにも無い。`labels=['ubuntu-26.04']` も同じスクリプトの出力の形)。一方、`reason` の「dpkg --print-architecture: amd64」はスクリプトの出力 (`dpkg arch: amd64`) には無く、結果節の表の見出しと値を「見出し: 値」に組み直した形なので、判定役は結果節も読んで言い換えている。判定役が読むのは最後のメッセージだけではない。ISSUE-81 の回の「途中のツールの出力を読み直したかは、記録からは分からない」は、この回では読んだ側に倒れる
- `reason` は完了の定義の 3 について「1 つ目のヒットは ci.yml の 4 行のほかに 11 件で、すべて残した」を引いて満たしたとした。判定の時点 (17:20 UTC) ではゲートの修正 (17:08 UTC) が入っていて表が載せるヒットは 11 件だったので、この判定は正しい。ただし同じ文は、ゲートの前の 10 件しか載せていない表にも書かれていた。判定役が表が載せるヒットの数と数え合わせたのかは記録から分からないので、文を引くだけの判定だったなら、完了の定義の 3 はゲートの前の表でも満たしたとされていた (全体の判定はゲートの前には起こりえない。まだ PR が無かった)。実行役が書く主張の文が判定を左右するという ISSUE-81 の見立ては、この意味で残る

## 裁定 (2026-09-29)

ユーザー裁定で、ひな形の skill は作らない。

- 共通化で減る痛みは、起票のときに 2 本の条件文を揃えて直す手間だけだった。2 本を実行して、条件文が原因で止まった箇所は無かった (上の順序の衝突は push を 1 回増やしただけ)
- 品質を支えたのは条件文よりマージ前ゲートと一次資料との突き合わせのほうだった。判定役が主張を数え直すかは確かめられない (上の判定役の側の、完了の定義の 3 の件)。ひな形に条項を足しても、この層の代わりにはならない
- 条件文は 4000 文字が上限で、共通の条項を貼るほど本題の条件に使える文字が減る
- dev-workflow の skill にすると、PUBLIC に配る面と保守の面が 1 つ増える

3 本目の `/goal` を書くときは、ISSUE-81 と ISSUE-82 の完了の定義を写し元にし、この Issue の材料を読む。
