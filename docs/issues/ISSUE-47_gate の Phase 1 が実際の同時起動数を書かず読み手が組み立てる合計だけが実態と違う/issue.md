# docs: gate の Phase 1 が実際の同時起動数を書かず読み手が組み立てる合計だけが実態と違う

## 背景

`dev-workflow:pre-merge-quality-gate` の Phase 1 は、レビューを並列で回す手順を持つ。

そこに書かれている個々の記述に誤りは無い。にもかかわらず、**読み手が自分で組み立てないと
Phase 1 が消費する agent の総数に届かない。** 節は 4 つのレーンを launch するとしか書いておらず、
レーンのうち 2 つは `Skill` tool 経由でさらに agent へ展開する。

agent の本数は週次リミットという実制約に直結するので、実行者が事前に把握できる必要がある。
把握できないと、上限を設けている運用でも黙って超過する。

## 実測 (2026-08-31)

`plugins/dev-workflow/skills/pre-merge-quality-gate/SKILL.md` を逐語で確認した。

引用が実在することの確認 (文言が存在するかであって、記述が事実かは別に見る):

| 行 | 記述 |
| --- | --- |
| 49 | 4 つを「同じメッセージ内で 4 つ並列に launch する」 |
| 54 | 「`simplify` 自体が reuse / simplification / efficiency / altitude の 4 並列内部実行を行う」 |
| 84 | 「並列で投げると 30〜90 秒で 4 つの結果が揃う」 |

**総数を書いた行がどこにも無い。** SKILL.md 全 185 行を数字を含む行の総なめと
`本数|リミット|上限|同時|並列` の grep で見たが、総数にも同時本数にも言及した行は 1 つも無い。
`plugins/dev-workflow/` 全体でも同じ。

Phase 1 が消費する agent の内訳:

| レーン | 起動の種類 | agent 数 | 数の出所 |
| --- | --- | --- | --- |
| `simplify` | Skill | 4 | **この SKILL.md の外**。下記参照 |
| `feature-dev:code-reviewer` | Agent | 1 | 56 行 |
| boy-scout-sweep (`general-purpose`) | Agent | 1 | 59 行 |
| `dev-workflow:e2e-scenario-impact-check` | Skill | 0 または 1 | **gate 側に数が無い**。e2e skill の SKILL.md 61 行 |
| 合計 | | **6 または 7** | どこにも書かれていない |

e2e は「フロント変更がある場合、`Agent` tool で `general-purpose` を起動する」(同 skill 61 行)。
早期 skip の条件は同 45 行と 57 行。**このリポジトリには `frontend/` も `e2e/` も無い**ので、
自リポで gate を回す限りこのレーンは常に skip し、実効は 6 側になる。

### `simplify` の 4 の出所について

`simplify` は built-in skill で、定義ファイルがこのリポジトリにも配布先 (`~/.claude*/skills/`)
にも存在しない (`find` で確認、0 件)。値を確かめられるのは skill を実際に invoke したときに
配られる本文だけで、そこには「Launch 4 independent review agents via the Agent tool, all in a
single message」とある (実測)。

つまり **この数の canonical は skill 本体にあるが、静的には読めない。** gate SKILL.md はその値の
写しを 54 行と 147 行の 2 箇所に literal で持っている。手当てを考えるときはこの既存の写し 2 つを
どうするかも同時に決めること。

## 何が問題か

「launch するレーンの数」と「消費する agent の数」が別物なのに、節は前者だけを書いて後者を
書いていない。読み手は gate SKILL.md の 49 / 54 / 56 / 59 の 4 箇所と、e2e skill の SKILL.md
61 行を突き合わせないと実態に届かない。**とくに e2e が起こす 1 本は gate 側に数として存在せず、
ファイルを越えないと確定しない。**

この形は「宣言が実態より狭い」欠陥にあたる。広い側と同じだけ危険で、狭い側は
「そこまでは起きない」と読める。しかも本数は実行してみるまで観測できないので、超過したことに
事後でも気づきにくい。

節のどの 1 行にも誤りが無いため、逐語のレビューでは見つからない。実使用して本数を数えた側だけが
気づける形になっている (実際、この Issue の出所も実使用の報告)。

## 検討の起点

- Phase 1 節へ総数を書く。値を literal で写すか「レーン数より多くなる」形にとどめるかを決める。
  写す場合、`simplify` の 4 は既に 54 行と 147 行の 2 箇所に写しがあるので、3 つ目を増やさない
  置き方を選ぶこと
- e2e の 1 本を gate 側から辿れるようにするか、e2e skill を読ませる形のままにするかを決める
- 起動前に本数を申告する手順を置くかを決める。上限そのものは skill の外 (実行者の運用) が
  持つので、skill は本数を知らせるところまでを射程にするのが妥当かを併せて判断する
