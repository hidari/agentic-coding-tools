# fix: GitHub 記法の免除が単一の前置しか持たず他リポジトリの参照を区別できない

## 背景

`issue-id.py` は GitHub の番号記法 (`#N`) を in-repo Issue の記法違反として報告し、自リポジトリの
PR を指す形だけを免除する。免除の判定は単一の文字列との後方一致で行う (定数 `GITHUB_REF_ALLOWED_PREFIX`
と、同ファイルの `before.endswith()`)。

この形が 2 つの問題を同時に抱えている。どちらも「エラーにならない」ので、検査を取り付けるまで、
あるいは取り付けても表に出ない。

### 免除したい前置を 1 つしか書けない

GitHub Issues から in-repo Issue へ移行したリポジトリでは、GitHub の Issue を指す参照が本文に残る。
移行後も GitHub 側の番号は永続するので、これは壊れた参照ではなく正しい参照である。しかし免除の
文字列と一致しないため、記法違反として報告される。

**実際にこの形が原因で、記法検査の取り付けを見送った配布先がある。** 差分だけを見る入口
(`--check-diff`) でも違反が残り、取り付けても緑にならないという判断だった。見送りの経緯は
そのリポジトリの CLAUDE.md へ明記されている。

ISSUE-32 は層 3 の完成後に「規模の小さい配布先から実地で取り付けを通す」と計画しているが、
この配布先では免除の制約が残っている限り同じ理由で止まる。層 3 が完成しても解けない。

### 免除が自リポジトリと他リポジトリを区別しない

判定は前置の文字列だけを見るので、他リポジトリの PR を指す形も無条件に通る。検査の目には
自リポジトリの PR に見える。

`## 関連` 節の規約は、他リポジトリの Issue を指すときリポジトリ名の前置を要求している。理由は
「番号は各リポジトリが独立に採番するので、前置が無いまま解決すると、たまたま番号が一致する
自リポジトリの Issue へ静かに解決される」ことだった。**PR 側にはこの規則が無く、検査も区別しない。**
同じ危険が PR の番号空間にも存在する。dotfiles の ISSUE-46 が実例を持つ。

### 2 つは同じ原因を持つ

前者は「通すべきものを通せない」、後者は「通すべきでないものを通す」で向きが逆だが、どちらも
免除が「どの記法を、どのリポジトリのものとして通すか」を表現できないことに由来する。片方だけを
直すと、もう片方は残る。

## 決めること

免除の表現をどうするか。候補を挙げる。

1. 定数を集合にし、`Issue ` を許す前置へ加える
   - 最小の変更だが、GitHub Issues が生きているリポジトリでは `Issue #N` が自リポジトリの
     Issue を指すので、無条件の許可は正解にならない
2. 免除をプロジェクト側の設定で与えられるようにする
   - リポジトリごとに事情が違う (GitHub Issues が生きているか、移行済みか) ので表現力は足りる
   - 設定の置き場と、設定が無いときの既定を決める必要がある
3. リポジトリ名を伴う形だけを免除する (`<owner>/<repo>#N` と同じ扱いへ寄せる)
   - `## 関連` 節の規約と形が揃う。ただし既存の `PR #N` が一斉に違反になるので、移行の順序が要る

どれを採っても、免除の canonical をどこに置くかは別に決める必要がある。定数のままにするか、
設定ファイルへ出すか、SKILL.md が持つかで、配布先から見た変更のしやすさが変わる。

## タスク

- [ ] 免除の表現を上の 3 候補から決める。決め手は「GitHub Issues が生きている配布先と移行済みの
      配布先が、同じ実装で別の判定を得られるか」
- [ ] 免除の canonical の置き場を決める
- [ ] 決めた形を実装する
- [ ] 変異注入で確かめる。免除の判定を壊したときに赤くなること、および免除すべき形が通ること
      の両方を見る (片方だけだと、免除を広げすぎた変更が緑のまま通る)
- [ ] ISSUE-32 の層 3 の取り付け手順へ、この変更が前提であることを書く
