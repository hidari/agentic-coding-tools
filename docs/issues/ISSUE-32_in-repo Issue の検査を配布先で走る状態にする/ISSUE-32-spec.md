# ISSUE-32 spec: in-repo Issue の検査を配布先で走る状態にする

配布先リポジトリの実名と実パスはこの文書に書かない。本リポジトリは PUBLIC なので、
配布先の分布は件数までに抽象化する。

## 解こうとしている問題

`issue-id.py` は識別子の記法を検査するが、pre-commit / CI への取り付けは
「プロジェクトの判断」として skill の外に置かれている。
配っただけでは検査は走らず、抜けはエラーではなく緑として現れる。

## 配線方式の選択

コミット時に走るコードは、ユーザー権限で、エージェントのツール権限プロンプトを
通らずに実行される。したがって配線方式の選択は供給連鎖の設計そのものになる。

| | remote hook (`repo: <URL>`) | 追跡下の写し (`repo: local`) |
| --- | --- | --- |
| 実行されるコードの所在 | pre-commit のキャッシュ配下 (作業ツリーに無い) | 自リポの追跡下 |
| 更新時に diff へ出るもの | `rev:` の 1 行 | スクリプト全文 |
| 上流侵害の到達 | **full SHA pin のときだけ** pin を上げるまで届かない | 写しを更新するまで届かない |
| 第三者への供給責任 | 受動的な依存面が生じる | 能動的な取り付け指示として**残る** |
| drift | 原理的に起きない | 起きる。検出で塞ぐ |

**追跡下の写しを採る。**

### pin の同等性は full SHA に限る

`rev:` に tag を書くと、上流が tag を動かすだけで、消費側に diff が 1 行も出ないまま
新しいマシンで別のコードが実行される。lightweight tag には可変参照の警告が出るが、
annotated tag では出ない。`pre-commit autoupdate` は `rev:` を最新 tag へ書き換える
コマンドなので、tag 運用を始めると 1 コマンドで pin が動く。

この段落はレビュー担当が pre-commit 4.6.1 の隔離環境で実測した結果に基づく。
起票側は再現していない。写しを採る決定には影響しないが、比較の根拠として記録する。

### レビューが起きる場所は 1 箇所に集約される

「写しなら全文 diff が出るのでレビューできる」だけでは足りない。
写しの供給元は apm が deploy した skill で、その更新は消費側 apm.yml の
1 行 SHA bump である。「1 行 bump では中身が分からない」という批判は
写し方式の供給鎖にもそのまま当てはまる。

正確には、**実質のレビュー地点は本リポジトリの PR フロー 1 箇所**に集約される。
写しの同期 PR にできるのは、その 1 箇所で何が起きたかを可搬にすることだけ。
したがって同期 PR の本文には上流の commit range を必ず併記する。

### 第三者への供給責任は消えない。形が変わる

`.pre-commit-hooks.yaml` を置かないことで消えるのは、pre-commit エコシステム経由の
受動的な依存面だけである。取り付け手順は PUBLIC に配る SKILL.md に載るので、
apm で skill を取った第三者のエージェントにも「自リポへコミット時実行コードを置き
`pre-commit install` せよ」と指示することになる。むしろ能動的に促すぶん、
供給者としての立場は残る。

この認識を持たないと、SKILL.md 側に第三者にも効く安全装置を仕様化する動機が失われる。
本設計では「hook block の固定テンプレート化」と「配置後の内容 hash 突合」が
その安全装置にあたる。

### 受容するリスク

- **単独運用では self-approve が残る。**層 0 の ruleset はエージェントの直 push 事故には
  効くが、アカウント侵害には効かない。required reviewers を置ける相手がいないため受容する
- **増分の ratchet は暗黙である。**ISSUE-28 が扱う `LINK_BASELINE` は件数が監査できる
  記録された ratchet だが、差分で絞る方式は既存違反をどこにも記録しない。
  増分が見落とした違反は記録なしで恒久 baseline 化する
- **内容 hash 突合は上流侵害を防がない。**hash も同じ経路で配られるため。
  防ぐのはエージェントの誤りと drift であって、上流侵害への防御は層 0 に置く

## 層 0: 前提の穴を塞ぐ

- 本リポジトリへ repository ruleset を入れる。main への直 push を止め PR を必須にする。
  実測時点で `rulesets` は空配列、classic の protection は 404 で、両系統とも保護が無い
- semver tag と release note を導入する。**pin の機構は SHA のまま**にする (tag は動かせる)。
  release は bump PR にレビュー可能な単位を与えるための器である
- 消費側の pin を更新する (対応済み)

## 層 1: 増分モード `--check-diff`

入口を 1 つ足す。規則もエンジンも共有したまま、見る範囲だけを差分へ絞る。

| 規則 | `--check` (全走査) | `--check-diff` (増分) |
| --- | --- | --- |
| ディレクトリ名の形式 | 全 Issue ディレクトリ | issue.md が **A または R** の Issue |
| 番号の重複 | 全体 | **全体のまま** |
| 数字記法 | 追跡ファイル全体 | 差分で追加された行だけ |
| フェンスの閉じ忘れ | 全ファイル | **無条件で報告** (行番号で絞らない) |

数字記法の絞り込みは「変更行だけスキャンする」ではなく
「全文をスキャンしてから、違反の行番号が追加行集合に入るものだけ残す」形にする。
数字記法がコードフェンスの中かどうかは全文を見ないと決まらないため。

そのため `_scan_line()` の戻り値を文字列から `(lineno, message)` へ構造化する。
文字列化は `_report()` 側に寄せる。

### 実装が踏む罠 (隔離リポで再現済み)

以下 4 件はすべて「違反を見落としたまま緑になる」経路である。
1 から 3 は起票側が使い捨てリポで対照付きに再現した。

#### 罠 1: 既存の閉じ忘れフェンスが増分を丸ごと免除する

base に閉じていないフェンスがあると、追加行の裸の数字記法は「フェンス内」として
非報告になり、閉じ忘れ違反自体は旧行番号 (フェンス開始行) に付くのでフィルタで落ちる。
結果は完全な緑になる。

再現: base の 2 行目でフェンスを開いたまま閉じずにコミットし、4 行目へ違反行を追加する。
hunk は 4 行目を指すが `scan_text` が返すのは 2 行目の閉じ忘れ違反 1 件だけなので、
追加行集合で絞ると 0 件になる。対照としてフェンスを閉じると、追加行の違反が現れる。

手当て: フェンスの閉じ忘れ違反は行番号フィルタの対象外とし、無条件で報告する。
閉じ忘れが出た増分は検証不能なので rc 1 にする。

#### 罠 2: 非 ASCII パスが diff ヘッダで C クォートされる

`git diff --cached` のヘッダは非 ASCII を含むパスをエスケープした形で出す。
対照として ASCII だけのパスは素で出る。`-z --name-only` と
`core.quotePath=false` はどちらも素のパスを返す。

Issue ディレクトリはタイトル部を含むので非 ASCII を含むものが多数を占める。
これは端ケースではなく主流ケースで、パス一致でファイルを対応付ける実装だと
対象の違反が全部落ちる。

手当て: パス列挙は `-z --name-only` で取り、行番号はファイル単位の
`git diff --cached -U0 -- <path>` から取る。
`ls-tree -z` で同型の失敗を踏んだ記録が `issue-id.py` 自身にある。

#### 罠 3: rename が `--diff-filter=A` から漏れ、git 設定で結果が変わる

既存 Issue のディレクトリを違反名へ rename すると、既定の rename 検出下では
`R` になり `--diff-filter=A` が空になる。`--diff-filter=AR` なら捕捉できる。
`diff.renames=false` にすると同じ操作が `D` と `A` に分かれて `A` でも捕捉される。

**マシンの git 設定で検査結果が変わるのはそれ自体が欠陥である。**
移行期の主要操作が接頭辞付与の rename なので、誤った rename が静かに通る。

手当て: `--diff-filter=AR` にして `R` は新パス側を検査対象に含める。
rename 検出の on/off どちらでも同じ結果になることをテストで pin する。

#### 罠 4: partial staging で index と worktree の行番号がずれる

全文スキャンの対象が worktree のファイルだと、部分 stage で
`diff --cached` の行番号と食い違い、コミットされる違反がフィルタで落ちる。
逆方向 (未 stage の違反が staged 行番号に重なる偽陽性) も同じ根から出る。

手当て: 走査対象を「diff の後側の内容」に統一する。
コミット時は index の内容、`--base` 指定時は HEAD 側。

### その他の仕様

- submodule は hunk 付きで diff に出るが index からの内容取得は失敗する。skip する
- 引数は `--base <ref>` 無しなら staged、指定ありなら `<ref>...HEAD`
- 終了コードの写像は既存と同じ。差分が空のときは 0。
  ただし差分の取得自体に失敗したら 2
- **走査の要約を必ず印字する。**「走査した追加行 N / ファイル M / Issue ディレクトリ K」。
  これが無いと、配線ミス (base が常に HEAD と一致する等) と正常な空コミットが
  区別できない。`--check` が持つ「何を何件見たか」と同じ役割である

## 層 2: 遅延取り付け (SKILL.md)

起票フローの先頭に加入判定を足す。

1. `.pre-commit-config.yaml` に該当 hook があるか見る
2. 無ければユーザーへ確認する。**判断を求めるのは「このリポで採用するか」の 1 bit だけ**
3. 承諾されたら次を行う
   - `scripts/issue-id.py` を canonical から配置する
   - 由来 SHA を 1 行のファイルへ記録する
   - `.pre-commit-config.yaml` へ hook を追加する。
     **書く内容は skill 内の canonical テンプレート 1 つに固定**し、自由記述を禁じる
   - `pre-commit install` を走らせる
   - install 直後に重複検査を 1 回走らせ、結果を見せる
4. 断られたら追跡外へ記録して二度と聞かない

### 確認の設計

「書く内容を全文見せてから聞く」は確認疲れに対して実効がない。
配布先の数だけ、しかも初回と同期のたびに YAML と Python の全文を見せられた人間は
読まなくなり、「見せた」という事実を作るだけになる。

したがって人間の判断は 1 bit に絞り、内容の正しさは機械へ移す。
確認に載せるのは 2 行だけにする。

- 配置した写しと deploy された canonical のハッシュが一致したこと
- 書いた hook block が canonical テンプレートと同一であること

この機械化が守るのはエージェントの誤りと drift であって、上流侵害ではない
(ハッシュも同じ経路で配られる)。上流侵害への防御は層 0 に置く。

### 危険度の順位

3 つの書き込みのうち **`.pre-commit-config.yaml` の編集が最も危険**である。
`repo: local` の `entry:` は任意コマンドで、pin という概念が構造的に存在せず、
以後の全コミットで権限プロンプトを通らず実行される。
写しの配置は配線されるまで不活性で、内容をハッシュ突合できる。
`pre-commit install` は既存 hook を破壊せず、上書きには明示のフラグを要求する。

だから hook block を固定テンプレートにすることが、この層のいちばん効く手当てになる。
テンプレートからの逸脱は層 3 の検査項目に足す。

### 未定: 消費側 hook の具体形

`stages` と `always_run` と commit-msg hook の有無をどう写像するかは未定である。
本リポジトリの `.pre-commit-config.yaml` は commit-msg stage の空集合 skip や
`always_run` の罠を大量に実測して文書化しているが、その知見を消費側テンプレートへ
写像する場所が設計にまだ無い。

`git commit -v` の diff がコミットメッセージ検査へ混入する問題は、
本リポジトリが本文をファイルで渡す規約で回避している。
同じ規約を持たない消費側リポジトリではそのまま発火する。

## 層 3: 横断スイープ (消費側リポジトリが持つ)

対象リストは持たず、実行時にリポジトリを走査する。
配布元と消費側の両方が PUBLIC なので、走査対象の名前をコミットしないため。

報告するのは 7 つ。

| 報告 | 見方 |
| --- | --- |
| 未加入 | Issue を持つが hook が無い。拒否記録があるものは除く |
| 写しの内容が canonical と違う | **内容ハッシュを canonical の blob と突合**する |
| 由来 SHA が上流の履歴に実在しない | オブジェクトの存在確認 |
| 由来 SHA が古い | 上流の commit range と touched paths の要約を添える |
| hook block がテンプレートと違う | 逸脱の検出 |
| template の写しが残っている | 層 4 で不要になるため |
| pin と上流 main の距離 | 配布層自体の鮮度 |

由来 SHA を鮮度の判定だけに使うのは危険である。記録は自己申告なので、
写しを差し替えて記録を温存すればスイープは「最新」と報告する。
**判定の主軸は内容ハッシュの突合に置き、由来 SHA は注釈として扱う。**

古さの報告に commit range を添えるのは、更新判断の材料を報告時点で渡すため。
これが無いと「古い」という警報が、中身を見ないまま更新を促す装置になる。

## 層 4: template の写しをやめる

template の写しを持つ配布先は全て canonical と不一致だった。
skill は起票時に同梱の template を直接読めるので、消費側へ写しを置く要求を消せば
drift のクラスがもう 1 つ消える。

例外が 1 件ある。ある配布先の template は独自改変であって古い版ではなく、
frontmatter へ skill が禁じたキーを 2 つ足している。撤去とは別に扱う。

ISSUE-29 は本リポジトリ内に 2 部ある template の一致を検査する Issue なので、
層 4 で消費側の写しが不要になっても前提は変わらない。対象が別である。

## テスト方針

`--check-diff` は変異注入で pin する。重点は緩めすぎる方向、つまり
増分にしたことで本来止めるべき新規違反が素通りする経路である。

| # | 何を pin するか |
| --- | --- |
| 1 | 新規 Issue ディレクトリの名前違反が検出される |
| 2 | 追加行の数字記法が検出される |
| 3 | `--base` 指定時の range が正しい |
| 4 | 追加行の数字記法がコードフェンスの中なら免除される |
| 5 | 既存行の数字記法が報告されない (ratchet が効いている) |
| 6 | 番号の重複が増分モードでも全体で見られる |
| 7 | base に閉じ忘れフェンスがある状態で、追加行の違反が緑にならない |
| 8 | partial staging で index の内容が走査される |
| 9 | 非 ASCII のディレクトリ名を持つ Issue で違反が検出される |
| 10 | rename が検出され、`diff.renames` の on/off で結果が変わらない |
| 11 | submodule を含む差分で例外にならない |

5 と 6 は逆方向の対照である。5 だけを見ると「何も報告しない」実装でも緑になる。
7 から 11 はレビューが見つけた経路で、7 と 9 と 10 は隔離リポで再現済み。

`--check` の既存テストが緑のままであることも確かめる。
入口を足す変更なので、規則とエンジンの側に変化が無いことが条件になる。

| 順 | 内容 |

| 2 | 消費側の pin 更新 (対応済み) |

## 未解決

- `check-related-refs.py` は本リポジトリ固有の baseline を literal で持つので、
  今回の配布対象に含めない。配布するなら baseline の持ち方から設計し直しが要る
- CI での増分モードは base ref の解決が要る。shallow clone や force-push 後に
  base が解決できない状態の扱いが未定。配布先の多くは CI 自体を持たない
- 消費側 hook の具体形 (層 2 の「未定」節)
- 消費側に全走査の backstop が無い。増分が見落とした違反は記録なしで恒久 baseline 化する
- gitattributes で diff を抑止したテキストファイルは hunk が出ず全行免除になるはず。
  機構上は罠 1 と同根だが未実測
