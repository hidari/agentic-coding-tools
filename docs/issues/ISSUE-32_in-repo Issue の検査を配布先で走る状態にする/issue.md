# feat: in-repo Issue の検査を配布先で走る状態にする

## 背景

`dev-workflow:in-repo-issue` は識別子の記法を検査する `issue-id.py` を持つが、
検査を pre-commit / CI へ取り付けるかは「プロジェクトの判断」として skill の外に置かれている。
配っただけでは検査は走らず、抜けはエラーではなく緑として現れる。

ISSUE-22 はこの構造を「配った時点で全リポジトリに新版が届くので、委ねる先が存在しない」と
記録した。ISSUE-13 は「取り付けの有無そのものを見る層がどこにも無い」と書いている。
この Issue はその担当を引き受ける。

配布先での cutover も射程に含める。ただし ISSUE-22 の「既存は rename しない」判断は覆さない。

## 実測 (2026-08-27)

`~/Develop` を `find -maxdepth 5` で列挙し、外部参照リポを除いた 28 リポを走査した。
Issue の計上は `issue_dirs()` を借りた (この関数は issue.md の有無で絞らないので、
検査が実際に見る母集団はこちら)。

| 指標 | 件数 |
| --- | --- |
| Issue ディレクトリ | 982 |
| うち issue.md を持つ | 980 |
| ディレクトリ名が新記法でない | 938 |
| `docs/issues/` を持つリポ | 14 |
| `scripts/issue-id.py` の写しを持つリポ | 1 |
| `docs/issues/templates/issue.md` を持つリポ | 12。全て canonical と不一致 |
| `.pre-commit-config.yaml` を持つリポ | 3 |

2026-08-25 の棚卸しは 13 リポとしていた。`find -maxdepth 3` で 1 段深い場所にある
リポジトリ (102 件) を漏らしていた。**同じリポジトリはこの調査の中でも 2 度目の脱落で**、
並列 subagent に同種の走査をさせたときも同じ 1 件が落ちた。

template の内訳は、7 リポが ISSUE-24 裁定前の旧版で byte 一致、5 リポが独自改変。
1 リポは frontmatter へ skill が禁じたキーを 2 つ足している。

### 重複検査は両方の入口で全リポ緑

`issue-id.py` の docstring は「重複判定の鍵は入口ごとに違う」と明記しているので、
2 つの入口を別々に測った。

| 入口 | 鍵 | 結果 |
| --- | --- | --- |
| `--next` | 全 ref、接頭辞を除いた同一性 | 14 リポすべて rc 0 |
| `--check` | 現ツリー、パス | 14 リポすべて違反 0 件 (陽性対照付き) |

これが緑でないと、取り付けた瞬間から全コミットが赤くなる。
重複検査は増分モードでも全体を見る規則なので、緩めても逃げられない。

## 前提の訂正

ISSUE-22 は「取り付けると既存ディレクトリ名が全部違反になるので、取り付けと rename は
同時にしか選べない」と書いた。これは検査が全走査しかできないことを前提にしている。
走査範囲を差分へ絞れば同時性の制約は外せる。

成立条件は 2 つある。1 つ目は上の重複検査で確認済み。
2 つ目は「増分の ratchet が暗黙であること」の受容で、これは設計上の選択として引き受ける。
ISSUE-28 が扱う `LINK_BASELINE` は件数が監査できる記録された ratchet だが、
差分で絞る方式は既存違反をどこにも記録しない。

## 設計

canonical は同ディレクトリの spec が持つ。ここには層の名前と担当だけ書く。

| 層 | 内容 | 担当リポ |
| --- | --- | --- |
| 0 | main の保護、release の導入、消費側 pin の鮮度 | 本リポと dotfiles |
| 1 | `issue-id.py` へ増分モード `--check-diff` を足す | 本リポ |
| 2 | skill が未加入を検知して初回のみ確認して配線する | 本リポ |
| 3 | 横断スイープで加入状況と写しの drift を検出する | dotfiles |
| 4 | template の写しを消費側へ置く要求をやめる | 本リポ |

配線は remote pre-commit hook ではなく追跡下の写し (`repo: local`) を採る。
理由は更新のレビュー可能性と、第三者への供給面を増やさないこと。
比較と受容するリスクは spec が持つ。

本リポジトリの `repo: local` hook をまとめて写すとき、**プロジェクト固有の前提やデータを
持つ検査は配布対象から外す**。どの検査がそれに当たるかは名前で列挙せず、各スクリプトの
docstring と SKILL.md 側の宣言から判定する。載せてよい条件も同じ場所が持つ。

現時点で該当を宣言しているものが 2 つある。`check-issue-closure.py` はクローズ経路に
前提を置き (docstring)、`check-related-refs.py` は残リンクの baseline と参照先リポジトリ名を
持つ (in-repo-issue SKILL.md の「Issue 間の参照」節が「この規約の検査は同梱しない」と宣言)。
層 2 に入る時点で宣言を読み直すこと。この 2 つは着手の目印であって除外集合ではない。

## 追記 (2026-10-31): 既存の Issue を抱えた配布先へ後から取り付けた報告

出所は dotfiles の ISSUE-132 (受け箱に届いた skill の改善提案) の「既存の Issue を抱えた配布先へ検査を後から取り付ける」節。どれも別のリポジトリのセッションの申告で、本リポジトリでも dotfiles でも再現していない。層 2 で SKILL.md へ書く配線手順の材料にあたる。

- 報告 (実測): 既に in-repo Issue を運用している配布先へ、pre-commit stage に `--check-diff`、commit-msg stage に `--check-text`、CI に `--check-diff --base origin/main` を取り付けた。既存の違反を残したまま新しく入る違反だけを止められ、staged に違反を仕込んだ対照は rc=1、本物の変更は rc=0、commit-msg も対照で赤・正常で緑だった。取り付けの前の `--check` の全走査では、旧形式のディレクトリ名・他のリポジトリの Issue を裸の数字で書いたメモ・自リポジトリの古い記法・偽陽性の 4 種で 57 件あった
- 報告 (実測): 「初期化」節は新規プロジェクト向けで、既存の Issue を抱えたまま後から取り付ける経路 (`--check-diff` を使い、`--check` はまだ赤い) が節の中に無い。`issue-id.py` の docstring には書いてあるので、読めば辿り着ける。報告者の提案 (ドキュメントのみ): 増分の入口を使うことと、`--check` を backstop にする時期をどう決めるかを初期化の節に足す
- 報告: `--check-diff --base main` はコミット済みの差分しか見ず、作業ツリーを数えない。この罠を SKILL.md に書くかの判断は、dotfiles の ISSUE-121 のタスク「報告された使い方の罠を SKILL.md に書くか決める」が既に持っている。書くと決まったときに載る先が、層 2 で書く配線手順になる
- 報告 (実測): 本リポジトリの `.pre-commit-config.yaml` のコメントにある「commit-msg の hook は `always_run: true` が無いと常に skip される」が再現しなかった。pre-commit 4.7.0 の使い捨てのリポジトリで、本物の git commit で `always_run` の有無を比べたら、どちらでも hook が走ってコミットを止めた。報告者の提案: 版を添えて測り直す

最後の項は、コメントの側の主張が条件付きであることに注意する。コメントは「ファイル名やファイル型で絞る指定があると、渡るファイルが message ファイル 1 本しかないので集合が空になる」ことを理由にしており、絞り込みが無い構成とは比べている条件が違う。報告に絞り込みの有無は書かれていない。SKILL.md の「初期化」節はこの設定ファイルを取り付けの実例として名指しするので、配布先が写すコメントでもある。
