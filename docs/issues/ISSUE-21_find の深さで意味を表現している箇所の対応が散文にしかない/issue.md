# refactor: find の深さで意味を表現している箇所の対応が散文にしかない

## 背景

`dev-workflow:in-repo-issue` の SKILL.md は `find` の探索深さで「どの集合を見るか」を
表現している。深さは実装の詳細ではなく**意味を担っている**が、深さと意味の対応は散文にしか
書かれていない。

### 実測: 3 つの意味対応がある

SKILL.md 内で深さ指定を持つ `find` は 9 箇所ある。root と深さの組み合わせで 3 つの意味に
分かれる (ほかに一覧用が 1 つ)。

| root と深さ | 意味 | 箇所数 |
|---|---|---|
| `docs/issues` + `-mindepth 2 -maxdepth 3` | active と closed の両方 | 2 |
| `docs/issues` + `-mindepth 2 -maxdepth 2` | active のみ (closed を除く) | 4 |
| `docs/issues/closed` + `-mindepth 2 -maxdepth 2` | closed のみ | 2 |
| `docs/issues/closed` + `-mindepth 1 -maxdepth 1 -type d` | closed のディレクトリ一覧 | 1 |

明示されているのは Phase E.1 の解説 1 箇所だけである。そこは `-maxdepth 2` が closed 配下を
含まないことと、`-maxdepth 3` にすると既に closed の親へ close 提案が出ることを実測付きで
書いている。一方 **Phase C.3 の `-maxdepth 3` が「active と closed の両方を見る」意味である
ことは、どこにも書かれていない**。読み手はそれを E.1 の解説から反転して導く必要がある。

### これは正確性のバグではない

現在の 9 箇所はすべて意図どおりの集合を見ている。問題は保守性で、**深さを 1 つ変えると意味が
変わるのに、変わったことを見る検査が無い**。

- 深さを増やす方向の変異は「余計なものまで拾う」形で出る。E.1 の実測はこの形を捕まえた例で、
  捕まえたのは検査ではなく人間である
- 深さを減らす方向の変異は「静かに 0 件」で返る。C.3 なら「Issue が見つからない」、E.1 なら
  「active な子が 1 件も無い」と読める。どちらも妥当に見える答えなので出力からは分からない

後者は ISSUE-18 が扱う未定義変数の空振りと同じ返り方をする。原因は違うが、症状と気づけなさは
同じである。

### 機械検証に落とすと制約と衝突する

対応を機械検証可能にする素直な方法は、深さ指定を `issue-id.py` 側のヘルパ (「active な Issue
を列挙する」「closed を含めて解決する」といった名前を持つ入口) へ切り出し、SKILL.md からは
そのヘルパを呼ぶ形にすることである。そうすれば意味が識別子で表現され、深さは 1 箇所に閉じる。

**ただしこれは ISSUE-14 の plan の Global Constraints と正面から衝突する。**

> **ツールの surface を広げない**: `issue-id.py` の入口は `--next` / `--check` /
> `--check-text` の 3 つだけ。将来別ツールへ切り出す前提なので機能を足さない。

この制約は「将来別ツールへ切り出す前提」を理由にしている。ヘルパを足すと入口が 4 つ以上に
なり、切り出しのときに一緒に動かすものが増える。

**どちらを採るかは着手時に決める。**この Issue は緊張を記録するところまでを持ち、結論を
先取りしない。中間案 (SKILL.md 内に対応表を置くだけで、ツールは触らない) もあり、その場合は
表と実際の `find` が drift しうるという別の二重管理を引き受けることになる。
