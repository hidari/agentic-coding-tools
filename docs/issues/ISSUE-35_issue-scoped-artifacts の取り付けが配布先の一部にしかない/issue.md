# fix: issue-scoped-artifacts の取り付けが配布先の一部にしかない

## 背景

`dev-workflow:issue-scoped-artifacts` は消費側へ 3 つを要求する。
CLAUDE.md へのポインタ 1 行、`.pre-commit-config.yaml` への `language: fail` hook、
`.gitignore` への追記である。ポインタが無いプロジェクトでは
「何もせず既定の置き場に従う」と skill 自身が明示している。

この設計だと、**opt-in する意図があってポインタを書き損ねた場合と、
意図的に opt-out した場合が同じ出力になる。**

## 実測 (2026-08-27)

`~/Develop` を `find -maxdepth 5` で列挙した 28 リポ (外部参照リポを除く) を走査した。

| 指標 | 件数 |
| --- | --- |
| CLAUDE.md にポインタを持つリポ | 11 |
| pre-commit hook を持つリポ | 3 |
| 上流既定パスに成果物が残るリポ | 9 (115 ファイル) |
| うちポインタを持ちながら未移行 | 5 (80 ファイル) |
| 別ディレクトリへ移行済み | 3 (36 ファイル) |

母集団は hook の `files:` 正規表現と同じ規約で切った。
`docs/superpowers/` 配下を全部数えると 151 件になるが、移行先として使われている
サブディレクトリは hook も見ないので違反ではない。

### hook が効いているときの出力が、効いていないときと同じ

`language: fail` の hook は該当ファイルが staged のときだけ発火するので、
健全時の出力は永久に「対象ファイル無しで skip」になる。
「正しく効いている」「entry が typo」「ブロックごと消えた」が同一出力になる。

この観察は消費側の 1 リポが自前のテストの docstring に書いており、
そのリポだけが hook の存在と `files:` の挙動を pin している。
つまり検査は存在するが、skill の採用手順を検査しているのではなく
1 消費側の設定を検査しているだけで、他の 10 リポには何も無い。

### 写しが既に drift している

hook の YAML ブロックは SKILL.md に literal で書かれており、消費側へ写される。
hook を持つ消費側 1 リポの `entry:` は canonical と表記が食い違っている。
写しと canonical を突き合わせる経路は無い。

### 走査から同じリポが 2 度落ちた

この実測を並列 subagent にも行わせたところ 73 ファイル / 4 リポと報告された。
差の 1 リポは 1 段深い場所にあるリポジトリで、
同じリポジトリが別のセッションの `find -maxdepth 3` からも落ちている。
**走査の深さで母集団が変わることが、繰り返し同じ形で起きている。**
