# docs: 手順書のコードブロックに未定義変数の silent 空振りが残る

## 背景

`dev-workflow:in-repo-issue` の SKILL.md は Phase ごとにコードブロックを持ち、前の Phase が
定義した変数を後ろの Phase が使う。ブロック単位でコピペすると変数が未定義のまま実行され、
`find` は **rc 0 / 0 行 / stderr 無し**で返る。

この形は「その識別子の Issue が無い」と読める。エラーでも空でもなく、**妥当に見える否定の
答え**として返るので、出力を見ても間違いだと気づけない。

同じ形は検索手順の 3 本目にもあり、そちらは ISSUE-14 のレビュー (M-1) でプレースホルダ代入の
1 行を足して塞いである。Phase 側は塞がれていない。

### 実測

`sh` と `zsh -f` の両方で、SKILL.md のコードブロックを逐語で実行した。結果は両シェルで同一。

| 出所 | 未定義の変数 | rc | 出力行数 | stderr |
|---|---|---|---|---|
| Phase C.3 の `ISSUE_PATH` | `ID` | 0 | 0 | 0 バイト |
| Phase D.3 の 2 本目 (`find ... -exec grep`) | `ID` | 0 | 0 | 0 バイト |
| Phase E.1 の `CLOSED_PATH` | `ID` | 0 | 0 | 0 バイト |
| Phase E.1 の `PARENT_PATH` | `PARENT` | 0 | 0 | 0 バイト |
| 対照: 実在する識別子を入れた同じ `find` | — | 0 | 1 | 0 バイト |

対照が 1 行返るので、走査器が生きていることは確認済みである。0 行は「見ていない」ではなく
「マッチしなかった」で、その原因が未定義変数だと出力からは分からない。

### 壊れ方は 1 種類ではない

同じ Phase D.3 の**1 本目**は逆方向に壊れる。

```
grep -rn "${ID}_" --include='*.md' docs/
```

`ID` が未定義だと検索語が `_` だけになり、実測で **182 行**返る。こちらは silent ではないが、
「補正が必要な参照が 182 件ある」という誤った出発点を与える。

**未定義変数の害は「静かに 0 件」に限らない**。同じ節に「静かに広すぎる」形が同居している。
塞ぐときは両方を対象にしないと、片方だけ直して「塞いだ」と見えてしまう。

### 正規フローでは再現しない

Phase を順に辿れば手前のブロックが変数を定義するので、この経路には入らない。顕在化するのは
**ブロック単位のコピペ**という逸脱のときだけである。手順書がコピペされる前提で書かれている
以上、逸脱は起こる想定に含めるべきだが、緊急度は低い。

機械で塞ぐには「Markdown のコードブロック内で未定義のまま参照される変数を検出する」という、
既存のどの検査とも別クラスの検査が要る。それを作るかどうかも判断に含まれる。

## タスク

      fail-fast ガードを置く / 検査を作る / 受容して明記する)
- [ ] Phase D.3 の 1 本目 (過剰マッチ側) も同じ手当てに含める
- [ ] 検査を作る場合は対照を並べる。未定義で赤、定義済みで緑、**Phase をまたいで定義される
      正規フローを誤検出しない**の 3 つを見る
- [ ] 塞いだ後に `sh` と `zsh -f` の両方でブロックを逐語実行して確かめる
