# fix: Phase E の親伝播が frontmatter の乖離で静かに発火しない

## 背景

SKILL.md の Phase E は、子 Issue が全部 closed になったら親 Issue の close を提案する。
親子の対応は frontmatter の `parent` / `children` で持つ。

配布先のプロジェクトが独自の frontmatter スキーマを持っている場合、Phase E の抽出は
0 件を返す。0 件は「親が無い」と読めるので、Phase E は no-op として正常終了する。
**親子構造が実在するのに伝播が一度も起きない状態が、エラーを出さずに続く。**

これは skill の規約に反しているのはプロジェクト側だが、乖離を検出する層がどこにも無いのは
skill 側の欠陥である。検査 (`issue-id.py`) が見るのはディレクトリ名と本文の記法だけで、
frontmatter は見ていない。

## 実測 (2026-08-27)

配布先のリポジトリで観測したエージェントからの報告。

| 指標 | 値 |
| --- | --- |
| SKILL.md が規定する frontmatter | 必須 1 キー + 任意 2 キー |
| そのプロジェクトの template | 12 キー |
| 親子のキー名 | 規約と別の名前 |
| Phase E の抽出が引いた件数 | 0 |
| 実記法での親参照 (非 null) | 18 |

18 件の親子関係が実在するのに、Phase E は 0 件として no-op になっていた。

## 裁定が要る点

拡張スキーマを認めるかどうかで、配布先の作業が変わる。

1. **skill が canonical のまま**: プロジェクト側が SKILL.md のキー名へ寄せる。
   キーが増えること自体を認めるかは別途決める
2. **拡張を認める**: skill が未知のキーを無視すると明記し、親子のキー名だけを規約にする
3. **キー名を設定可能にする**: 配布物が設定を持つことになるので、`check-related-refs.py` が
   プロジェクト固有の baseline を持つのと同じ問題 (ISSUE-32 の spec が配布対象から外した理由) に
   ぶつかる

現時点の SKILL.md の記述は 1 に読める。ただし「未知のキーがあったらどうするか」は書いていない。

## 検出をどう入れるか

裁定がどうなっても、乖離が静かに続く状態は塞ぐ。案は 2 つ。

- Phase E が 0 件を引いたとき、frontmatter に親子らしきキーが存在するかを見て、
  あれば「規約と違うキー名がある」と報告する。0 件を「親が無い」と即断しない
- 検査側 (`issue-id.py` か別スクリプト) が frontmatter のキー集合を見る。ただし配布物が
  YAML パーサを持たない制約がある (stdlib に無い)
