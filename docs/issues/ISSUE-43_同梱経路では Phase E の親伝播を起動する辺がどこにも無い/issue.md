# fix: 同梱経路では Phase E の親伝播を起動する辺がどこにも無い

## 背景

`dev-workflow:in-repo-issue` の Phase E (子が全部 closed になったら親の close を提案する) を
起動するのは Phase D.5 である。D.5 は Phase D の最後の手順なので、Phase C が「未チェック 0」と
判定して Phase D へ進んだときにだけ通る。

クローズを feature PR へ同梱する経路には、この辺が無い。

- 同梱節が feature ブランチで行えと書いているのは D.1〜D.4 で、D.5 は範囲の外にある
- マージ後に Phase C が走っても、対象は既に `closed/` 配下にあるので C.3 の「既に closed」
  分岐で no-op になる。Phase D へ進まないので D.5 にも到達しない

同梱節自身は「親 Issue の Phase E 伝播 close も、親を閉じる PR に同梱するか、直 push が
許されない環境では別 PR で行う」と書いている。これは伝播をどこで実行するかを決めているだけで、
伝播が要ることを誰が検出するかは決めていない。検出は D.5 が持つ。

`scripts/check-issue-closure.py` が入ったことで、このリポジトリではクローズの同梱が既定に
なった。つまり Phase E は既定の経路から起動しなくなる。

## 発火しないことに気づけない理由

親子 Issue が現在 0 件なので、起動しなくても症状が出ない。

新検査も代替にならない。不変条件 A は active な Issue の箱が全て `[x]` であることを見るが、
A.5 が定める親の `## タスク` は子 Issue へのリンクを並べた箱で、Phase E は「親のチェック状態は
判定に使わない」と明記している。子が closed になっても親の箱は未チェックのまま残るので、
不変条件 A は発火しない。

## 実測 (2026-08-29)

| 観測 | 結果 |
| --- | --- |
| frontmatter に `parent` / `children` を持つ Issue | 0 件 |
| 同梱節が feature ブランチへ含めろと書く範囲 | D.1〜D.4 |
| gate SKILL.md の Phase 2 / Phase 3 が同梱時に適用しろと書く範囲 | 同梱節へ委譲。範囲を持たない |

gate は範囲を持たず同梱節へ委譲するので、射程の canonical は同梱節 1 箇所だけにある。
そこが D.1〜D.4 に限っている以上、canonical をそのまま辿ると D.5 が落ちる。手当ては
同梱節の側へ入れれば足り、gate は自動で追随する。

## ISSUE-38 との違い

症状 (Phase E の親伝播が静かに発火しない) は同じだが、機序が違う。

| | 起動 | 抽出 |
| --- | --- | --- |
| ISSUE-38 | 起動する | frontmatter のキー名が規約と違うので 0 件を返す |
| 本 Issue | そもそも起動しない | 起動しないので抽出まで行かない |

ISSUE-38 の手当て (0 件を「親が無い」と即断せず規約外のキー名を報告する) は、Phase E が
走ることを前提にしている。走らない経路はそちらでは塞がらない。
