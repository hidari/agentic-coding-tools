# ISSUE-41 spec: クローズ同梱の判定を促す入口を足し、閉じ忘れを状態検査で止める

## この spec が決めること

ISSUE-41 の本文は欠陥を記述するところまでで、手当ての形は「置き場の候補 2 つ」までしか
決めていない。この spec は形を確定させる。

初版は敵対的レビュー (4 観点 43 指摘) で 7 件が生き残り、16 件が未検証のまま残った。
未検証分は起票者が自分で実測して潰した。本版はその結果を反映した第 2 版で、初版から
設計が変わった点は「決めたこと」の表に印を付けてある。

## 決めたこと

## この検査は同梱を強制する

初版は「同梱を促す」と書いていたが、実測すると強制になる。

過去の main コミットへ不変条件を当てた結果:

| コミット | 内容 | 違反 |
| --- | --- | --- |
| `c33ab70` | ISSUE-11 の実装 PR をマージした直後 | active 30 件中 1 件 (ISSUE-11) |
| `d1de3ea` | ISSUE-27 の実装 PR をマージした直後 | active 24 件中 1 件 (ISSUE-27) |

どちらも「実装 PR をマージ → 次の PR で close」という経路で生じた状態である。hook は
`always_run: true` なので、この状態が残っている間はその Issue に触らないコミットまで
全部止まる。

つまりこの検査は post-merge クローズ経路と両立しない。in-repo-issue は
「プロジェクトが main 直 push を許すなら従来どおり post-merge 直 push でよい」と
その経路を既定として宣言しているので、衝突を明示的に処理する必要がある。

### 処理の仕方

**このリポジトリでは post-merge 経路をそもそも選べない。** main は ruleset で保護されており
PR が必須なので、直 push を前提とする経路は使えない。したがってこのリポジトリに限れば
強制は正しい。

ただし帰結を隠さずに書く。この検査を入れると、このリポジトリでは以下が到達不能になる。

- in-repo-issue Phase B で最後の箱を `[x]` にして、クローズを後続コミットへ回す形
- C.3 の `unchecked == 0` → Phase D 分岐 (同梱済みなら C.3 は「既に closed」で no-op になる)

これは検査が作る制約ではなく、同梱を既定にすることの帰結である。検査はそれを機械で
固定するだけで、in-repo-issue の散文を書き換えるものではない。**配布先では post-merge が
既定として生きているので、この検査をそのまま配ってはいけない。**「配布は ISSUE-32 層 2 へ」
という射程外宣言には、この理由が加わる。

## 採らなかった案と理由

### PR 本文の `Closes <ID>` を見る検査

`pull_request` の既定 activity type は `opened` / `synchronize` / `reopened` で `edited` を
含まない。したがって**本文なしで PR を作って通し、あとから `Closes` を書き足す**順序は
検査を素通りする。必須チェックは緑のままなので誰も気づかない。

`types:` へ `edited` を足せば塞げるが、本文を編集するたび 4 job が再実行される。加えて
push トリガの run では `github.event.pull_request` が空になるのでガードが要り、新 job に
すると ruleset の必須チェック名への登録も要る。

### `issue-id.py` の入口として足す

配布チャネルを既に持っているので最も安いが、同スクリプトは
「規則は 1 つ、エンジンは 1 つ」を設計として宣言している。検査の 3 入口 (`--check` /
`--check-diff` / `--check-text`) は数字記法という 1 つの規則と `scan_text()` という 1 つの
エンジンを共有する (`--next` は採番なのでエンジンを通らない)。クローズ漏れは記法ではなく
ライフサイクルの状態なので、足すと規則もエンジンも 2 つ目が入る。

配布が安いのは中身が単一規則だからで、規則を増やした時点でその安さの前提が消える。

## 設計

### 1. 検査 — `scripts/check-issue-closure.py` (新規)

2 つの不変条件を見る。片方だけでは、もう片方が抜け道になる。

**不変条件 A (完了漏れ)**: active な Issue で `## タスク` 節を持ち、チェックボックスが
1 個以上あり、未チェックが 0 件のものは違反。

**不変条件 B (配置と status の不整合)**: `closed/` 配下の Issue は `status: closed`、
active な Issue は `status: closed` 以外であること。

B が要るのは、A だけだと `git mv` 1 回で緑に戻せてしまうため。Phase D の 3 手のうち
D.2 だけを実行し D.1 (frontmatter の書き換え) を落とすと、`closed/` に居るのに
`status: open` という状態が残る。**このリポジトリの検査は現在 1 本も frontmatter の
`status` を読まないので、この状態はどこからも見えない** (`scripts/` と `plugins/` を
`status:` で走査して確認。ヒットするのはテストの fixture 文字列だけ)。

A を verify する検査を入れると、赤を緑に戻す最短手が `git mv` になる。B が無いと、検査が
「verify する 1 手だけを踏ませ、verify しない 1 手を落とさせる」形になる。

#### 母集団

`issue-id.py` から `issue_dirs` を **importlib で借りる**。自前で glob と除外を書かない。

`check-related-refs.py` が既にこの形を採っており、借用名を `BORROWED` に列挙して起動時に
実在を検査する。rename されたときに素通りではなく検査不能で落ちる。`issue_dirs` は
`templates/` と `closed/` の除外規則を持つので、自前実装するとその規則の 4 つ目の写しになる。

`issue_dirs` は active と `closed/` の両方を返すので、不変条件 A は `closed/` 配下を除いた
側に、不変条件 B は両側に当てる。

各ディレクトリの `issue.md` は、**ディレクトリ内の追跡ファイルから名前を小文字化して
`issue.md` に一致するもの**を採る。git の pathspec はファイル名を大小区別して照合するが、
macOS の既定は `core.ignorecase=true` で追跡名は作成時の綴りが記録される。`Issue.md` で
作られた Issue は開発機では普通に開けるのに pathspec からは落ちる (fixture で実測)。

見つからないディレクトリは違反にせず「走査できなかった Issue」として件数に出す。
沈黙させると母集団が縮んだことが出力から見えない。

#### 終了コード

| 状況 | rc |
| --- | --- |
| 合格 | 0 |
| 違反あり | 1 |
| 検査不能 (`docs/issues/` が無い / 借用名が消えている) | 2 |
| **active な Issue が 0 件** | **0** |

active が 0 件になるのは「open な Issue が 1 件も無い」という正常な状態なので、
2 (検査不能) にしない。初版は `issue-id.py --check` と `check-related-refs.py` の
「走査対象 0 件は 2」を転写していたが、あの 2 本が数えているのは常に非空になる上位集合
(追跡ファイル全体 / `docs/issues/*.md` 全体) で、意味が違う。

代わりに走査した Issue の総数 (active + closed) が 0 のときを 2 にする。この集合が空なら
Issue 管理そのものが無いか、借用が壊れている。

#### そのほか

| 要素 | 決定 | 根拠 |
| --- | --- | --- |
| 引数 | argparse + `allow_abbrev=False` | 既存 3 本の作法。短縮形が別モードへ静かに落ちるのを防ぐ |
| 出力 | 違反は stderr、「何を何件見たか」の要約は stdout | `issue-id.py` / `check-related-refs.py` と同じ |
| 依存 | 標準ライブラリのみ | リポジトリの MUST |

終了コード 2 を 1 と分ける理由の canonical は `check-leak-guard-rules.py` の docstring。
この規約を持つのは `check-leak-guard-rules.py` / `check-related-refs.py` /
`run-python-tests.py` / `issue-id.py` の 4 本 (`check-package-shape.py` と `gen-readme.py`
は 0 と 1 しか返さない)。

#### 書式の揺れを吸収する

行頭アンカーの素朴な正規表現 3 本では、完了済み Issue が 9 通りの書き方で素通りする
(fixture で実測。対照の素直な全 `[x]` だけが捕捉された)。

| 揺れ | 扱い |
| --- | --- |
| `- [X]` (大文字) | チェック済みとして数える |
| リストマーカー `*` / `+` | `-` と同じに扱う |
| インデントされたリスト | 数える |
| 全角スペースの箱 `[　]` | 未チェックとして数える |
| `### タスク` / `##タスク` (空白なし) | タスク節として認める |
| コードフェンス内の箱 | 数えない |
| HTML コメント内の箱 | 数えない |

フェンスの追跡は `check-related-refs.py` が `FENCE_LINE` で既に実装しているので、
そちらの扱いに揃える。この種の穴が既知であることの証拠でもある。

### 2. 取り付け

| 経路 | 形 |
| --- | --- |
| pre-commit | `repo: local` hook。`pass_filenames: false` / `always_run: true` |
| CI | 既存の `package-shape` job へ step 追加。**`- name:` を明示する** |

CI で新 job を作らないのは、ruleset の必須チェック名が ci.yml の 4 job 名と完全一致で
登録されているため。新 job を足すと ruleset 側の登録が要り、登録を忘れると必須でない
チェックとして緑を待たずにマージできる。

`- name:` の明示は ci.yml が相乗りの条件として書いている作法で、既存の相乗り 2 件
(`issue-id.py --check` と `check-related-refs.py`) はいずれも `- name:` を持つ。

`scripts/test_check_issue_closure.py` を追加し、`scripts/python-tests-manifest.txt` を
`--update-manifest` で再生成して diff ごとコミットする。

ISSUE-13 が「現状の 4 本」として記録している `scripts/` 直下の検査は、この変更で 6 本になる
(`check-related-refs.py` の追加で既に 5 本になっており、ISSUE-13 の数字は古い)。

### 3. 二重管理の処理

`未チェックが 0 件なら close` という閾値は in-repo-issue の C.3 が bash スニペットで持つ。

初版は「SKILL.md の literal とスクリプトの正規表現が一致することを pin する」と決めていたが、
**この pin は既に起きている乖離を捕まえない**。C.3 は `has_task_section` と `unchecked` の
2 つしか数えず箱の総数を数えないので、`## タスク` 節があって箱が 0 個の Issue を
`unchecked == 0` として Phase D (close) へ送る。新検査は同じケースを明示的に免除する。
両者は literal (`^## タスク` / `^- \[ \]`) を共有したまま分岐構造で判定が割れるので、
literal 照合の pin は緑のまま食い違う (fixture で実測: 箱 0 個の Issue に対し C.3 は
「close する」、新検査は「合格」)。

したがって pin の形を変える。

1. C.3 のスニペットへ「箱が 1 個以上あること」の条件を足し、判定を新検査と揃える
2. 一致は literal ではなく**挙動**で pin する。同じ fixture 集合に対して C.3 の判定と
   新検査の判定が一致することをテストで確かめる

`scripts/test_check_related_refs.py` が「上流が状態機械だけを変えると drift する」として
既に挙動の一致を pin しており、この形には前例がある。

### 4. 散文の入口 — `pre-merge-quality-gate/SKILL.md`

Phase 4 には置かない。同梱は issue.md の編集 + `git mv` + 相対リンクの補正というファイル
変更を伴うので、Phase 4 に置くと Phase 3 の再検証を通らない変更が PR へ入る。また Phase 4 は
「ここで初めて」という 1 文で執行専用フェーズとして規定されている。

Phase 0 単独にも置かない。Phase 0 の本文は「並列レビューに渡す情報を取得する」と目的を
限定しており、同梱要否の判定結果は Phase 1 の 4 レーンのどれも消費しない。

| Phase | 追加する内容 |
| --- | --- |
| 0 | 保護の有無を確かめる。**手順は書かず in-repo-issue の同梱節を指すポインタに留める** |
| 2 | 判断軸に「クローズ同梱の要否」を追加 |
| 3 | 同梱するなら D.1〜D.4 を feature ブランチのコミットへ含め、再検証に含める |
| 関連節 | in-repo-issue を追加 |

Phase 0 をポインタに留めるのは、判定手順を gate 側にも書くと同梱節との二重管理になるため。
gate Phase 5 が起動可否の判定を C.1 に持たせているのと同じ形で、この継ぎ目が既に採っている
作法に揃う。

Phase 3 で適用する範囲は D.1〜**D.4**。初版は D.1〜D.3 としていたが、D.4 (新パスの明示
stage) を落とすと `git mv` が stage した HEAD の内容 (`status: open`) のまま `closed/` へ
入る。同梱節が「D.1〜D.3 と同じ操作」と書いているのはコミット文言の話を除く意味なので、
stage の規約は落とさない。コミット文言の `(PR #<M>)` は Phase 3 時点で PR 番号が未確定なので、
同梱時は文言を feature PR のコミットメッセージに委ね、D 形式は post-merge 経路のものとする。

gate の `## 関連` 節へ in-repo-issue を追加する。同節は 6 件挙げるが in-repo-issue は不在で、
gate 全体でも Phase 5 の 1 行しか名指ししていない。

編集の衝突に注意する。gate SKILL.md は ISSUE-17 と ISSUE-33 も編集し、in-repo-issue SKILL.md は
ISSUE-17 / 19 / 32 も編集する。本 Issue を先に入れる。

### 5. ポインタ先の補強 — `in-repo-issue/SKILL.md`

#### 5.1 同梱節へ保護の判定手順を足す

**これが無いとポインタが情報を持たない参照になる**。同梱節は「main への直 push を禁じる
プロジェクト」という条件を散文で述べるだけで、それを判定する手順を持たない。

判定は classic branch protection API の 404 だけで結論しない。ruleset は別系統で classic API に
出ないため `rulesets` も見る。判定式は「branch を target とする active な ruleset が
`pull_request` rule を持つか」。

実測値は ISSUE-41 の issue.md が持つので、ここでは再掲しない。

#### 5.2 Phase F (reopen) へ残作業の追記を規定する

closed の Issue は定義上すべての箱が `[x]` (このリポジトリで 11 件中 11 件)。F.1〜F.3 は
frontmatter の書き換えと `git mv` とリンク補正だけで、箱を戻す手順を持たない。したがって
**reopen 直後は必ず「active かつ全 `[x]`」になり、不変条件 A に触れる**。

手当ては箱を uncheck することではない。それは reopen 前の作業記録を壊す。代わりに
**reopen の理由を未チェック項目として `## タスク` へ追記する**ことを F の手順に足す。
既存の `[x]` は 1 行も変えずに済み、F.3 の「1 コミット」の形も崩れない (fixture で実測)。

これは検査のための回避策ではない。reopen とは「まだ終わっていない作業がある」という判断
なので、その作業が未チェック項目として書かれるのが本来の形である。現行の Phase F は
それを書かせないまま `closed → in_progress` へ戻すので、**新検査の有無に関係なく C.3 は
reopen 直後の Issue を「完了」と判定する** (C.3 のスニペットを逐語実行して確認)。
Phase F 側の記述不足を埋める変更にあたる。

#### 5.3 squash subject が PR 番号を 2 つ持つ件

同梱が既定になれば分割は例外なので、規約としては許容し「分割したときは実装 PR と
マージされる PR の両方を書く」と「PR / コミット規約」節へ明記する。避ける方法は無い。
D 形式は「どの PR がこの Issue を閉じたか」を、squash 規約は「どの PR がこのコミットを
作ったか」を残そうとしており、分割するとこの 2 つは別の番号になる。

## 射程外

| 事項 | 引き渡し先 |
| --- | --- |
| 検査を配布先で走らせる | ISSUE-32 層 2 |
| 同梱経路で Phase E (親伝播) の自動検出が働かない | 新規 Issue へ切り出す |

配布については、`scripts/` 直下が apm のパッケージ単位 (`plugins/<name>` または
`skills/<category>/<name>`) の外にあるため、現状の配布設計には運搬手段が無い。層 2 が
その手段を作る担当なので、そこで扱う。加えて前述のとおり、この検査は post-merge 経路と
両立しないので、配布するなら経路の選択と組で設計する必要がある。

Phase E については、初版に書いた「新検査が親の全 `[x]` を捕まえるので部分的な代替になる」を
**撤回する**。A.5 が「Phase E の close 判定はディレクトリ位置のみで、親 `## タスク` の
チェック状態は判定に使わない」と明記しており、親の箱を判定に使う主張はこれと衝突する。

## テスト計画

`scripts/test_check_issue_closure.py` に置く。既存の検査スクリプトのテストと同じ作法に従う。

- ハイフン名のスクリプトは `importlib.util.spec_from_file_location` で読む
- git を歩く経路は `tempfile` + `git init` の fixture リポジトリで検証し、
  `GIT_CONFIG_GLOBAL` / `GIT_CONFIG_SYSTEM` を `os.devnull` へ潰した環境を渡す
- 終了コードの写像は `subprocess` で起動する専用クラスで pin する。関数を直接呼ぶテスト
  だけだと「違反ありで `return 0`」の 1 行の変異が全緑のまま生き残る
- 取り付けは `Attachment` クラスで pin する

仕様として pin する項目:

| 項目 | 期待 |
| --- | --- |
| 未チェックが残る Issue | 合格 |
| 全て `[x]` の active な Issue | 違反 (A) |
| `closed/` 配下で全て `[x]` かつ `status: closed` | 合格 |
| `closed/` 配下だが `status: open` | 違反 (B) |
| active だが `status: closed` | 違反 (B) |
| `templates/` 配下 | 対象外 |
| `## タスク` 節が無い | 合格 |
| `## タスク` はあるが箱 0 個 | 合格 |
| 大文字 `[X]` / `*` `+` マーカー / インデント / 全角スペース | 正しく数える |
| コードフェンス内 / HTML コメント内の箱 | 数えない |
| `Issue.md` (大文字始まり) | 母集団に入る |
| `issue.md` を持たない Issue ディレクトリ | 「走査できなかった」として件数に出る |
| active が 0 件 | rc 0 |
| Issue が 1 件も無い | rc 2 |
| 借用名が消えている | rc 2 |
| C.3 との挙動一致 | 同じ fixture 集合で判定が一致 |

`templates/` の除外は実ツリーに対しては常に成立するので dead pin になりやすい。fixture 側で
`templates/` に全 `[x]` の Issue を置き、それが違反にならないことを見る形にする。
実ツリーの pathspec が `templates/` と `closed/` を返すことは確認済み (12 件) なので、
除外は生きている。

### 変異注入

検査機構を足すので 3 種を当てる。1 種だけで完了としない。

1. **検査対象を壊す**: active な Issue の箱を全て `[x]` にする / `closed/` の Issue の
   status を `open` に戻す → それぞれ A と B が報告すること
2. **検査機構を壊す**: 違反ありで `return 0`、`closed/` の除外を外す、`templates/` の除外を
   外す、箱 0 個ガードを外す、フェンス追跡を外す、大小の吸収を外す
3. **取り付けを外す**: `.pre-commit-config.yaml` と `ci.yml` から呼び出しを消す →
   `Attachment` が赤くなること

加えて範囲を数える。母集団が active な Issue 全件を覆っていることを、件数ではなく
Issue ディレクトリ名の集合で確かめる。

## 導入時の状態 (実測)

導入した瞬間に赤くならないことを確認済み。赤い土台の上に検査を載せると、その日から
緑を無視する運用が始まる。

| 指標 | 件数 |
| --- | --- |
| active な Issue | 31 |
| 不変条件 A の違反 | 0 |
| `## タスク` 節が無いもの | 0 |
| `## タスク` はあるが箱 0 個のもの | 0 |
| 揺れた書式で書かれた完了済み Issue | 0 |
| 対照: `closed/` で全て `[x]` | 11 件中 11 |

対照が非空なので、この 0 件は走査が機能した上での 0 件である。ただし**この対照は新検査が
出した数字ではない**ので、実装後に新検査自身で測り直すこと。不変条件 B の現状は未測定で、
実装時に測る。

これは HEAD 1 点の測定である。過去のコミットでは違反が出る (上の「同梱を強制する」節)。
導入は「今後のコミットに対して」効き、過去の履歴を遡って直すものではない。
