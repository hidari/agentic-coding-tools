# fix: 2 部ある Issue テンプレートの一致を検査する

## 背景

Issue のテンプレートは 2 箇所にある。

| パス | 役割 |
|---|---|
| `plugins/dev-workflow/skills/in-repo-issue/templates/issue.md` | skill が配る originals |
| `docs/issues/templates/issue.md` | このリポジトリへ配置した copy |

後者は skill の「初期化」節が `cp` で置くもので、両者は byte 単位で同一である (実測)。
一致を検査する機構は無い (`scripts/` と pre-commit と CI を走査して確認)。

ISSUE-24 の作業がこのコストを実演した。`## 関連` 節のプレースホルダを直す変更で、同じ 1 行を
2 ファイルへ 2 回入れている。片方だけを直しても誰も止めない。

## 何が問題か

配布物と配置物のずれは、新規に起票された Issue の形として現れる。テンプレートは全 Issue の
コピー元なので、ずれた側から起票された Issue だけが別の構造を持つことになる。しかも
ずれた側が古い方だと、新しい規約を知らない Issue が静かに増える。

ISSUE-24 が取り付けた検査は `issue.md` に `## 関連` 節を要求するが、テンプレートの中身が
規約どおりかは見ていない。節の有無しか見ないので、プレースホルダの文面がずれても緑になる。

非対称がもう 1 つある。`docs/issues/templates/issue.md` は関連節の検査の走査対象 31 件に
含まれるが、skill 側のテンプレートは `docs/issues/` の外なので対象外である。

## 決めること

検査の形をどれにするか。

- 2 ファイルの byte 一致を検査する。単純だが、配置側に固有の追記を将来許せなくなる
- 配置側を生成物にする。`gen-readme.py` と同じ `--check` の形にできるが、生成スクリプトが
  1 本増える
- 配置側を追跡から外し、初期化のたびに `cp` させる。追跡下から消えると、このリポジトリの
  Issue を起票する経路が skill の取得に依存する

どれを採っても、skill が配布された先のリポジトリには届かない (コピー配布に再同期の機構が
無い。同じ性質は ISSUE-22 が追跡している)。射程はこのリポジトリに限る。
