# feat: jev-lint の採用方式を決めて取り込む

## 背景

mizchi/jev-lint は、コメントや識別子の名前が直下のコードと食い違っている箇所を LLM で採点する
lint である。このリポジトリは「コメントは WHY を書く」「WHAT は識別子で示す」を規約に持つが、
どちらも機械検査に落ちておらず、レビューだけが防衛層になっている。この層を自動化できるかを
確かめるために試用した。

試用の実測は次のとおり (2026-09-21 から 09-22 にかけて、npm の 0.5.0 で測った)。

- 費用と速度: `scripts/` 全体で61リクエスト、約216万トークン、0.079ドル、10秒。リポジトリ全体の
  dry-run では367リクエスト、約905万トークン、0.38ドル
- 検出の質: `scripts/` に対する findings 6件のうち、有用が3件 (いずれも識別子の名前が中身と
  合っていないという指摘)、誤検出が3件
- 日本語コメントの扱い: 嘘のコメントを仕込んだ写しで陽性対照を取ったところ、日本語でも英語と
  同等に拾った (嘘は0.84から0.96、正しい主張は0.06から0.15。どれも3回の試行でばらつきはほぼ無い)。
  ただし拾えるのは露骨な矛盾に限る。射程はコメントとその直下のコードで、ファイルをまたぐ散文の
  真偽は見ない
- 依存は2つだけ (`@ast-grep/cli` と `yaml`)

そのまま採用できない理由が4つある。

- 上流の SKILL.md と command 4本が `npx -y jev-lint` で書かれており、版が固定されていない。加えて
  `npx` はこの開発環境では許可されていない
- pnpm 12 では `@ast-grep/cli` の postinstall が `ERR_PNPM_IGNORED_BUILDS` を起こすので
  `--allow-build=@ast-grep/cli` が要る。postinstall の中身はプラットフォーム別パッケージの
  実行ファイルを置くだけで、読んで無害を確認してある
- 上流の `commands/prose.md` は `node_modules/jev-lint/rules/markdown` が存在する前提で書かれて
  いるため、dlx 経由の呼び出しでは成立しない
- API キーは環境変数から読まれて外部の採点 API へ Bearer で送られる。送り先は環境変数と設定
  ファイルの両方で差し替えられる。エージェントがキーを読んで第三者へ渡す形は classifier が
  止めるので、実行はユーザーが行う必要がある

提案済みの方向は「版の固定と `pnpm dlx` の呼び出しとキーの扱いだけを持つ薄いラッパを自前で持ち、
ルールの書き方は上流の skill を参照する」。まだ裁定を受けていない。
