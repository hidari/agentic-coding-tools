# fix: Phase D.3 の検出の宣言が検査器の記法対応を前提にしている

## 背景

SKILL.md の Phase D.3 は Issue を `closed/` へ移したときに壊れる相対リンクの補正を扱う。3 つ目の
方向 (移動対象から移動先の兄弟へ) を説明する行が、検出できるかどうかをこう宣言している。

> 相対リンク検査を持つプロジェクトはコミット時に検出するが、持たないプロジェクトでは沈黙した
> まま壊れる

同じ節のもう 1 箇所、D.3 の grep が山括弧を任意にする理由を説明する行が「パスに半角空白や日本語を
含むと Markdown リンクが山括弧形式で書かれる」と書いている。この 2 行が本 Issue の対象である。

## 実測 (2026-09-10)

**件数はすべてこの Issue を追加したツリーで測った。** 起票前の値を残すと、この作業が作るツリーでは
一度も真にならない。

### 素朴な抽出規則へ 6 記法を通した

`docs/a/target.md` と半角空白を含む `docs/a b/target.md` と `docs/日本語/target.md` を実在させ、
`docs/src/` 配下から 6 記法で参照する fixture を作った。検査器側の抽出規則は `\]\(([^)\s]+)\)`
とし、リンク先の解決規則を 3 通りに振った。

参照先はすべて実在するので、missing は偽陽性、checked=0 は「リンク切れが無い」ではなく「1 本も
見ていない」を意味する。1 行目が陽性対照である。

| リンク記法 | 囲みを外さない / decode しない | 囲みを外さない / decode する | 囲みを外す / decode する |
|---|---|---|---|
| 素・空白なし (陽性対照) | 緑 | 緑 | 緑 |
| 素・空白あり | checked=0 | checked=0 | checked=0 |
| 山括弧・空白なし | 偽陽性 | 偽陽性 | 緑 |
| 山括弧・空白あり | checked=0 | checked=0 | checked=0 |
| パーセントエンコード | 偽陽性 | 緑 | 緑 |
| 素・日本語のみ | 緑 | 緑 | 緑 |

**壊れ方は 2 つあり、原因が別である。**

- **半角空白は抽出の段階で落ちる。** 引き金は空白の側で、山括弧の有無によらない。抽出で落ちた
  ものは後段の解決規則に影響されないので、3 設定すべてで checked=0 のまま動かない。返り値は
  「補正不要」としか読めない
- **山括弧とパーセントは抽出には成功する。** 解決規則が囲みを外すか decode するかで結果が変わり、
  外さなければ実在しても MISSING になる。こちらは騒がしいので気づける

つまり宣言が成立するかは、検査器の抽出規則と、囲みを外すかと、パーセントを decode するかという
独立した選択に依存する。日本語だけを含むパスは 3 設定すべてで正しく検査されたので、山括弧形式を
要求するのは半角空白の側だけである。

### 抽出軸の先例はあるが、解決軸の先例は無い

`scripts/check-related-refs.py` の `LINK` は山括弧の別枝を持ち、同じ fixture の 6 記法すべてを
抽出できた。だが同スクリプトが行うのはリンクの本数を数えることだけで、**リンク先をファイルへ
解決する経路を持たない**。パーセントの decode はリポジトリ全体に 1 箇所も無い。上の表で緑に
なったセルは、この抽出規則へ本 Issue の fixture 側の解決器を繋いだ結果である。

このリポジトリには相対リンクの実在検査が 1 つも無い。D.3 が宣言している「相対リンク検査を持つ
プロジェクト」に、skill を配っている当のリポジトリが該当しない。

### 記法の分布と移行コスト

`check-related-refs.py` の `LINK` と同じ抽出規則で追跡下 `*.md` 96 ファイルを走査した。フェンスと
インラインコードをマスクした本数を実リンク、マスク前との差を例示とし、`http` / `#` / `mailto`
宛は除外している。本 Issue の記法例はすべてインラインコードなので実リンクには入らない。

| 記法 | 実リンク | 例示 |
|---|---|---|
| 素・空白なし | 3 | 6 |
| 山括弧 | 14 | 0 |
| パーセントエンコード | 15 | 0 |
| 素・半角空白あり | 2 | 1 |

山括弧の実リンクは全数がパスに半角空白を含み、含まないものは 0 本だった。上の表が示した因果を
追跡下のデータも支持する。素・半角空白ありの 2 本は ISSUE-5 と ISSUE-7 が ISSUE-4 を指すもので、
どちらも `## 関連` 節の外にある。抽出の段階で落ちる側、つまり素朴な検査器から構造的に見えない
位置にある。

同じ走査を参照先で割ると、Issue を指す実リンクは `## 関連` 節の中に 25 本、節の外に 9 本ある。
**Issue 以外を指すローカルリンクは 0 本だった。** 節の外の 9 本のうち 4 本は `closed/` 配下に
ある。

**件数は数え方を書かないと再現しない。** 同じツリーを独立に数えた別の走査は山括弧 15 / 素・半角
空白あり 5 を報告した。差はラベルを伴わない `](...)` を数えるかと、コードスパン内の例示を数えるか
の 2 点で説明がつき、双方の証拠で一致した。構造的な結論はどちらの数え方でも変わらないが、着手の
根拠に件数を使うときは規約ごと書くこと。

### A.5 の親タスクリンクはまだ一度も使われていない

`^children:` を持つ `issue.md` は 0 件だった。対照として同じ述語で `^status:` を数えると 55 件
出る (`docs/issues/templates/issue.md` を含む。Issue ディレクトリだけなら 54 件)。検査が壊れた
0 ではない。

A.5 が規定する親タスクのリンク形式はこのリポジトリで一度も書かれていない。壊れるのは使ったとき
なので、実績が無いぶん書式を変える判断のコストは低い。

### ISSUE-24 が射程を節に限った理由は今は成立しない

ISSUE-24 は射程を `## 関連` 節に限る理由を「識別子が裸の数字であるリポジトリでは本文中の参照と
数量表現を機械的に区別できない。節に現れる識別子は参照だと言い切れる」と書いた。

だが識別子の形の canonical は `scripts/issue-id.py` の docstring で、in-repo Issue を指す唯一の
形を規定している。裸の数字である識別子はこの規約の下でつくれない。節境界は、識別子の規約が既に
消した曖昧さを避けるために引かれていたことになる。

## 何が問題か

1. **宣言が無条件である。** 「検査を持つ = コミット時に検出する」と読めるが、成立するかは抽出
   規則と解決規則に依存する。しかも失敗の一方は checked=0 という緑で返るので、出力を見ても
   気づけない。加えて skill はその検査を配らず、仕様も規定していない
2. **因果の記述だけが実測と合わない。** 山括弧形式を要求するのは半角空白であって、日本語では
   ない。抽出パターンは両形式を拾うので、パターン自体の変更は要らない
3. **ISSUE-24 が射程外にした 3 つの面が、記法の規約を持たないまま残っている。** 節の外の言及、
   A.5 の親タスクリンク、PR 本文のリンクの 3 つである
4. **A.5 の親タスクリンクは ISSUE-24 が問題と判断した性質をそのまま持つ。** 参照先が `closed/`
   へ移るとパスの深さが 1 段変わり、リンクだけが両方向とも書き換えを要求する

## 裁定 (2026-09-10)

**ISSUE-24 の「リンクを張らない」の射程を、節境界ではなく機構で定義し直して広げる。**

- **対象は「参照先が `closed/` を跨いで動く参照」。** 実質は issue.md を指すリンクで、A.5 の
  親タスクリンクも節の外の言及もここに入る。今のツリーではローカルリンクの全数が Issue 宛なので
  結果は「全リンク」と同じだが、機構で書いておけば将来スクリプトや skill へ張るリンクを巻き込まない
- **PR 本文の `Closes` 行はこの定義から外れる。** 面がリポジトリ外にあり、D.3 が補正できないため。
  射程外である理由をここに書いて、3 つ目の面を未回収のまま残さない
- **識別子の実在検査の射程は `## 関連` 節のまま動かさない。** 節境界は今リンク禁止と実在検査の
  両方を支配しているが、実在検査を本文全体へ広げると、存在しない識別子を例として書いた散文が
  偽陽性になる面が増える。広げる利益が薄い側なので触らない
- **既存のリンクは一括変換しない。** ISSUE-24 が決めた baseline へ記録して触ったついでに減らす
  形を、増える 9 本にもそのまま適用する

この裁定は ISSUE-24 の裁定の一部を再決定するものである。ISSUE-24 が比較した 3 案の canonical は
このリポジトリの外にあり、ここからは辿れない。着手時に 3 案の比較を持たないまま再決定することに
なる点を承知しておくこと。

### 名指しだけしておく案

D.3 も ISSUE-39 も ISSUE-28 も ISSUE-24 も、すべて「クローズがパスを変える」という 1 つの事実の
派生である。`status` は frontmatter にもあるので、`closed/` への移動そのものを廃す案が原理的には
ある。この Issue の軸ではないが、名指ししておかないと後続が「D.3 の文面を直す」枠の中でしか案を
出せなくなる。採らないなら理由を書くこと。

この案には実在するコストがある。Phase E は close 判定にディレクトリ位置だけを使うので、状態を
frontmatter へ一本化するとこの判定は frontmatter を読むしかなくなる。ISSUE-38 は配布先が独自の
スキーマを持つときに frontmatter からの抽出が静かに止まる件を記録しており、この案はその面を
正面から踏む。
