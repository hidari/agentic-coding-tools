# fix: Issue 間の相対リンクの書式が 3 通り混在している

## 背景

`docs/issues/` 配下の Issue が互いを参照するとき、書き方が揃っていない。どの形も読めるので実害は
見えにくいが、揺れは複数の軸にまたがっている。

タイトルの「3 通り」は軸 1 の第 1 段階 (リンクを張る / 張らない / そもそも参照を持たない) を指す。
実測すると軸は 2 つあり、通り数は分類の切り方で変わる。ディレクトリ名のタイトル部は後から
変えられない (採番スクリプトが同じ番号の別名を重複と見て止まる) ので、タイトルはそのままにして
実態をここに書く。

## 実測 (2026-08-24)

`docs/issues/` 配下の `issue.md` を closed 込みで 24 件走査した (`templates/` を除く。本 Issue を
含む)。対象は `## 関連` 節。

### 軸 1 第 1 段階: リンクを張るか

| 書き方 | 件数 | 該当 |
|---|---|---|
| リンクを張る | 10 | 下の第 2 段階で分かれる |
| リンクを張らず識別子だけ書く | 8 | ISSUE-15 から ISSUE-22 |
| そもそも Issue 間の参照を持たない | 6 | ISSUE-1, ISSUE-2, ISSUE-3, ISSUE-5, ISSUE-6, ISSUE-7 |

合計が母数 24 と一致する。3 つ目は揺れではなく対象外だが、書いておかないと「落ちた 6 件」と
区別できない。

### 軸 1 第 2 段階: 半角空白を含むパスをどうエスケープするか

リンクを張る 10 件の内訳。Issue のディレクトリ名はタイトル部を含むので、半角空白を持つものが多い。

| 書き方 | 件数 | 該当 |
|---|---|---|
| 山括弧で囲う | 3 | ISSUE-14, ISSUE-23, ISSUE-24 (本 Issue) |
| 空白を `%20` へ置換 | 7 | ISSUE-4, ISSUE-8, ISSUE-9, ISSUE-10, ISSUE-11, ISSUE-12, ISSUE-13 |

**`%20` 群の中に素のパスが混ざって見えるが、規則が破れているのではない。**ISSUE-4 と ISSUE-12 は
同じ節の中で素のパスと `%20` 形を併用しているが、素のまま書かれているのは空白を含まない
ディレクトリ名への参照だけである。つまり「空白があればエンコードする」が一貫して適用された結果で、
ファイル単位で形式が揺れているわけではない。

### 軸 2: リンクテキストの書き方

同じ走査で 5 通りが出た。件数は該当ファイル数ではなくリンク本数で数えている (1 ファイルが複数の
書き方を使うため)。

| 書き方 | 本数 |
|---|---|
| 識別子だけ | 13 |
| 識別子 + closed 表記 | 1 |
| 識別子 + タイトル | 6 |
| 識別子 + closed 表記 + タイトル | 5 |
| リンクを張らず識別子と説明だけ | 8 ファイル (リンク本数は 0) |

**5 通りに見えるが、独立に決めるべきことは 2 つしかない。**タイトルを含めるかどうかと、closed を
明示するかどうかである。closed 表記は対象の状態で決まる条件付きの要素なので、同じ書式でも参照先が
open なら現れない。この 2 つが独立に揺れた結果として、literal では 4 通りのリンクテキストが出ている。

### `## 関連` 節の外にもう 1 つの形式がある

節に限った走査では出てこないが、本文中には山括弧もエンコードも使わず、リンク先に生の半角空白を
そのまま含む形が実在する (ISSUE-5 と ISSUE-7)。CommonMark は山括弧で囲まないリンク先に空白を
許さないので、リンクとして成立するかがレンダラの寛容さに依存する。4 形式のうちこれだけが
「読めるとは限らない」側にある (実レンダリングは未確認)。

節の外の Issue 相互参照は 24 件中 15 件にあり、うち 5 件がリンク形である。したがってこの Issue の
射程を `## 関連` 節に限るかどうかも、決めるべきことに含まれる。

### 計測を 2 回外した

どちらも「エラー」ではなく、もっともらしい数値として返ってきた。

1. **裸識別子を 0 件と報告した。**拾う正規表現に `re.MULTILINE` を付け忘れていて、行頭アンカーが
   文字列の先頭にしかマッチしていなかった。**陽性対照はこれを検出しなかった。**対照として渡したのが
   1 行だけの文字列だったので、`^` が狙った機構ではなく文字列先頭という別経路で成立していた。
   対照を「節見出しに続く行」という検証対象と同じ構造上の位置へ置き直すと 8 件が現れた
2. **母数から自分自身を除外した。**走査を本 Issue の起票前に回したので、母数が 23 件、山括弧が
   2 件になっていた。起票した時点で自分も対象になるという当たり前のことが、走査の時点では
   視界に入らない

## 何が問題か

- **リンクを張らない形はクリックで辿れない。**識別子は一意なので機械的には解決できる (手順は
  skill の検索手順節にある) が、読む側がそれを知っている必要がある
- **節の外の形式はレンダラ依存になる。**上記のとおり CommonMark の規定から外れている
- **リンクテキストにタイトルを含める形は、既にディレクトリ名と一致していない。**`## 関連` 節に
  限れば 11 本中 2 本、節の外も含めると 3 本が不一致である。いずれも同じ写し間違いで、
  ディレクトリ名に無い記号がラベル側に入っている。drift の経路は「ディレクトリを rename する」
  ではなく「写した時点で一致していない」側なので、rename が禁じられていることは防御にならない。
  **節の内と外で数が変わること自体が、射程を決める必要があることの実例でもある**

### `%20` 形とクローズ時の補正は噛み合う

当初これを問題として挙げたが、実例が反証した。記録として残す。

クローズ時の相対リンク補正 (skill の Phase D.3) は `${ID}_` を鍵に探索する。エンコードされるのは
接頭辞より後ろのタイトル部だけなので、この鍵はエンコードで変わらない。`](../` の部分も同様である。
実際に過去のクローズコミットを読むと、`%20` 形のリンクが 3 方向とも正しく補正されている。

困るのはディレクトリ名全体を鍵にした一括置換を書くときだけで、D.3 はそれを規定していない。
**「エンコードされている = 検索できない」は、どこがエンコードされるかを見ずに立てた推論だった。**

## どこで決めるか

規約の canonical は `dev-workflow:in-repo-issue` skill が持つ。同 skill を全文確認したが、`## 関連`
節の書式を規定する記述は無い。関連する記述は 2 箇所あり、どちらも書式の規定ではない。

- `#` を含むパスについて URL エンコードせず素のパスでよいと書いている箇所。`#` に限った記述である
- Phase D.3 の grep パターンが山括弧を任意にしている理由の説明。パターン設計の根拠であって
  書式の指定ではない

決めたら散文ではなく検査へ落とせないかを先に検討すること。書式は機械検証できるので、散文に書く
だけでは同じ揺れが再発する。

## 裁定 (2026-08-26)

軸 1 と軸 2 の両方を「リンクを張らない」で解く。3 案の比較と設計の canonical は配布先
リポジトリの dotfiles の Issue 43 とその spec が持つ。ここには結論と、上流側に残る作業を書く。

### 決めたこと

- `## 関連` 節では他 Issue をリンクで参照せず、識別子だけを書く
- 他リポジトリの Issue を指すときはリポジトリ名を前置する。前置が無い識別子は自リポジトリを指す
- 射程は `## 関連` 節に限る。本文中の言及は検査しない
- 既存のリンクは一括変換せず、baseline に記録して触ったついでに減らす

軸 1 第 2 段階 (半角空白のエスケープ) と軸 2 (リンクテキストの書式) は、リンクを張らない決定に
よって決めるべきことでなくなる。

### なぜこれで解けるのか

書き換えの原因は `closed/` への移動でパスの深さが 1 段変わることにある。壊れる対象がリンクだけ
なので、リンクを張らなければ移動を残したまま書き換えが 0 になる。一覧で open と closed を
区別できる利点も失わない。

失うのは Issue 本体へのクリック導線で、エージェント側の導線は skill の検索手順が代替する。

### この Issue の実測が裁定を支えた

「リンクテキストにタイトルを含める形は、既にディレクトリ名と一致していない」という観測が決め手の
1 つになった。ISSUE-22 は rename を禁じることで参照が壊れないようにしたが、この経路は rename を
禁じても防げない。リンクを外すと写す対象が識別子 1 個に減る。

### 追加の実測 (2026-08-26): 他リポジトリ参照が別のものへ解決されていた

前置を規約に入れるかを決めるため、上流側の `## 関連` 節を全 27 件から抜き出し (非空行 137 行)、
他リポジトリの Issue を指す参照を見た。3 通りある。

| 書き方 | 該当 | 解決先 |
|---|---|---|
| `<owner>/<repo>#<数字>` | ISSUE-25 (closed) | GitHub 上の別オブジェクトへ解決される |
| リポジトリ名 + タイトル文字列 | ISSUE-27 | 機械では解決できない |
| リポジトリ名 + 識別子 | なし。この裁定で導入する形 | 解決できる |

1 行目は実害が出ている。ISSUE-25 は `hidari/dotfiles#36` と書いているが、指しているのは dotfiles の
in-repo Issue 36「CLAUDE.md を rules と skill へ分割し常時ロード量を減らす」である。GitHub 記法と
して解決すると dotfiles の PR #36「tirith コマンドセキュリティフックの整備と mise pin 固定」という
無関係のものになる。**どちらも実在するのでリンクは成立し、エラーにならない。**

`issue-id.py --check` はこれを検出しない。`<owner>/<repo>` の前置を GitHub のオブジェクトを指す形と
して免除しているためで、免除そのものは正しい。in-repo Issue を GitHub の番号空間で書いたことが規約
違反にあたるので、検査の穴ではなく規約の未適用として扱う。

2 行目のタイトル参照は、上で「写した時点で一致していない」と書いた経路をリポジトリ跨ぎで踏んで
いる。参照先のタイトルが変わっても、closed になっても、参照元は何も知らない。

#### 出所を明かさない参照は前置規約の対象外

同じ走査で、リポジトリ名も識別子も書かない参照が 1 件出た。ISSUE-14 (closed) の「同じ skill を
使う別リポジトリの investigation」がそれで、書き忘れではない。**このリポジトリが PUBLIC である
ために出所を伏せた形**であり、同じ節が理由も併記している。

前置規約はこの形を禁じない。規約が要求するのは「他リポジトリの Issue を識別子で指すときに
リポジトリ名を前置すること」であって、指せない参照を指させることではない。検査も違反として
報告しない (識別子が無いので実在検査の対象にならず、リンクも持たない)。

これを書き残すのは、規約だけを読んだ側が「リポジトリ名が無いから補う」と直しにいく余地を
消すため。補われると PUBLIC 制約の方が破れる。

### 上流側に残る作業

タスクへ反映した。検査の取り付けと、skill への規約記載と、既存ファイルへの適用の 3 つ。

検査の実装は dotfiles 側に先例があるが、そのまま持ち込めない。dotfiles は config-guard の
モジュールとして持ち、上流は pre-commit と CI へ既存の識別子記法検査と同じ形で載せることになる。

## 適用 (2026-08-26)

裁定を検査と skill へ落とした。

### 取り付けた検査

`scripts/check-related-refs.py` を新設し、pre-commit と CI の両方へ載せた。既存の
`issue-id-notation` と同じ形で、走査対象を絞らず `always_run` で固定してある。見るのは 3 つ。

| 見るもの | 違反になる形 |
|---|---|
| 節の存在 | `issue.md` が `## 関連` 節を持たない |
| 識別子の実在 | 前置の無い識別子が `docs/issues/` に無い |
| リンクの本数 | `LINK_BASELINE` より多い。少ないときも報告する (baseline を下げさせるため) |
| 括りの見出し | `<リポジトリ名> 側:` の形。配下の識別子が前置を失う |

節の存在を見るのは、見出しの等価変形 (末尾の `#` 列・余分な空白・setext 形) で節が開かず、
配下が丸ごと無検査になるため。変形ごとに正規化するより「持たないこと」を違反にする方が
穴が残らない。追跡下の `issue.md` 29 件は全て節を持つので、既存を赤にしない。

記法は写さず、`issue-id.py` を importlib で読み込んで借りている。dotfiles 側の同等の検査は
apm の deploy 先が追跡下に無いため写しを持たざるを得ず、記法が変わると検査側だけが取り残されて
「違反 0 件」で沈黙する。上流にはその制約が無いので、drift のクラスごと消した。借用名が
rename されたときは exit 2 (検査不能) で落ちる。

### 走査した結果

この Issue と ISSUE-28 の変更を含めた最終ツリーでの実出力。

```
実在する Issue: 29 個 / 走査したファイル: 32 個 (うち issue.md 30 個) / ## 関連 節: 30 節 / 識別子: 23 件 / 残リンク: 25 本
```

識別子は全て実在した。除外は `PR ` 前置とリポジトリ名前置とリンクテキスト内の 3 経路で、
`<owner>/<repo>#<N>` 形は 0 件になった。ISSUE-25 の 1 件をこの作業で直したため。

リンク 25 本のエスケープの内訳は山括弧 11 / `%20` 12 / エスケープ不要な素のパス 2。上の
「実測 (2026-08-24)」の表と数が合わないのは単位が違うためで、あちらはファイル数、こちらは
リンク本数を数えている。素の 2 本はタイトルに半角空白を含まないので、そもそもエスケープが要らない。

同じ規則を独立に実装した対照を並べ、走査ファイル数・節数・リンク本数・識別子数の全てが一致した。
対照側は「実在しない識別子 0 件」を信じる前に、4 記法と除外 4 規則を踏む合成 fixture で 6 件を
検出できることを先に確かめている。0 件が「検出できなかった」ではないことの根拠はそちらにある。

ただし対照が返したエスケープの内訳 (山括弧 9 / `%20` 13 / 素 3) は誤っていた。合計 25 は一致して
いたので、突き合わせを合計だけで済ませていれば通っていた。全 25 本を列挙して分類し直した結果が
上の 11 / 12 / 2 で、山括弧と `%20` を同時に使うターゲットも、素のまま半角空白を含むターゲットも
節の中には無い。**合計が合うことは内訳が合う根拠にならない。**

### 敵対的レビューで塞いだ穴

「違反を見落としたまま緑になる経路」だけを探すレビューを 1 本走らせ、14 経路の報告を得た。
うち実測で確認して塞いだのは次のとおり。深刻度は「規約違反を止める」という目的への効き方で
並べている。

| 塞いだもの | 塞ぐ前に何が起きるか |
|---|---|
| 終了コードの写像を subprocess で pin | 違反時の `return 1` を `return 0` にする 1 行が全緑のまま生存し、pre-commit も CI も永久に緑になる |
| リポジトリ名の照合を ASCII トークン境界へ | `my-dotfiles-backup` のような無関係の語が前置として通り、同じ行の自リポ識別子が全て免除される |
| `issue.md` の節の存在を必須に | 見出しの等価変形で節が開かず、配下が無検査になる |
| 数字記法の判定を借用先へ寄せる | 自前の厳しい後読みが `<owner>/<repo>#<N>` をパターン段階で落とし、免除の分岐へ一度も到達していなかった |
| `CROSS_REPO_REF` の `rstrip` を外す | 節に書いたファイルパスが `<owner>/<repo>` と誤認され、直後の識別子が免除される |
| 語形の境界を ASCII へ | `詳細はISSUE-1` のようにかな漢字へ続けて書くと `\b` が成立せず、識別子が読まれない |
| リンク計数でインラインコードを潰す | バッククォートで囲ったリンクの例示が違反として報告される (識別子側とは規則が食い違っていた) |
| 参照形式リンクを本数に数える | `[text][ref]` 形で規約を丸ごと迂回できる |
| 外部リンクのテキストから識別子を読む | 外部 URL を指すリンクは本数に数えないので、テキスト内の識別子がどちらの機構からも見えない |
| 括りの見出しを複数語まで | `<リポジトリ名> リポジトリ側:` が素通りし、この見出しが防ごうとした失敗が 2 語で再現する |
| decode 失敗を `skip` から `exit 2` へ | 不正なバイト 1 個でファイル全体が無検査のまま緑になる |
| 取り付けの pin を起動行の形まで | `entry: echo <path>` や `stages: [manual]` の変異が緑のまま通る |

塞いだ順に 16 個の変異を隔離コピーへ注入し、全てが赤くなることを確かめた。

塞がなかったものは検査の docstring へ「既知の限界」として書いた。チルダフェンス (`~~~`) の
未対応は借用先の `FENCE_LINE` が canonical なので、直すならそちらを直して両方の検査を同時に
直す。index と作業ツリーの乖離は `issue-id.py --check` と共通の性質で、CI が第 2 層になる。

### simplify が見つけた 3 つの写し

「借りる」と宣言した側にも写しが残っていた。どれも借用の一部だけを借りて、解釈の側を自分で
書いた形になっている。

1. **番号の同一性**。`ANY_ISSUE_DIR` は借りたが、その結果を `int()` で正規化する規則は借用先の
   関数側にあり、集合を自分で組んだ時点で落ちていた。`ISSUE-07` が `ISSUE-7` を指せない
2. **`GitError` の識別**。同じファイルの中で型として受けている箇所があるのに、入口だけ
   `type(e).__name__` の文字列比較で受けており、コメントがその必要性を誤って主張していた
3. **フェンス走査の状態機械**。`FENCE_LINE` は借りたが解釈は写しで、docstring が書いていた
   「借用先の正規表現を直せば両方が直る」という手当ては成立しない (チルダ対応は開いた
   フェンスの文字種を覚える必要があり、正規表現だけ広げると入れ子と閉じ忘れ検出が壊れる)。
   3 は写しのまま残し、docstring の誤りを訂正した

### baseline の鍵がクローズで壊れていた

最も効いた指摘。`LINK_BASELINE` の鍵をパスにしていたので、Phase D.2 の `git mv` で違反 2 件が
出る。実測した出力はこうだった。

```
ISSUE-4_.../issue.md: baseline 2 — baseline に記録があるが ... 見つからない
closed/ISSUE-4_.../issue.md: 2 > 0 — `## 関連` 節ではリンクを張らず識別子だけを書くこと
```

2 件目は診断が誤っている。リンクは 1 本も増えておらず、ファイルが動いただけなので、読んだ人は
リンクを外しにいく。baseline 10 件のうち 7 件が open なので、今後 7 回のクローズで必ず踏む。

鍵を Issue ディレクトリ名にすると、移動しても変わらない。同じ再現で違反 0 件になることを
確かめた。付随して `closed/` の接頭辞を持つ 3 エントリと、相対キーから絶対キーへの変換自体が
不要になった。**移動で変わらない同一性は識別子の側で、パスはクローズ手順が意図的に変えるもの。**

### 対照が別経路で緑になっていた (2 回)

`rstrip` を外す変更の対照を 2 回続けて外した。1 回目は識別子の前に `の` を挟んでいたので
`$` アンカーがそこで外れ、2 回目は語形で書いたので数字記法の枝を一度も通らなかった。どちらも
テストは緑で、変異を注入して初めて「機構を通っていない」と分かった。**陽性対照は「赤くなる
こと」ではなく「狙った機構を通って赤くなること」まで確かめる。**

### 起票前の数値をそのまま書きかけた

この節には当初 27 / 30 / 28 / 19 / 25 と書いていた。ISSUE-28 を起票する前に取った値で、この作業が
作るツリーでは一度も真にならない。ISSUE-24 は上の「計測を 2 回外した」で母数から自分が漏れる罠を
自ら記録しているのに、同じ罠を踏んだ。**走査結果を記録に残すときは、記録を書き終えたツリーで
測り直すこと。**

### 規約を書いた場所

`dev-workflow:in-repo-issue` skill へ `## Issue 間の参照` 節を新設した。置き場を frontmatter
スキーマの直後にしたのは、issue.md の中身を規定している層がそこにしか無いことと、Phase A.0 の
「相互に参照し」より前を読み手が通るため。同 A.0 の「相互リンク」「片方向リンク」という語も
規約と食い違うので参照へ直した。

射程の宣言はファイル面と節の両方で切ってある。skill 自身の `## 関連` 節や、A.5 が親の
`## タスク` へ置く子 Issue へのリンク、PR 本文のリンクまで届くと、規約だけ読んだ側がそれらを
違反と見て直しにいく。
