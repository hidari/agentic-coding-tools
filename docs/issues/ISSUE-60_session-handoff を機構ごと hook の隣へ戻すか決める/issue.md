# refactor: session-handoff を機構ごと hook の隣へ戻すか決める

## 背景

ISSUE-23 の B2 で `session-handoff` skill の責務を「書き出し」へ縮め、hook の挙動の再掲を落とした。
これは配布物としての欠陥を閉じる変更だが、根本の構造は残っている。

この機構は設計時に 3 層 (検知 = hook / 手順 = SKILL.md / 書式 = template.md) を 1 機構として
設計されていた。それを「hooks は Claude Code の設定、skill はエージェント資産」というファイル
種別の境界で 2 リポジトリに割ったのが、経路数の drift や record の呼び出しが境界を越える形の
原因である。機能の境界ではなく種別の境界で割ったことによる。

代償は既に払われている。drift を扱う Issue が配布先リポジトリ側に複数ある。

## 配布先での観測 (2026-09-17)

SKILL.md が hook の規則として書いているのは fail-closed の一点だけだが、手順 4 はそれとは別に
`record` の終了コードで取り付けの有無を判定している。この終了コードの意味が配布先で食い違っていた。

dotfiles の `record` は引き継ぎ書が無いときも例外が出たときも 0 を返していたので、この判定が
拾えたのは hook の実体が無い形 (python3 が起動に失敗する形) だけだった。SKILL.md の括弧書きは
その形だけを名指ししているので文面は偽になっていないが、終了コードの意味はどちらの側にも
書かれていなかった。dotfiles は v0.8.0 へ pin を上げる PR で `record` を直している (引き継ぎ書が
無いときと例外のときに 1。hook として呼ばれる経路は従来どおり無出力で 0。この日の時点でマージ前)。

直ったあとは、0 以外の終了コードに取り付け無し以外の原因が混ざる。手順 3 の直後に引き継ぎ書が
無いなら、手順 3 が失敗したか skill と hook が別の場所を見ているかで、手順 4 が呼ぶ「取り付け無し」
とは原因が違う。

fail-closed も終了コードも、skill の手順が配布物の外の実装を前提にしていて、その前提を見る検査が
どちらのリポジトリにも無い。下の 2 案目 (hook 側が provenance を記録する) を採れば、skill が
`record` を呼ばなくなり、手順 4 ごと要らなくなる。

同じ PR で、v0.8.0 が締めから落とした「切り替え先で自動で読み込まれる」という案内は dotfiles の
通知文へ移った (record が成功していればという条件付き)。行動の canonical を通知側に置く手順 5 に
沿った移し方で、上流の変更は要らない。

## 何を決めるか

skill をこのリポジトリの配布対象から外し、hook の隣へ戻す案がある。実現には未実測の前提が 1 つ
ある。配布先で apm のローカルパス依存が lockfile と `--frozen` で通るかを確かめていない。

もう 1 つ、hook 側が provenance の記録を自分で行う形にして skill から hook のパスを完全に消す案も
ある。こちらは配布先リポジトリ側の変更になるので、決めるのはあちら側になる。
