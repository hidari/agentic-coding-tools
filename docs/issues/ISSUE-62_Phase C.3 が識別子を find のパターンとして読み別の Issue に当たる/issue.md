# fix: Phase C.3 が識別子を find のパターンとして読み別の Issue に当たる

## 背景

`dev-workflow:in-repo-issue` の Phase C.1 は、`Closes` の直後の塊を装飾ごと識別子として抜き出す。
C.3 はその値をそのまま `find -path "*/${ID}_*/issue.md"` へ埋め込むので、値に `*` や `?` が
含まれるとグロブとして働く。

SKILL.md の「PR / コミット規約」節は、`Closes **<ID>**` が先頭の `**` ごと抽出され、C.3 の
「見つからない」分岐で no-op になると書いている。`*` を含む装飾については、この記述は実測と
合わない。

dotfiles からの報告を受けて、こちらでも再現した。

## 実測 (2026-09-18)

C.1 の 2 段と C.3 の `find` を SKILL.md から逐語で写し、隔離した fixture へ流した。fixture は
active な `145_z` / `15_v` / `ISSUE-52_x` と、closed な `45_y` の 4 件。BSD の `find` と、
Claude Code の zsh が `find` の代わりに呼ぶ bfs の両方で、結果は同じだった。

| 本文 | 抽出 | `find` の一致 | C.3 の行き先 |
| --- | --- | --- | --- |
| 対照: `Closes 45` | `45` | `closed/45_y` | 既に closed |
| 対照: `Closes ISSUE-52` | `ISSUE-52` | `ISSUE-52_x` | `ISSUE-52_x` の判定へ |
| 対照: `Closes 52` | `52` | なし | 見つからない |
| `Closes **45**` | `**45` | `145_z` と `closed/45_y` | **`145_z` の判定へ** |
| `Closes ?5` | `?5` | `15_v` と `closed/45_y` | **`15_v` の判定へ** |
| `Closes **52**` | `**52` | `ISSUE-52_x` | **`ISSUE-52_x` の判定へ** |
| `Closes **ISSUE-52**` | `**ISSUE-52` | `ISSUE-52_x` | `ISSUE-52_x` の判定へ (記述では no-op) |
| `Closes *ISSUE-52*` | `*ISSUE-52` | `ISSUE-52_x` | 同上 |
| `` Closes `ISSUE-52` `` | `` `ISSUE-52 `` | なし | 見つからない (記述どおり) |

数字の旧形式の識別子では、末尾が一致する別の Issue に当たる。`head -1` が先に返した 1 件しか
見ないので、本来の Issue が closed でも「既に closed」の分岐を通らない。

当たった先の結末は、その Issue のタスクの状態で決まる。全て `[x]` なら閉じられ、未完了が
残っていれば status が `in_progress` へ書き換わる。どちらも「見つからない」のログを出さないので、
出力からは気づけない。

数字だけの値は `ISSUE-<N>` 形式のディレクトリにも当たる。装飾が無ければ見つからないはずの値が、
先頭の `*` のせいで `ISSUE-<N>_` に一致する。このリポジトリの実ツリーでも C.3 の `find` を読み取り
だけで流し、`**45` が active な ISSUE-45 に当たることを確かめた (`45` は何にも当たらない)。
新形式だけのリポジトリでも、旧形式の癖で数字を装飾して書いた本文が別の Issue を動かす。

`ISSUE-<N>` 形式の識別子そのものを装飾した場合は、本来の Issue に当たる。実害は小さいが、規約の
記述とは逆の結果になる。

## 何が問題か

PR 本文は外部からの入力で、C.3 はそこから作った値を検索パターンに使っている。値の形を確かめる
層が無い。外部からの PR を受けるリポジトリでは、本文を書いた側が閉じる対象をずらせる。

同じ値は D.3 の `grep` と `find`、E.1 の `find` にもパターンとして渡る。直すなら C.3 の手前で
値を確かめて、以降の Phase へは確かめた値だけを渡す形が素直。

## 検討の起点

- 文字種の照合は注入を防ぐ層で、識別子の記法を確かめる層 (canonical は `issue-id.py`) とは別に
  置く。照合のために記法を SKILL.md へ写さないこと
- グロブ文字をエスケープするだけなら、装飾付きの値は「見つからない」へ落ちて、今の記述どおりの
  挙動になる。照合で弾く場合も、落ちる先のログを「見つからない」と揃えるかを決める
- `find` の一致が 2 件以上になるのは、値を確かめた後なら手順違反のときだけになる。それでも
  `head -1` で黙って 1 件を選ぶ形を残すかは別に決める
