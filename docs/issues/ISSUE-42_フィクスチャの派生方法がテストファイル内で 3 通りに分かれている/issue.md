# refactor: フィクスチャの派生方法がテストファイル内で 3 通りに分かれている

## 背景

`skills/devops/windows-vm-verification/test_winvm.py` は実機 `prlctl list -a -i -j` の出力を
`PRLCTL_LIST_JSON` として持ち、テストごとにその変種を作る。変種の作り方が 3 通りに分かれていて、
そのうち 1 つは**同じファイルが docstring で「やってはいけない」と名指ししている形**である。

## 実測 (2026-08-28)

| 行 | 形 | 何を再掲するか |
| --- | --- | --- |
| 55 | モジュール定数で `PRLCTL_LIST_JSON.replace` | IP の値 1 つ |
| 408 | `_with_bundle` が `json.loads` して該当キーだけ書き換える | 再掲しない |
| 532 | テストメソッド内で `PRLCTL_LIST_JSON.replace` | `GuestTools` の行を丸ごと (バージョン文字列を含む) |

表が数えているのは JSON テキスト層の派生で、タイトルの「3 通り」もこの層を指す。

### 表の外にもう 1 層ある

`PickIpv4` (137-166 行) はパース済みオブジェクト層で手書きの Python dict を組んでいる。
`PRLCTL_LIST_JSON` から派生せず、`{"type": ..., "ip": ...}` のリスト構造と `10.211.55.3` を
自前で書き直している (154 行と 157 行)。

JSON テキストの派生ヘルパでは覆えない層なので、寄せる対象に含めるかは別に決める必要がある。
**ただし下のタスク「IP の literal に名前を与えるか」の対象にはこの層も入る**ので、射程から
落とすと寄せ先が決まらない。

このほかに退化した直書き入力が 86 行 (`'{"ID": "x"}'`)、509 行 (`list_json=""`)、
133-134 行と 176 行 (`{}` / `None`) にある。これらは異常系の入力なので寄せる対象ではない。

`_with_bundle` の docstring はこう書いている。

> 置換は Home の値だけを狙う。フィクスチャのパスを再掲して str.replace すると、
> フィクスチャ側を変えたとき replace が黙って no-op になり、テストは
> 実在しないパスを見に行って隔離が全部 None に落ちる。

つまり 423 行の実装は、55 行と 532 行が採っている形を避けるために存在する。避けるべきとされた形が
同じファイルに 2 つ残っている状態になっている。

### 今は落ちない。落ちない理由が消費側の assertion に依存している

3 つとも、置換が空振りしても消費側の assertion が exact 値を見ているので赤くなる。

- 55 行の消費側 2 箇所はどちらも `169.254.10.20` を exact で assert する
- 532 行の消費側は `assertIsNone(c.ok)` を見る。空振りすると `GuestTools` が残って
  `ok=True` になるので落ちる

安全なのは設計ではなく、たまたま消費側が強い assertion を持っているから。帯だけを見る assertion や
警告文の部分一致だけを見る消費者が 1 つ増えると、その消費者は空振りしたフィクスチャに対して
緑を返す。

### 532 行はバージョン文字列まで再掲している

再掲しているのは `"GuestTools": {"state": "installed", "version": "26.4.0-57513"},` の全体。
フィクスチャのバージョンを実機の値へ追随させると (実機は既に別バージョンになっている) この
replace は no-op になる。

しかも影響はこの replace だけではない。バージョン literal `26.4.0-57513` はファイル内 7 行に
散っていて、フィクスチャ側を 1 つ変えると 3 つのテストが同時に赤くなる (隔離コピーで実測)。
再掲の幅は行単位ではなくファイル単位で効いている。

### IP の literal に名前が無い

`RUNNING_VM` / `STOPPED_VM` という定数があり、VM 名を再掲しない規律は既にある。IP には無い。
`10.211.55.3` が 11 行、`169.254.10.20` が 4 行に散っている。

## 応急処置は済んでいる

ISSUE-11 で 55 行に「置換が空振りしたら import 時に落ちる」ガードを 1 行入れた。
置換元を実在しない値へ変える変異で発火することを確認済み。532 行には入れていない。

## 何を直すか

派生の形を `_with_bundle` の方式へ寄せる。ただし `json.dumps` はフィクスチャの整形を失うので、
`PRLCTL_LIST_JSON` の直前のコメントが言う「実際の出力のままにしてある」の射程が値なのか
整形も含むのかを先に決める必要がある。
