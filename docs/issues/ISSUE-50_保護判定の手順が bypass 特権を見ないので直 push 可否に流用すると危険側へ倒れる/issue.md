# fix: 保護判定の手順が bypass 特権を見ないので直 push 可否に流用すると危険側へ倒れる

## 背景

`dev-workflow:in-repo-issue` の「クローズ経路: feature PR 同梱を優先 (main 直 push を避ける)」節が
持つ判定手順は、default branch に効いている rule に `pull_request` が含まれるかで保護の有無を決める。
この判定は rule を返す endpoint の応答だけを見ており、ruleset の `bypass_actors` を見ない。

endpoint は呼び出し元の bypass 特権を差し引かないので、`bypass_mode: always` を持つ当人が叩いても
同じ rule が返る。つまり手順は「PR が必須である」と答えるが、その人は直 push できる。

グローバル CLAUDE.md は「classic 404 だけで保護なしと結論するな」と「bypass 特権で素通り push して
required checks / PR レビューを欠落させるな」の 2 つを別々に規定している。判定手順が塞いでいるのは
前者だけで、後者は塞いでいない。

## 倒れる向きはトリガで変わる

同じ手順が返す同じ答えでも、どちらへ倒れるかは呼ばれた文脈で反転する。

| トリガ | 手順の答え | 実態 | 倒れる向き |
| --- | --- | --- | --- |
| Issue のクローズ経路を選ぶ | PR 必須なので同梱経路 | bypass できる | 安全側 (できるのに選ばないだけ) |
| 保護ブランチへ直 push してよいか | PR 必須なので直 push しない | bypass できる | 安全側 |
| bypass 特権を持つ主体が「自分は素通りできるか」を問う | (答えられない) | できる | **危険側** |

3 行目が問題になる。判定手順は「この branch は保護されているか」には答えるが「自分はその保護を
迂回できるか」には答えない。後者を問うている文脈で前者の答えを受け取ると、迂回できることに
気づかないまま「保護されているから安全」と結論する。

## 実測 (2026-09-02)

判定手順が使う endpoint と、bypass を持つ endpoint は別である。

- 手順が使う endpoint は `pull_request` を含む 4 rule を返す
- 同じ主体が ruleset 本体を引くと `bypass_actors` に自分が `bypass_mode: always` で入っている
- classic branch protection API は rc 1 (404)

つまり手順どおりに引いた結果からは、bypass の有無を区別できない。区別するには ruleset 本体を引き、
叩いている主体が bypass actor に含まれるかを解決する必要がある。

この事実の初出は ISSUE-41 の spec (2026-08-29 のレビュー中の訂正) で、ISSUE-48 が 2026-09-02 に
再実測している。どちらも記録しただけで、手順そのものには反映されていない。

## 着手前に確認すること

手順へ段を足すのは配布物の変更になる。踏む前に次を確かめること。

- `bypass_actors` の `actor_type` は `User` だけではない。`Team` / `Integration` / `RepositoryRole` が
  ありうる。実測できたのは `User` の 1 ケースだけなので、他の型の解決方法は未確認
- 消費側 (dotfiles) が判定手順の写しを持つ。ISSUE-48 が 6 点一致を実測しており、段を足すと 7 点目が
  増えて確実に drift する。向こうの `instruction_refs` は skill 名参照を母集団に持たないので赤くならない
- 配布は apm 経由の SHA pin なので、マージしただけでは開発機へ届かない
- 手順が返すものが 1 つの verdict ではなくなる。「保護されているか」と「自分は迂回できるか」は
  別の問いなので、2 つ返す形にするか、トリガごとに使い分けを書くかを決める必要がある

## タスク

- [ ] `actor_type` が `User` 以外のときの解決方法を確かめる。実測できていないのはこの面
- [ ] 手順が返す形を決める。1 つの verdict にまとめるか、保護の有無と迂回可否を分けて返すか
- [ ] 手順へ段を足し、消費側の写しへも同じ段を反映する。写しの drift は機械層が見ないので、
      反映漏れを防ぐ手立ても併せて決める
- [ ] グローバル CLAUDE.md の「bypass 特権で素通り push」の規範から、この手順へ辿れるようにするか
      判断する。規範と手順が別々に存在していても、規範を読んだ人が手順に到達できなければ意味がない
