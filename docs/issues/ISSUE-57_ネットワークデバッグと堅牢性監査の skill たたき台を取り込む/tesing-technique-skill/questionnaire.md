# 特化 skill 生成：質問リスト（＝契約の境界面）

> このファイルの三役：
> 1. 汎用 plugin と特化 skill の **境界面（契約）の定義**
> 2. 生成 skill が対話で埋めさせる **質問項目**
> 3. 生成される特化 skill の **テンプレート構造**
>
> 各質問には `なぜ訊くか（接続先の手法）` / `答えの形式` / `機密の扱い` を紐付ける。
>
> 凡例：
> - 🤖 機械判定の材料（analyze が自動で下書きできる／するべき）
> - 🧠 要人間判断（recommend が却下・確認のために人間に問う）
> - 🔒 機密に触れうる項目（参照のみ許可・直書き禁止）

---

## セクション 0：メタ情報

### Q0-1. プロジェクト識別子
- **なぜ**：report の見出し、verify の対象特定。
- **形式**：短い slug（例 `my-app`）。
- 🤖 リポジトリ名から下書き可。

### Q0-2. 主要言語・スタック
- **なぜ**：scaffold がどのツール（proptest/fast-check、cargo-fuzz 等）を提案するかの分岐。
- **形式**：言語とフレームワークの列挙（例 Rust/Actix Web＋TS/Next.js etc.）。
- 🤖 マニフェスト（Cargo.toml / package.json）から下書き可。

## セクション 1：信用境界（→ L5 ファジング／L2 契約の発火条件）

### Q1-1. 信用できない入力のエントリポイントはどこか
- **なぜ**：L5 ファジングの第一候補。「入り口なのにハーネス無し」を指すための材料。
- **形式**：エントリポイントの列挙（例：アップロード受け口の Webフレームワークのハンドラ、Workers などの fetch 境界、ブラウザ側のファイル読み取り）。各項目に「何をパース/デシリアライズするか」を添える。
- 🤖 依存シグネチャ（serde、extractor、パーサ crate）から候補を下書きできる。ただし **確定は人間**（外部公開されているか、認証で守られているかは意味論）。
- 🧠 各候補について「これは本当に信用できない入力か？（内部専用ではないか）」を確認させる。

### Q1-2. 独自フォーマットのパーサはあるか
- **なぜ**：L5 ＋ L3 ゴールデンの両方が刺さる典型。
- **形式**：ファイルのフォーマット名と実装場所（例：画像ファイルの場合のEXIF パース、その他独自メタデータのパース）。
- 🤖 grep で候補抽出可。🧠 自前実装か既存 crate 依存かで扱いが変わるので確認。

---

## セクション 2：正解が定義できない領域（→ メタモルフィックの発火条件）

### Q2-1. 「正しい出力を一意に定義できない」処理はあるか
- **なぜ**：メタモルフィックテストはここでしか発火しない。**コードからは機械判定不能**な意味論判断。
- **形式**：処理の列挙＋「言えそうな不変関係」の下書き（例：画像処理で「回転→処理 ≒ 処理→回転」）。
- 🧠 **完全に人間判断**。recommend はここを勝手に埋めず、必ず問う（過剰処方防止の代表例）。

---

## セクション 3：設計の正しさが致命的な箇所（→ 形式手法／Alloy の発火条件）

### Q3-1. 壊れると致命的な設計上の制約はあるか
- **なぜ**：Alloy 等の形式手法は「認証・権限・状態制約」に絞ってこそ費用対効果が出る。
- **形式**：制約の列挙（例：この権限モデルで「他人のユーザー情報が見えない」が絶対、共有リンクの失効ルール）。
- 🧠 **ドメイン知識依存**。機械では出せない。recommend が問う。

---

## セクション 4：既存テストの棚卸し（→ ミューテーション／背骨の現在地）

### Q4-1. 既に存在するテスト種別
- **なぜ**：背骨の現在地を把握し、ミューテーション（下地が要る）の発火可否を判断。
- **形式**：L1〜L5・オプションのどれが既にあるか（proptest ディレクトリ、fuzz ターゲット、snapshot の有無）。
- 🤖 **ほぼ全自動で下書き可**（ディレクトリ構成・マクロ・依存から）。

### Q4-2. 二実装が併存する箇所はあるか
- **なぜ**：差分テストの発火条件（旧実装／参照実装の存在）。
- **形式**：併存ペアの列挙（例：FFI バインディングの新旧実装、Rust 実装と TS 実装 etc.）。
- 🤖 検出可能な場合あり。🧠 「意図的に一致させたいペアか」は確認。

---

## セクション 5：実行環境とアクセス（→ verify の実行先）🔒

> **最重要の機密ゾーン。ここは「参照」のみを書き、資格情報そのものは絶対に書かない。**

### Q5-1. verify（ファジング/ミューテーション等）を実行してよい環境
- **なぜ**：本番のユーザーデータ・オブジェクトストレージ等に触れさせないための境界定義。
- **形式**：許可される環境の識別子（例：`local`、`ci-ephemeral`、`staging-copy`）と、**明示的に禁止する対象**（例：本番オブジェクトストレージ、本番 DB）。
- 🔒 環境の**名前と方針**は書いてよい。**接続文字列・鍵は書かない。**

### Q5-2. その環境へのアクセス方法（参照のみ）
- **なぜ**：verify を自動で走らせるための手順。ただし機密は在り処への参照に留める。
- **形式**：**参照の記述のみ**。例：「1Password 項目 `<project>-staging` を `op run` で注入」「環境変数 `X` は CI の Service Account 経由」。
- 🔒 **直書き禁止**。プレースホルダは `op://vault/item/field` 形式の参照か、環境変数名のみ。

## セクション 6：プロジェクトの制約・哲学（→ recommend の抑制条件）

### Q6-1. 方法論上の制約・原則
- **なぜ**：recommend が「一般には推奨だがこのプロジェクトでは避ける」を判断するため。
- **形式**：原則の列挙（例：依存最小化＝新ツール追加は慎重に、データ主権＝外部サービスに実データを送らない、本番非接触）。
- 🧠 人間が明示。recommend の提案フィルタになる。

## テンプレートに常設する固定ブロック（質問ではなく生成物に必ず入るもの）

### 機密ハードコード禁止の宣言（生成物冒頭に常設）
```
# ⚠️ このファイルに資格情報を直書きしないこと。
# アクセス情報は必ず参照（op://... や環境変数名）で記述する。
# 下の検出スクリプトは「うっかりの警報」であり、通過＝安全の保証ではない。
```

### ゆるい機密検出スクリプト（同梱、厳密でなくてよい）
- 目的：**完璧な検出ではなく、素朴な直書き事故への警報**。
- 検出するもの（ヒューリスティック 3 種）：
  1. 既知プレフィックス（`AKIA` / `sk-` / `ghp_` / `xoxb-` 等）
  2. 高エントロピーな長い連続文字列
  3. キーらしい名前の隣の長い値（`api_key = "..."`, `secret: "..."`）
- 明示する限界（epistemic honesty）：
  - 「参照に見えて実は秘密」「秘密に見えない秘密（短いトークン・パスフレーズ）」は取りこぼす。
  - **「スキャン通過＝安全」ではない**旨を検出出力に必ず併記。
- 多層化：同じヒューリスティックを **pre-commit（Lefthook）** 側にも置き、生成時とコミット時の二段で網をかける。

## この質問リストの使われ方（3 フェーズ対応）

1. **生成時**：generate-project-skill が上から順に対話。🤖 項目は analyze の下書きを提示して確認、🧠 項目は必ず人間に問う、🔒 項目は参照形式を強制。
2. **生成物**：回答が特化 skill に整形され、固定ブロック（禁止宣言＋検出スクリプト）が常設される。
3. **運用時**：汎用 plugin（analyze/recommend/scaffold/verify/report）が、この特化 skill を「契約の充足済みデータ」として参照して動く。
