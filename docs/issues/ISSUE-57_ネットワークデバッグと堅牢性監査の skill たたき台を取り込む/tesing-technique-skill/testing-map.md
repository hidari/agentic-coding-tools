# テスト手法の地図：堅牢性への寄与で整理する

> 分類の考え方：テストは「合格/不合格」ではなく「何に対する確信を買っているか」で整理する。
> 構造は *背骨（積み上げ式）＋ オプション（条件が来たら差し込む）* の二層。
>
> 凡例：
> - ✅ 定番と言える（自信あり）
> - ⚠️ 私（Claude）が最新状況を追いきれていない／決定版を確信できない部分

---

## 二層構造の全体像

- **背骨（L1〜L5）**：下がないと上が効きにくい依存関係がある。基本は下から順に積む。
- **オプション**：難易度の階段ではなく「該当する発火条件が来たら、背骨のどこにいても差し込む」もの。

現実には両者は交差する。背骨を全部積んでからオプション、ではなく、条件が来た時点で割り込むのが実態に合う。

---

## 背骨：積み上げ式（下から順に）

### L1 例示ベースのユニット / 結合テスト
- **目的**：想定した入力に対する実装の正しさ。回帰ネット兼、実行可能な仕様書。全ての土台。
- **限界**：思いついた範囲しかカバーしない。
- **ツール**：Rust 標準の `#[test]` / `cargo test` ✅ ／ TS は Vitest ✅

### L2 契約テスト（コンポーネント / 依存の境界）
- **目的**：依存の境界を固める。外部依存をラッパ＋契約テストで包む（library-contracts パターン）。
- **ツール**：専用フレームより、L1 の土台の上に「ラッパの振る舞いを検証するテスト」として書くのが基本。

### L3 キャラクタライゼーション / ゴールデン（スナップショット）
- **目的**：**変更の安全性**。現在の挙動そのものを正解として焼き付け、意図しない差分を警報する。
- **刺さる場面**：
  - 仕様が曖昧なコード／レガシーのリファクタ安全網
  - 出力が構造的で長いもの（AST、シリアライズ結果、レンダリング済み HTML、CLI 出力）
  - 例：`.po` パーサ、静的サイトジェネレータのビルド出力
- **弱点**：正しさは保証しない（間違った出力もそのまま焼き付く）。承認を惰性でやると空洞化する。正しさは L1/L4 に任せる分業。
- **ツール**：
  - Rust：`insta`（`cargo insta review` で対話承認）✅ ／ `expect-test`（インラインスナップショット）✅
  - TS：Vitest / Jest のスナップショット（`toMatchSnapshot` / `toMatchInlineSnapshot`）✅ ―― 追加ライブラリ不要

### L4 プロパティベーステスト（入力空間全体）
- **目的**：不変条件・代数則・ラウンドトリップを膨大な入力で検証。**不変条件を言語化する**層。
- **位置づけ**：背骨の折り返し点。ここを書けると以降（L5・差分・メタモルフィック）の質が変わる。
- **ツール**：Rust `proptest` ✅（`quickcheck` も）／ TS `fast-check` ✅

### L5 ファジング（敵対的・不正な入力）
- **目的**：信用できない入力の入り口で、panic / クラッシュ / 無限ループ / メモリ異常を探す。
- **L4 との関係**：L4 で書いた不変条件がそのままファジングのオラクル（異常判定基準）になる。だから L4 → L5 の順が素直。
- **Web で効く入り口**：ボディのデシリアライズ、クエリ/パス/URL デコード、ルーティング、認証トークンのパース（JWT・Cookie）、アップロードファイルの中身・EXIF、独自フォーマット（`.po`、テンプレート HTML）。
- **Web で効きにくい所**：認可判定・状態遷移・ビジネスルール（＝クラッシュしないが間違う類）。ここは形式手法（Alloy）の担当で棲み分け。
- **運用**：見つけたクラッシュ入力を回帰テスト（L1）に昇格させるループとセットで初めて価値が出る。
- **ツール**：
  - Rust：`cargo-fuzz`（libFuzzer ベース）✅ ＋ `arbitrary`（生バイト列→型付き入力の導出。Webフレームワークのハンドラ検証に有効）✅
  - TS：⚠️ 決定版を確信できない。`fast-check` で大量ランダム入力を投げて代用が現実的。カバレッジ誘導型の JS/TS エコシステム成熟度は要・最新確認。

## オプション：条件が来たら差し込む（順序不問）

### ミューテーションテスト
- **目的**：ソフトではなく **テストスイート自体の検出力** を測るメタ層。
- **発火条件**：L1〜L4 がある程度揃っている（測る対象＝下地のテストが必要）。手間は軽いが、効果が下地に比例する。
- **ツール**：Rust `cargo-mutants` ✅ ／ TS `Stryker`（`@stryker-mutator`）✅

### 形式手法（Alloy など）
- **目的**：実装の前に **設計そのものの正しさ** を検証。権限・制約設計にドンピシャ。
- **特徴**：実装を待たなくていい数少ない手法。用途を認証・権限に絞れば書く量はコンパクトで、**前倒しできる**。難易度階段の「最後」に置くのは誤解を招く。
- **道具**：Alloy（関係・構造的制約の有界モデル探索）。並行・分散の時相的性質なら TLA+ が別担当。⚠️ Rust/TS の「コード側」ツールではなく、別レイヤの専用言語。

### 差分テスト（differential testing）
- **目的**：同じ入力を 2 実装に通し、出力の一致を検証。正解を人間が書かなくていい（片方をオラクルにする）。
- **発火条件**：参照実装 or 旧実装が存在する。例：**FFI バインディング層の載せ替え**でのデグレ検出、自作パーサ vs 枯れた既存実装、Rust 実装 vs TS 実装。
- **道具**：⚠️ 専用の定番クレート/パッケージは（私の知る限り）無い。L4 のプロパティ系（`proptest` / `fast-check`）で入力生成 → 両実装に通す → `assert_eq`、という「書き方の型」。

### メタモルフィックテスト
- **目的**：正解そのものは定義できないが「入力をこう変えたら出力はこう関係するはず」という*変化の法則*が言えるとき用。
- **例**：画像処理（回転してから処理 ≒ 処理してから回転）、検索（絞り込んだ結果は元の部分集合）、ソート（並べ替えてからソートしても同じ）。
- **道具**：⚠️ 専用ツールは無し。実体は「正解が無い版のプロパティ」なので `proptest` / `fast-check` に自然に乗る。

### 並行性・障害下
- **目的**：並行実行の順序・障害注入下での安全性。
- **発火条件**：実際に共有状態の並行がある所にだけ。
- **内部にも階段あり**：軽い方（TSan・ストレステスト）で絞り込んでから、重い方（`loom` の網羅探索）へ。いきなり loom は状態爆発でつらい。
- **ツール**：Rust `loom`（並行実行順序の網羅探索）✅ ／ ThreadSanitizer（TSan）✅ ／ フォールトインジェクション・決定論的シミュレーション ⚠️（2026 時点の Rust シミュレーション系の成熟度は要・最新確認）

## 効率の見立て（ソロ・多プロダクト前提）

投資対効果が高い順のざっくり方針：

1. 型で不正状態を表現不能にする（Rust ならほぼタダで最も効く。テスト以前の設計）
2. コア不変条件のプロパティベース（L4）
3. 信用できない入り口のファジング（L5）
4. 本当に難しい設計（認証・権限）にだけ形式手法（Alloy）
5. 並行テストは実際に共有状態の並行がある所にだけ

背骨は基本の登り順、オプションは条件が来た時点で背骨のどこにいても差し込む――この二層で持っておくのが現実的。
