# robustness-audit — 叩き台一式と引き継ぎメモ

テスト戦略の監査を自動化する skill（plugin 候補）の叩き台。会話で設計した内容を Claude Code に引き継いで、実ソースの上で詰めるための出発点。

## これは何か

コードベースを分析して「足りない/弱い検証」を判別し、堅牢性のためにどのテスト手法を足すべきかを推奨する **コントローラー型 skill**。5 フェーズ（analyze → recommend → scaffold → verify → report）を、フェーズごとに新鮮なサブエージェントへディスパッチして回す。中核の規律は **epistemic honesty**：機械判定できること（🤖）と、人間のドメイン知識が要ること（🧠）と、確認できていないこと（⚠️）を常に区別し、過剰処方しない。

## 現状のステータス

叩き台（draft）。skill-creator の流儀でいう「一周目の draft を書いた」段階。テストプロンプトでの実走・評価・改善ループはこれから（＝Claude Code 側で実ソースに当てて回す想定）。

確定していること（confirmed）:
- テスト手法の二層構造（背骨 L1–L5 ＋ オプション）とその発火条件の地図。
- 汎用 plugin ／ 特化 skill の分離を「契約（質問リスト）」で繋ぐ方針。
- 機密ハードコード禁止＋ゆるい検出スクリプト（動作確認済み）＋pre-commit 二層。
- コントローラー＋サブエージェント構造（superpowers の SDD から作法を借用）。
- 監査は SDD と違い「継続実行」しない ── 🧠 確認と verify の本番非接触が停止点。

未確認（unverified）:
- microsoft/apm 上で「コントローラー skill がサブエージェントをディスパッチ」「plugin が生成 skill を同梱し別 skill を出力」が素直に表現できるか。superpowers は apm ではなく各ハーネス（Claude Code 等）のネイティブ plugin 機構向け。
- superpowers の作法は検索抜粋・DeepWiki の二次引用から読んだもの。上流の SKILL.md 本文の直接確認が未了。

## ファイル構成

```
robustness-audit/
├── SKILL.md                     コントローラー本体。5フェーズ＋サブエージェント作法＋停止点
├── references/
│   ├── testing-map.md           テスト手法の地図（背骨＋オプション、Rust/TS ツール）
│   ├── questionnaire.md         契約の境界面＝特化skill生成用の質問リスト
│   └── generator.md             特化skill生成ガイド（機密禁止・検出同梱の強制）
└── scripts/
    └── detect_secrets.py        ゆるい機密検出（警報目的、通過≠安全を明記）
```

各ファイルの役割:
- **SKILL.md** ── オーケストレーションの骨格。「何を機械で、何を人間に問うか」のラベル規律、ファイル経由の受け渡し、4ステータスプロトコル、モデル選択、そして superpowers から意図的に外した「停止点」を規定。
- **references/testing-map.md** ── 手法ごとの目的・発火条件・代表ツール。recommend フェーズが参照する本体知識。
- **references/questionnaire.md** ── 汎用と特化の契約。🤖/🧠/🔒 ラベル付きの質問が、そのまま生成 skill の対話項目・特化 skill のテンプレート構造になる三役。
- **references/generator.md** ── 特化 skill を生成する手順。固定ブロック（機密禁止宣言＋検出スクリプト同梱）を常に埋める。
- **scripts/detect_secrets.py** ── 既知プレフィックス／高エントロピー／キー名隣接の3ヒューリスティック。参照形式（op://、env var）は素通し。

## 設計の芯（引き継ぎ時に失いたくない判断）

1. **過剰処方しないことが信頼の条件。** 「何にでも fuzzing を足せ」と言い出すツールは信用を失う。コードから判定できない意味論（信用境界か／正解が定義できない領域か／設計が致命的か）は、断定せず人間に問う。
2. **背骨とオプションは別物。** L1–L5 は積み上げ順に意味がある（特に L4 プロパティ→L5 ファジングは「不変条件を書く→それがオラクルになる」）。差分・メタモルフィック・形式手法・並行は、発火条件が来たら差し込むオプション。
3. **汎用と特化は契約で繋ぐ。** 方法論は汎用 plugin、プロジェクト固有の答え（信用境界・致命的制約・環境アクセス・哲学）は特化 skill。library-contracts と同じ発想。
4. **機密は「在り処への参照」で書く。** 資格情報を skill に直書きしない。規律を人間の意志力でなく仕組み（生成器の強制＋検出＋pre-commit）に乗せる。
5. **監査は継続実行しない。** superpowers の SDD 構造は借りるが、🧠 確認と verify 本番非接触という停止点は残す。成果物が「判断」だから。

## ここからの進め方の地図

実ソースがある Claude Code 環境で詰める前提。上から順に、粒度の小さい検証しやすいものから。

### フェーズ A：一次ソースの確認（設計の土台固め）
- [ ] superpowers の SKILL.md 本文を直接読む（特に `subagent-driven-development` と `writing-skills`）。二次引用でなく本文で、ディスパッチプロンプトの書式・受け渡し・停止条件の作法を確認。
- [ ] microsoft/apm 側で「コントローラー→サブエージェント」「plugin が生成 skill を同梱」が表現可能かを、apm の実仕様で確認。表現できないなら、コントローラー構造をどう畳むかを決める。
- 目的：SKILL.md 末尾の ⚠️ 2項目を潰し、confirmed に昇格させる。

### フェーズ B：ディスパッチプロンプトのテンプレート作成
- [ ] `analyze` サブエージェント用プロンプト雛形を書く（1フェーズ分だけ渡す・結果をファイルで返す・4ステータスで報告、の具体形）。
- [ ] 同様に `scaffold` / `verify` / `report` 用も。recommend は 🧠 対話をコントローラーが持つのでプロンプト化は最小限。
- 目的：抽象的な「サブエージェントにディスパッチ」を、実際に走る文面に落とす。superpowers の implementer-prompt.md が参考形。

### フェーズ C：実プロジェクトで最初のドッグフーディング
- [ ] `analyze` を実プロジェクトのソースに走らせ、🤖 インベントリ（信用境界の入り口・既存テスト種別・二実装の有無）が実際に取れるか検証。
- [ ] `recommend` の 🧠 質問が実務で機能するか（粒度が細かすぎ/粗すぎないか）を確認。ここが skill の当たり判定の要。
- [ ] 最初のスコープは **アップロード受け口の L5 ファジング** に絞る推奨。効果が数字（新規クラッシュ検出）で出るので verify→report を最短一周でき、骨格が早く固まる。
- 注意：verify は必ずローカル/CI コピー上で。本番のオブジェクトストレージ・DB・ユーザーデータには一切触れない。

### フェーズ D：特化 skill 生成器の実装と検証
- [ ] `questionnaire.md` に沿って対象プロジェクトの特化 skill を **手で一本書く**（＝生成器の出力の完成形を先に作る）。テンプレート構造が確定する。
- [ ] `detect_secrets.py` を pre-commit（Lefthook）に組み込み、生成時＋コミット時の二層を実際に回す。
- [ ] 生成器（generator.md の手順）を、手書き完成形を再現できるかで検証。

### フェーズ E：分割とサブエージェント化の最終判断
- [ ] フェーズ A–D の実地感触をもとに、skill を単一のままにするか分割するかを決める。会話時点の暫定案は「analyze 独立／verify 独立／recommend+scaffold+report 統合」の非対称分割だが、superpowers 流に自動トリガー前提なら更に細かく割る余地あり。
- [ ] verify を「独立 skill かつ権限隔離サブエージェント」で切り出すのを最優先候補に（safety-critical を規律でなく権限で担保）。

### 横断的に持っておく原則
- 各ステップで、確定した事実・推論・未確認を分けて記録。
- 実ソースに当てて初めて分かることを優先。会話で描けたのは地図まで。
- ⚠️ 印は「Claude が確信を持てなかった箇所」の目印として残す。潰せたら confirmed に上げる。

## 一言サマリ

地図（testing-map）と契約（questionnaire）とコントローラー（SKILL.md）と安全弁（detect_secrets）まで骨格はできた。ここから先は実ソースの上で、A: 一次ソース確認 → B: プロンプト雛形 → C: 実プロジェクトで analyze/recommend 実走 → D: 生成器検証 → E: 分割の最終判断、の順に固める。最初の一撃はアップロード受け口の L5 ファジングが、効果が数字で出て一周が早い。
