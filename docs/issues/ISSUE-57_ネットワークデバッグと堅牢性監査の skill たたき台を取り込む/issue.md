# ネットワークデバッグと堅牢性監査の skill たたき台を取り込む

## 背景

2 つの skill のたたき台を会話で設計したまま追跡外の作業ディレクトリに置いてあり、
そこに居る限りどの検査も届かず、次のセッションからも見えない状態だった。この Issue で
追跡下へ移し、配布できる skill にするまでを扱う。

- `network-debug-skill-draft/`: macOS で通信そのものを観測して切り分ける
  `network-debug-mac`。既にこのリポジトリのパッケージ構造に沿った形で書かれており、
  構成の根拠は同梱の `DECISIONS.md` が持つ
- `tesing-technique-skill/`: テスト戦略の監査をコントローラー + subagent の 5 フェーズで
  回す `robustness-audit`。フラットな置き方なのでパッケージ構造への詰め直しが要る
  (ディレクトリ名の typo も未修正のまま)

### 移動時に落としたもの

どちらも PUBLIC であることに由来する制約で、たたき台の判断そのものを変えたわけではない。

- **別ハーネス向けの記述**: 配布先を Claude Code に絞った。`snippets/apm-targets.md` は
  全体がその向けだったのでファイルごと削除。`DECISIONS.md` の「割り方を運ぶ仕組み」は
  別ハーネスのフラット展開の挙動を根拠にしていたため、component skill の description が
  互いに競合するという Claude Code 単独で成立する論理へ書き直した
- **プロダクト固有名詞**: private リポジトリのものが混ざるため一般化した。発火条件の
  具体性 (どういうときに何が刺さるか) は残し、出所だけ落としてある

この 2 つは検査では捕まらなかった。固有名詞は禁止語リスト 28 件のどれにも当たらず、
移動前に全ファイルを `--check-text` へ通しても `findings=0` だった (実測)。棚卸しの表は
見つけた分しか載らないという既知の性質で、リストの穴ではない。

マージ前のレビューで、語単位の照合では原理的に捕まらない形がさらに 2 種類見つかった。

- **集合が指紋になる形**: 個々は残してよい公開 OSS 名なのに、列挙の組み合わせが一つの
  プロダクトを特定できてしまう。語単位の対照は 1 語ずつの可否しか測れないので、どの語も
  「正しく残す」と判定されたまますり抜ける
- **解釈を反転させる一行**: 「この文書は特定の対象を念頭に書いた」と明かすメタ記述。それ自体は
  固有名詞を 1 つも含まないのに、文書中の全ての例示を架空のものから実在の答えへ読み替え
  させる。語の集合をいくら見ても検出できない

前者は例を実在と異なる組み合わせへ差し替え、後者は一行を落として解消した。1 ファイルだけ
直すと同じ語が別ファイルに残るため、消えるべき語と残るべき語の対照を全ファイルへかけ直して
確定させている。
