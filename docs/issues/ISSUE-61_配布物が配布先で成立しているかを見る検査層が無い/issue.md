# feat: 配布物が配布先で成立しているかを見る検査層が無い

## 背景

ISSUE-23 の最後のタスクで、保留していた 7 箇所を ISSUE-15 が設計した 3 層に当てた。結果、B 面
(配布先に存在しない前提を断定形で書いている) はどの層も見ていないことが分かった。

- 層 1 (形の決まった漏洩ルール) と層 2 (禁止語リスト) は漏洩の形を見るので対象外
- 層 3 (ゲートの PUBLIC 漏洩スイープ) は「公開してよい状態か」を見るので「配布先で動くか」には
  届かない

つまり「配布物が配布先で成立しているか」を担当する層が存在しない。ISSUE-23 が B を「露出ではなく
別の欠陥」と分類したことが、そのまま担当の不在を意味していた。

この欠陥の性質は、失敗が「エラー」ではなく「静かに何もしない」形で出ることである。ISSUE-23 の B1
では、ディレクトリ名を持たない配布先で早期 skip の判定条件が恒真になり、検査せずに合格を返して
いた。配布元では前提が満たされているので、ここで動かしても気づけない。

## 何を決めるか

観点を足す場所の候補が複数ある。ゲートの並列レーンへ足すと体数が増え、リミットに直接効く。配布物を
触った PR でだけ起動する条件付きにする形もある。機械検査へ落とせる部分があるかも未検討。

## タスク

- [ ] 「配布先に存在しない前提を断定形で書いている」を検出する観点をどこへ置くか決める
- [ ] 機械検査へ落とせる部分があるか検討する。配布物の中にリポジトリ固有のパスが literal で
      現れることは検出しうる
- [ ] 落とせない部分は観点として書き、検出すべき例と許可すべき例の両方を実際に通す
