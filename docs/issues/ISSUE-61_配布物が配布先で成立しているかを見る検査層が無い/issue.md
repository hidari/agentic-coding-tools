# feat: 配布物が配布先で成立しているかを見る検査層が無い

## 背景

ISSUE-23 の最後のタスクで、保留していた 7 箇所を ISSUE-15 が設計した 3 層に当てた。結果、B 面
(配布先に存在しない前提を断定形で書いている) はどの層も見ていないことが分かった。

- 層 1 (形の決まった漏洩ルール) と層 2 (禁止語リスト) は漏洩の形を見るので対象外
- 層 3 (ゲートの PUBLIC 漏洩スイープ) は「公開してよい状態か」を見るので「配布先で動くか」には
  届かない

つまり「配布物が配布先で成立しているか」を担当する層が存在しない。ISSUE-23 が B を「露出ではなく
別の欠陥」と分類したことが、そのまま担当の不在を意味していた。

この欠陥の性質は、失敗が「エラー」ではなく「静かに何もしない」形で出ることである。ISSUE-23 の B1
では、ディレクトリ名を持たない配布先で早期 skip の判定条件が恒真になり、検査せずに合格を返して
いた。配布元では前提が満たされているので、ここで動かしても気づけない。

## 何を決めるか

観点を足す場所の候補が複数ある。ゲートの並列レーンへ足すと体数が増え、リミットに直接効く。配布物を
触った PR でだけ起動する条件付きにする形もある。機械検査へ落とせる部分があるかも未検討。

## ISSUE-58の計画レビューで見つかった2件 (2026-09-24)

どちらも配布元では気づけず、配布先で読み込まれたときにだけ壊れる形である。出所は ISSUE-58の計画レビューの B-13と B-15 / D-7。指摘の全文は残っておらず、題と行き先は ISSUE-58の plan の「計画レビューの裁定」節にある。どちらも2026-09-24の作業ツリーで今も成り立つことを確かめた。

### 1. インストール先の決め打ちの検査が plugin の内側の skill 名を見ない (B-13)

`scripts/check-package-shape.py` の規約 7は、パッケージが自分のインストール先を `~/.claude/<plugins|skills>/<パッケージ名>/` の形で名指すことを違反にする。パッケージ名として集めるのは plugin の名前と単体 skill の名前だけで、plugin の内側の skill (`plugins/*/skills/*`) の名前は入らない。この開発機のインストール先には、plugin の配下 (`~/.claude/skills/dev-workflow/skills/<名前>/`) と平らな置き場 (`~/.claude/skills/<名前>/`) の両方に内側の skill がある。平らな置き場を決め打ちしたパスは、開発機では解決するが配置の違う配布先では解決しない。それでも検査を通る。

作業ツリーの写しで再現した。`commit-and-pr-message` の配下に、内側の skill 名で決め打ちした行 (`~/.claude/skills/commit-and-pr-message/scripts/...`) を持つファイルを置くと「違反なし」になる。走査したファイルの数は置く前より1本増えており、置いたファイルは読まれている。対照として plugin 名で決め打ちした行 (`~/.claude/skills/dev-workflow/skills/commit-and-pr-message/scripts/...`) に変えると違反1件になる。`in-repo-issue` の名前で決め打ちした行も素通りした。

レビューが出した手当ての案は、内側の skill の名前もパッケージ名の集合へ加え、変異注入で内側の名前の形が赤になることを確かめること。

### 2. skill のディレクトリを指す変数に触れる散文が、読み込み時の置換で壊れる (B-15 / D-7)

Skill ツールで読み込んだ本文では、`CLAUDE_SKILL_DIR` の変数がコードブロックの外でも絶対パスへ置換される (ISSUE-58の spec の前提 8)。変数の振る舞いを説明する散文は、置換のあとで意味を失い、ホームディレクトリを含む絶対パスが本文に載る。Read で読んだ本文では置換されず、Bash の環境変数にも無い (同じく前提 8) ので、配布元で SKILL.md を読んでも気づけない。

作業ツリーの `in-repo-issue` の SKILL.md では、「初期化」節の `issue-id.py` をプロジェクトへ配る理由の段落と、A.1の「`${NEXT}` が空になったら」の段落が、散文の中で変数の名前に触れている。2026-09-24に Skill ツールで `dev-workflow:in-repo-issue` を読み込むと、この2箇所はどちらも変数の名前の部分が絶対パスに置き換わっていた (読み込まれたのは pin された版だが、この2段落の文面は作業ツリーと同じ)。A.1の段落は「<絶対パス> が未設定だとパスが /scripts/issue-id.py になる」という偽の文になる。

同じ形が `skills/tooling/markdown-to-pdf/SKILL.md` の「コマンド」節にもある。コードブロックの直後の段落が、散文の中で変数の名前に触れ、読み込み時に絶対パスへ置換されるという振る舞いそのものを説明している。計画レビューの B-15は markdown-to-pdf でも散文の置換を観測しており、ISSUE-58の Task 5のレビューでも Skill ツールでの読み込みで再現した。置換のあとは「<絶対パス> はこのファイルが読み込まれる時点で実際の skill ディレクトリの絶対パスへ置換される」という意味の通らない文になる。`plugins/` と `skills/` の追跡下の Markdown 33本をコードブロックの外だけ行で走査すると、`CLAUDE_SKILL_DIR` が散文に現れるのは、ここまでに挙げた3箇所だけだった。

未確認の同型の候補が2つある。plugin の root を指す `CLAUDE_PLUGIN_ROOT` の変数を散文で名指して、その振る舞いを説明している箇所で、`plugins/dev-workflow/skills/issue-scoped-artifacts/SKILL.md` の「language: fail を選ぶ理由」節の箇条 (変数がシェルに export されないことの説明) と、`plugins/security-blue-red-team/SKILL.md` の「schema の所在」節 (root のこのファイルでは変数が展開されないことの説明) である。読み込み時に置換されるかは、ISSUE-58のレビューでは確かめていない。同じ走査では `agents/` と `commands/` の本文にもこの変数が現れるが、どれもパスとして使う箇所で、変数の振る舞いを説明する散文ではない。

レビューが出した手当ての案は、散文では変数の名前を書かず (「skill のディレクトリを指す変数」のように言い換える)、コードブロックの呼び出しだけに置くこと。`commit-and-pr-message` の SKILL.md は ISSUE-58でこの形にしてある (ISSUE-58の plan の Global Constraints)。コードブロックの外に変数の名前が現れることは行の走査で拾える形なので、タスクの2つ目 (機械検査へ落とせる部分) の候補になる。
