# fix: git commit -v の scissors 以降の diff で記法検査が偽陽性になる

## 背景

`git commit -v` はコミットメッセージのテンプレートに scissors 行 (`>8`) を置き、その下へ
staged diff を貼る。git 自身はこの部分をコミットしないが、commit-msg hook へ渡るファイルには
そのまま載っている。`issue-id.py --check-text` は渡されたテキスト全体を走査するので、
**diff に映っただけの数字記法でコミットが止まる**。

止まる対象には、追跡ファイルとして走査したなら免除される側 (コードフェンス内・インライン
コード内・`.css` 等) も含まれる。つまり「その内容自体は規約違反ではない」ものが違反として
報告される。

### 実測

隔離した空リポジトリに commit-msg hook を置いて再現した。同じ内容を 3 つの経路で見ている。

| 観測 | 結果 |
|---|---|
| 対照: 数字記法をフェンス内に持つ追跡ファイルへ `--check-text` | 7 行走査 / 違反 0 件 (rc 0) |
| その 1 ファイルを `git commit -v` (エディタ経路) | hook rc 1 / 26 行走査 / 違反 1 件 (25 行目) |
| hook を外して同じコミット | rc 0。記録されたメッセージは subject 1 行のみ (`diff --git` は 0 件) |
| そのメッセージファイルへ `git stripspace --strip-comments` | diff が残る (数字記法 1 件) |

subject には数字記法を一切書いていない。違反として報告された 25 行目は diff の中身である。
最後の 2 行が示すのは、**git 自身がコミットに含めない部分で hook が赤くなっている**こと、
そしてコメント行の除去だけでは落ちないこと (scissors 以降の切り落としは別のステップ) である。

### 今すぐの実害は無い。配布先では違う

本リポジトリの規約は本文をファイルに書いて `-F` で渡す形で、`-m` / `-F` の経路にはこの面が
無い。開発機の設定も実測で `commit.verbose` / `commit.template` / `core.hooksPath` /
`core.commentChar` がいずれも未設定 (`git config --get` が rc 1) なので、既定では踏まない。

しかし **この skill は他プロジェクトへ配布される**。`commit.verbose` を有効にしている
プロジェクトや、`-v` を手で打つ人がいる環境では初回のコミットで踏む。

そして偽陽性のコストは「一度赤くなる」では終わらない。**説明のつかない赤は `--no-verify` の
常用を招き、機構ごと死ぬ**。commit-msg stage の hook は他に検査を持たない単独の防衛層なので、
迂回が習慣になった時点で surface 全体が無検査に戻る。

### 現状の記述との関係

`.pre-commit-config.yaml` の `issue-id-notation-commit-msg` hook のコメントは、この挙動を
既に「既知の限界」として記述し、「潰すには git の cleanup 規則を hook 側で再実装することに
なり二重管理と引き換えになるため採っていない」と結論している。

本 Issue はその結論を見直す。**再実装が要るのは cleanup 規則の全体ではなく scissors 行以降の
切り落としだけ**で、コメント行の除去 (`--check-text` が拾っても違反にならない部分) は
巻き取らなくてよい。範囲を絞れば二重管理のコストは小さくなる。
