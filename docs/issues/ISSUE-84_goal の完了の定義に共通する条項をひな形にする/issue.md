# agent: /goal の完了の定義に共通する条項をひな形にする

## 背景

ISSUE-81 と ISSUE-82 は、Claude Code の `/goal` に貼る完了の定義を本文に持つ。`/goal` の判定役は会話に出た出力しか読まずツールも呼ばないので、条件文は自己完結させる必要がある。そのため、証拠の出し方 (rc の表示、ログの抜き方)、3 通りの終わり方、「未完了:」の目印、公開面に載せない形、といった条項を 2 本がそれぞれ持っている。起票の PR の中で、同じ条項を 2 本で歩調を揃えて直す手間が既に起き、片方にだけ入った条項 (Bash のタイムアウト、`docker run` に `-t` を付けない) も出た。

判定役は条件文の外を読まないので、canonical は参照先ではなく貼るためのひな形になる。置き場は dev-workflow の component skill が候補になる。in-repo-issue やその Issue テンプレートは、`/goal` を使わない配布先にも届くので向かない。

事例はまだ 2 本で、起票の時点ではどちらも実行していなかった (ISSUE-81 は 2026-09-28 に実行した。下の節)。一度も走っていない条項を canonical にしないため、ISSUE-81 を `/goal` で回した結果を見てから着手する。

## ISSUE-81 の実行から拾った材料 (2026-09-28、実行役の側)

判定役の側 (各条項を判定役がどう判定したか) は、`/goal` が終わった後でないと分からないので、ここにはまだ無い。

- 条件 3 の「ログに postinstall script did not run が無い」は、その文言がどこかに実在することを示す対照を求めていなかった。実行役は registry の tarball を読む対照を足した。一方、コンテナの中で回したもう 1 つの対照 (astgrep-marker.sh) は、文言を持つ唯一のファイルを除外していて判別力が無かった。これはマージ前ゲートに足した一次資料との突き合わせで見つかった。0 件を条件にする条項は、対照を置くことと、その対照が判別できることまで条件に書く候補になる
- スクリプトの rc で段の成否を示すとき、rc が何を覆うかを条件は決めていなかった。ISSUE-81 の stage1.sh の rc が見たのは、前提の項目のうち 3 つだけだった。`pnpm store path` の rc は終了コードに反映せず、取れなかったときも rc=0 になりうる形だった
- 「pnpm はネットワーク無しでも起動できる形にする」は、手段を指定していなかった。実行役は pnpm 12.3.4 の配られ方を調べ、`@pnpm/exe.<platform>` の tarball を integrity で照合して置いた。取得と照合を共通化した `scripts/ci/download-and-verify.sh` はあるが、契約が sha256 だけなので使っていない。そのスクリプトが付ける `--proto '=https' --tlsv1.2` も、Dockerfile には付いていない。ひな形が取得の段を持つなら、このスクリプトを sha512 へ広げて参照するかを決める材料になる
- 「ホスト側のパスは $PWD で書き、$(...) を使わない」は射程が曖昧だった。実行役は、コンテナの中のスクリプトでもコマンド置換を避け、一時ファイルと `read` を往復させた。一方で、Bash 呼び出しの先頭の `cd` にはホストの絶対パスを書いていた。公開面に載せた記録 (ISSUE-81 の結果節) では、ホスト側のパスを相対パスか $PWD で書いた
- 完了の定義の外で実行役が足したもの: 結果節の記録をマージ前ゲートで、一次資料と突き合わせるレーンに通した。別々の観測を 1 つの因果に結んだ記述 (上の astgrep-marker.sh の件) と、tarball の中身の不正確な記述が、そこで見つかった
