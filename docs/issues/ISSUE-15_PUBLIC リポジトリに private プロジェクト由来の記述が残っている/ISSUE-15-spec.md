# ISSUE-15 spec: private 由来の記述の流入を止める検査の設計

ISSUE-15 のタスクのうち、修正済みの 2 件を除く 6 件を対象とする設計。実装計画は
`ISSUE-15-plan.md` が持つ。

## 前提 (すべて実測)

設計の形はこの 4 つで決まっている。

**push は取り消せない。**このリポジトリは PUBLIC なので、push した時点で公開される。ISSUE-15 の
「既知の限界」が述べているとおり、現在のツリーを直しても過去のコミットと closed PR の diff は
公開のまま残る。したがって回復できるのは「これから読む人が見る状態」だけである。

**CI は防御層にならない。**main は保護されていない (classic branch protection が 404、repository
ruleset が空。両系統を確認した)。CI は push 後に走るので、CI が露出を見つけた時点で既に GitHub 上に
ある。CI の役割は「防ぐ」ではなく「気づく」である。

**唯一の push 前の関門は pre-commit である。**上の 2 つから従う。`--no-verify` で回避できる点も
含めて、この層の性質を理解した上で設計する。

**現行ルールは対象カテゴリを 1 件も見ていない。**対照ファイル (271 バイト) に UUID の大小両方、
内部 TLD を持つホスト名、URL、メールアドレス、ビルドターゲット名を並べて現行の `.gitleaks.toml` へ
通したところ `no leaks found` を返した。同じファイルにユーザー名を含むパスを 2 行足すと
`leaks found: 2` になったので、走査器は生きたまま該当カテゴリだけを素通ししている。

## 流入経路

想定する経路は 3 つである。

1. private プロジェクトから skill を新規に切り出すとき
2. 別セッションのエージェントがこのリポジトリへ書くとき
3. コミットメッセージと PR 本文 (tree の外)

**経路 2 があるため、手順だけでは止まらない。**手順を踏まない主体が書けるので、機械検査が要る。
逆に経路 1 は手順の入口が明確なので、機械化できない判定をそこへ載せられる。

## 走査面

実際に使っている面だけを走査面にする。使っていない面に機構を作ると、維持されないまま緑を出す。

| 面 | 実測 | 扱い |
|---|---|---|
| 追跡ファイル | 既に gitleaks がある | 層 1 と層 2 で見る |
| コミットメッセージ | 検査なし | 層 2 の commit-msg surface で見る |
| PR タイトル・本文 | 検査なし | 手順の中で層 2 を呼ぶ |
| ブランチ名 | 過去 17 件に露出なし | 機構を作らない。層 3 で扱う |
| 注釈付きタグ | 0 件 | 使い始めたときに決める |
| git notes | 0 件 | 使い始めたときに決める |

ブランチ名に機構を作らないのは、`default_install_hook_types` に stage を 1 つ増やす代償に対して
実績が 0 件だからである。タグと git notes も同じ理由で、決めたことだけを記録して機構は作らない。

## 3 層に分ける

露出のカテゴリは機械検査との相性で 3 段階に分かれる。層ごとに置き場所を変えるのは、自己言及の
制約が層 2 にだけかかるためである。

### 層 1: 形が決まっているもの

禁止語を必要としないので、ルールを PUBLIC な設定ファイルへ書ける。pre-commit と CI の両方で走る。

`.gitleaks.toml` に 2 つのルールを足す。

- **UUID**。ISSUE-15 の実測で VM の UUID が 2 件出ていた。許可側は schema の example と、仕様上
  固定の値 (nil UUID 等)。大小の揺れは一度取りこぼした実績があるので、ケースを両方置く
- **メールアドレス**。CLAUDE.md が MUST で禁じているのに現行ルールが 1 件も見ていない。許可側は
  RFC 2606 の予約ドメイン

**ホスト名は層 1 に入れない。**内部 TLD は標準的な用途を持つので、形だけで捕捉すると一般的な
説明文まで拾う。実際の露出は「プロジェクト名 + 内部 TLD」の形だったので、固有名詞側を層 2 で
持てば捕捉できる。形が決まっているように見えても、区別に必要な情報が固有名詞側にあるなら
層 2 の仕事である。

### 層 2: 固有名詞

禁止語が要る。PUBLIC な設定ファイルへ literal で書くとルールファイル自身が露出になるので、
リストをリポジトリの外に置く。

置き場所は環境変数で指定し、挙動を 3 分岐にする。

| 状態 | 挙動 |
|---|---|
| 環境変数が未設定 | skip する |
| 環境変数あり、ファイルあり | 検査する |
| 環境変数あり、ファイル無し | 非 0 で止まる |

無条件の fail-closed を採らないのは、このリポジトリが PUBLIC で第三者が clone するためである。
第三者の pre-commit が、その人と無関係な理由で常に赤くなる形は採れない。「設定した人には
fail-closed、設定していない人には無関係」という形にする。

走査面は追跡ファイル全体とコミットメッセージの 2 つ。入口を 2 つ持つ形は `issue-id.py` の
`--check` / `--check-text` に先例がある。staged 差分ではなく追跡ファイル全体を見るのは、新規の
流入だけでなく既存の見落としも対象にするため。ファイル数は 3 桁未満なので全走査でも速い。

照合は**大小を無視した部分一致**で行う。大小を区別すると取りこぼす。ISSUE-15 は小文字だけで
数えて 3 ファイルを落とし、その教訓を本文へ書いている最中に大文字の UUID を取りこぼしている。
単語境界での照合を採らないのは、対象が日本語混じりのテキストで境界が定義できないためである。
部分一致は誤検出を増やすが、禁止語リストは手で管理するので、誤検出が出る語はリストから外せる。

**検出結果に禁止語そのものを出力しない。**出力するのはファイル名と行番号と、リスト内での位置
だけにする。禁止語を表示すると、その出力が端末の履歴や CI のログへ残り、露出を防ぐための検査が
露出の経路になる。`gitleaks` が `--redact` で同じ配慮をしている。

### 層 3: 読解を要するもの

逐語引用、断定形の運用記述、他リポジトリの運用史、組織を前提にした語。機械検査では判定できない。

`skills/meta/` に新しい skill を作り、次の 3 つを持たせる。

1. 切り出し時のチェックリスト
2. **「例なのか実運用なのか」の判定基準**
3. 層 1 と層 2 の検査を呼ぶ手順

2 を入れるのは実際に踏んだためである。ISSUE-15 のスイープは通知手段への言及 2 件を「実際こう
していると読める」と報告したが、実物は例の列挙の一員だった (経緯は ISSUE-23 が持つ)。**同じ
固有名詞が出ていても、例として置かれているのか実運用の記述なのかで判定が逆になる。**この
見分け方は機械検査には原理的に持てない。

CLAUDE.md にはポインタだけを置く。CLAUDE.md は常時ロードされ、そのコストは session_start だけ
でなく subagent の起動ごとにかかる。判断基準は `context-loading-mechanics` skill が持つ。

## テスト

各層とも「検出すべき例」と「許可すべき例」の両方を先に書いてから実装する。

層 1 のケースは `scripts/check-leak-guard-rules.py` へ追加する。この検査は pre-commit と CI の
両方に既に取り付いているので、新しい配線は要らない。許可側を並べるのは CLAUDE.md の MUST で
あると同時に、このリポジトリには**許可側の対照が無かったせいで誤検出を入れかけた実績**がある。

層 2 のテストは、禁止語リストを固定値で与えた状態で検出と許可の両方を見る。テスト内の禁止語は
テスト用の架空語にする。実際の禁止語をテストへ書くと、テストファイル自身が露出になる。同型の
問題を `check-leak-guard-rules.py` が既に解いており、そちらはユーザー名を変数で組み立てている
(literal で書いて 13 件検出された経緯がコメントに残っている)。

## 実装順序

層は独立に取り付けられるので、価値の出る順に並べる。

1. 層 1 のルールと対照ケース
2. 層 2 の追跡ファイル surface
3. 層 2 の commit-msg surface
4. 層 3 の skill
5. PR 本文の検査を `commit-and-pr-message` skill の手順へ組み込む

## 既知の限界

**層 2 は自分の取り付けを自分では検査できない。**開発機で環境変数を設定し忘れると静かに skip し、
pre-commit は緑になる。ISSUE-15 が繰り返し踏んだ「0 件 = 見ていない」がそのまま当てはまる。
セットアップ手順に有効性を確認するコマンドを置くが、それを実行し忘れる面は残る。

**禁止語リストの網羅性は誰も保証しない。**リストに無い固有名詞は層 2 を素通りする。層 3 の
チェックリストが最後の網になるが、こちらは人の読解に依存する。

**`--no-verify` で層 1 と層 2 の両方を回避できる。**pre-commit を通さない経路が残る以上、
push 前の関門は完全ではない。CI が全履歴を走査するので気づけるが、その時点で既に公開されている。

**ハッシュ化案は採らない。**禁止語の sha256 だけをリポジトリへ置けば PUBLIC でも配れて CI でも
走るが、固有名詞は元の値のエントロピーが低く、辞書攻撃で復元できる。salt を同じリポジトリへ
置くなら意味がない。「ハッシュだから安全」は元の値に十分なエントロピーがある場合にだけ
成り立つ性質である。
