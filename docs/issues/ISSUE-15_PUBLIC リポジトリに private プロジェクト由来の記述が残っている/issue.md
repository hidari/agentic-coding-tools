# fix: PUBLIC リポジトリに private プロジェクト由来の記述が残っている

## 背景

このリポジトリは PUBLIC で、CLAUDE.md が次を MUST にしている。

> private リポジトリの内部事情 (未公開の設計、社内固有の運用) を書かない。一般化できる
> 知見だけを、出所を伴わない形で書く

skill の多くは private プロジェクトでの実運用から一般化して切り出したものなので、切り出しの
過程で出所が残った箇所がある。ISSUE-14 の作業中に、新しく書いた Issue 本文へ同種の記述を
入れかけたことをきっかけに発見した (そちらは push 前に落とした)。

本 Issue が扱うのは**既にマージ済みで公開されている分**である。

## 実測 (2026-08-16)

追跡下 85 ファイルのうち 5 ファイル、計 7 箇所。重さは一様ではない。

| ファイル | 件数 | 何が露出しているか |
|---|---|---|
| `plugins/dev-workflow/skills/e2e-scenario-impact-check/SKILL.md` | 2 | private リポジトリの CLAUDE.md を**逐語で引用**している |
| `plugins/dev-workflow/skills/pre-merge-quality-gate/SKILL.md` | 2 | プロジェクト名 + 内部コンポーネント名 + Makefile の実ターゲット名 |
| `plugins/security-blue-red-team/skills/security-blue-team/SKILL.md` | 1 | プロジェクト名 + 運用モードの名前 |
| `plugins/web-monkey-qa/README.md` | 1 | ローカル開発用ホスト名 (プロジェクト名由来) |
| `plugins/web-monkey-qa/schemas/tests/findings.schema.test.mjs` | 1 | 同じホスト名 (テストの fixture) |

最も重いのは 1 番目で、private リポジトリの内部ポリシー文がそのまま読める。2 番目は
プロジェクト名に加えて別の内部コンポーネント名も含む。

## 検査が捕捉しなかった理由

**`gitleaks` は全 hook 緑のままこれらを通している。** 誤りではなく設計どおりで、検出集合の
canonical は `.gitleaks.toml` にあり、プロジェクト名・リポジトリ名・ホスト名はそこに無い
カテゴリだからである。CLAUDE.md 自身が「gitleaks の緑を安全の根拠にしない」と警告している
とおりの形で起きた。

発見の経路も偶然だった。ISSUE-14 のレビューが「参照に使った owner 名が未検証」と指摘し、
確認しに行った先で visibility が PRIVATE だと分かった。owner 名を検証していなければ
気づかずに push していた。

**数え方でも一度取りこぼした。**最初は小文字で検索して 2 ファイルと数えたが、3 ファイルは
大文字始まりで書かれていた。case を無視して数え直すと 5 ファイルだった。

## 走査面が追跡ファイルに限定されていた (2026-08-22)

ISSUE-14 の最終レビューで、**未 push のコミットメッセージ 2 件**に private リポジトリの
内部事情 (リポジトリ名・向こうの Issue 番号・向こうの Issue タイトル) が残っていることが
見つかった。push 前に message-only の書き換えで潰してあり、書き換えの前後で対象 17 コミット
すべての tree がペアごとに一致することを確認している (内容は 1 バイトも変わっていない)。

**教訓は「消し忘れが 2 件あった」ではなく、走査面の取り方にある。**それまでの PUBLIC scrub は
対象を「追跡ファイル」に限定していた。**git が公開するのは tree だけではない**ので、tree しか
見ない scrub は面が 1 つ増えるたびに同じ穴を再生産する。

`gitleaks` はコミットメッセージも走査するが、リポジトリ名は検出集合に無いカテゴリなので緑の
まま通す。上の「検査が捕捉しなかった理由」とまったく同じ機序が、tree ではない面で起きた。

したがってこの Issue のスコープには「どこまでを走査面にするか」を決めることが入る。tree の
外で git が公開する面は他にもある (注釈付きタグのメッセージ、ブランチ名、`git notes` など)。
列挙は網羅ではないので、決めるときは列挙を作るのではなく**どの面を実際に数えたか**で判定する。

**この面は push 前にしか直せない。**push 済みのコミットメッセージを書き換えるとハッシュが
変わり、既存の参照がすべて外れる。下の「既知の限界」が tree について述べているのと同じ制約が、
メッセージにはより強い形でかかる。

## 設計上の問い

単に消すだけだと同じことが繰り返される。次を決める必要がある。

1. **消すのか、一般化するのか。** 引用は「一般化できる知見」を支える根拠として置かれている。
   出所を落とすと根拠が弱くなる箇所があるので、記述ごとに判断が要る
2. **検査に落とせるか。** `.gitleaks.toml` に custom rule を足せば機械的に捕捉できる。
   ただし禁止する固有名詞をこの PUBLIC リポジトリの検査ルールに literal で書くと、
   **ルールファイル自身が露出になる**。この自己言及をどう解くかが設計の中心
3. **今後の流入をどこで止めるか。** skill を private プロジェクトから切り出すときが
   流入点なので、切り出しの手順側に検査を置くほうが効く可能性がある

`Home` は `/Users/<name>` から `/Users/example` へ置換済みだったので、**過去にパスだけを
走査面にして識別子を残した**形になっていた。

fixture の識別子は置換しても検査力が落ちないことを確認してから替えた。docstring が保とうと

付きの `Home`) であって識別子ではない。代替名には空白を残した。名前に空白が入ることを前提に

逐語引用は出所を落として「こういう規定を持つプロジェクトで噛み合う」の一般形へ書き換えた。
引用が支えていた知見自体は一般的な内容なので、出所を落としても根拠は弱くならない。

fixture を書き換えても schema のテストは通る (findings 10 件 / cleanup-queue 7 件)。
`url` / `signal` / `repro_steps` に format 制約が無く、テストが値そのものを pin していないため。
なお `url` に format 制約が無いこと自体は既存の穴だが、この Issue の範囲外。

個人名 1 件は skill の動作説明の中で特定個人を判断者として名指ししていたもの。配布先の
利用者にとって意味をなさないので一般化した。LICENSE の著作権表示・`plugin.json` の author・
`<owner>/<repo>` のリポジトリ参照にある同じ名前は、公開された識別子としての正当な用途なので

### 走査面を 4 回漏らした

これがこの作業でいちばん重い結果である。

| 回 | 走査の形 | 出した結果 | 実際に見つけた経路 |
|---|---|---|---|
| 1 | 4 パターン (プロジェクト名の語幹 / ホスト名 / API パス / 日本語 UI ラベル) | 0 件・陽性対照 True | レビューが全文を読んで 3 箇所 |
| 2 | 走査語を広げた | 0 件・陽性対照 True | 自分で読み直して 2 箇所 |
| 3 | 6 パターンへ拡張 | 0 件・陽性対照 True | 全文スイープが 14 件 |
| 4 | `sed` による一括置換 | 置換完了 | テストが赤くなって残存 2 件 |

1 回目が漏らしたのは、API パスを `/api/v\d+/<ドメイン語>` の形で書いたため、同じ語を
ハイフン付きの識別子として使う書き方に届かなかったこと。

3 回目が漏らしたのは、VM 名・UUID・他リポジトリの CI 参照・書き手のメモ置き場パスという、
どのパターンにも入れていなかったカテゴリ。**語を知らないものには、どんなパターンも届かない。**

4 回目は 2 つの取りこぼしが同時に出た。大文字で書かれた UUID リテラル (`sed` が大小を
区別するため) と、リスト形式で分割された文字列 (`["cargo", "xtask", "check-*"]` は連続
文字列としてマッチしない)。**この Issue 自身が「大文字小文字を無視した再計測」を教訓として
挙げているのに、それを直している最中に踏んだ。**

**陽性対照は走査器が生きていることしか示さず、走査面が十分かは何も示さない。**
1〜3 回目はすべて「0 件 + 陽性対照 True」という、手続きとしては完璧に見える緑を出している。

### 捕まったのは検査層のあるものだけだった

4 回目の 2 件はテストが赤くして教えた。コードには検査層があるからである。1〜3 回目の漏れは
すべてドキュメントとコメントで、そこには検査層が無い。同じ取りこぼしが静かに残る。

この非対称は「## 設計上の問い」の 3 番目 (今後の流入をどこで止めるか) に効く。コードへ
混入した固有値はテストが捕まえうるが、散文へ混入したものは何も捕まえない。散文の側にこそ
検査が要る、という順序になる。

### 検索キーは外側から機械的には作れない (射程に注意)

「## 設計上の問い」の 2 番目 (検査に落とせるか) への入力。実測で分かったのは 3 つ。

- **ディレクトリ名をそのまま検索キーにしても届かない。**文書中の表記はディレクトリ名の語幹
  だけで、`\b<ディレクトリ名>\b` ではマッチしない
- **機械的に語幹へ割ると偽陽性の山になる。**開発機のディレクトリ名 32 件をそのままキーにした
  走査は 280 件と 18 件の偽陽性を返した。一般名詞がディレクトリ名になっているため。件数が
  多いぶん「情報のある結果」に見えるので、キーの質を疑わないと本物が偽陽性に埋もれる
- **内部コンポーネント名は外側から列挙できない。**落とした 2 出現はプロジェクト内部の
  コンポーネント名で、開発機のどのディレクトリ名にも現れない。ディレクトリ構造を定義元に
  する方法では原理的に届かない

**ただしこの結論の射程は「キーの列挙から regex を導出する」方向に限る。**上の 3 箇所は
全文を読んで見つかったもので、どのキーリストからも出てこない。全文レビューはキーを必要と
しないので、3 つの理由のどれにも当たらない。「機械的にキーを作れない」を「自動検出は
不可能」と読むと、実際に機能した手段を捨てることになる。

検出の候補は少なくとも 2 系統ある。regex による走査 (キーの入手が未解決) と、触ったファイル
または全追跡ファイルの全文レビュー (キーが要らない代わりに毎回コストがかかる)。後者は今回
2 回とも前者を上回った。

## 既知の限界

- **履歴からは消せない。**現在のツリーを直しても、過去のコミットと closed PR の diff は
  公開のまま残る。本 Issue が回復できるのは「これから読む人が見る状態」だけである
- 同じカテゴリの棚卸しが別リポジトリでも進行中で、そちらと重複しうる
