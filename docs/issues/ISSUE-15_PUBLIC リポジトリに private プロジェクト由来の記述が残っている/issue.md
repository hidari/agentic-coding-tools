# fix: PUBLIC リポジトリに private プロジェクト由来の記述が残っている

## 背景

このリポジトリは PUBLIC で、CLAUDE.md が次を MUST にしている。

> private リポジトリの内部事情 (未公開の設計、社内固有の運用) を書かない。一般化できる
> 知見だけを、出所を伴わない形で書く

skill の多くは private プロジェクトでの実運用から一般化して切り出したものなので、切り出しの
過程で出所が残った箇所がある。ISSUE-14 の作業中に、新しく書いた Issue 本文へ同種の記述を
入れかけたことをきっかけに発見した (そちらは push 前に落とした)。

本 Issue が扱うのは**既にマージ済みで公開されている分**である。

## 実測 (2026-08-16)

|---|---|---|
| `plugins/dev-workflow/skills/e2e-scenario-impact-check/SKILL.md` | 2 | private リポジトリの CLAUDE.md を**逐語で引用**している |

## 検査が捕捉しなかった理由

**`gitleaks` は全 hook 緑のままこれらを通している。** 誤りではなく設計どおりで、検出集合の
canonical は `.gitleaks.toml` にあり、プロジェクト名・リポジトリ名・ホスト名はそこに無い
カテゴリだからである。CLAUDE.md 自身が「gitleaks の緑を安全の根拠にしない」と警告している
とおりの形で起きた。

発見の経路も偶然だった。ISSUE-14 のレビューが「参照に使った owner 名が未検証」と指摘し、
確認しに行った先で visibility が PRIVATE だと分かった。owner 名を検証していなければ
気づかずに push していた。

**数え方でも一度取りこぼした。**最初は小文字で検索して 2 ファイルと数えたが、3 ファイルは
大文字始まりで書かれていた。case を無視して数え直すと 5 ファイルだった。

## 走査面が追跡ファイルに限定されていた (2026-08-22)

ISSUE-14 の最終レビューで、**未 push のコミットメッセージ 2 件**に private リポジトリの
内部事情 (リポジトリ名・向こうの Issue 番号・向こうの Issue タイトル) が残っていることが
見つかった。push 前に message-only の書き換えで潰してあり、書き換えの前後で対象 17 コミット
すべての tree がペアごとに一致することを確認している (内容は 1 バイトも変わっていない)。

**教訓は「消し忘れが 2 件あった」ではなく、走査面の取り方にある。**それまでの PUBLIC scrub は
対象を「追跡ファイル」に限定していた。**git が公開するのは tree だけではない**ので、tree しか
見ない scrub は面が 1 つ増えるたびに同じ穴を再生産する。

**`gitleaks` はコミットメッセージを走査しない** (8.30.1 で実測。同じ 2 つの文字列をメッセージ側
とファイル内容側に置いた対照で、検出されるのは内容側だけ。走査バイト数もファイル内容の合計と
一致し、メッセージ由来は 1 バイトも含まれない)。当初この節は「走査するがリポジトリ名は検出集合
に無いカテゴリなので通す」と書いていたが、それは誤りだった。上の「検査が捕捉しなかった理由」と
機序が違い、こちらは**面ごと見ていない**。したがって `.gitleaks.toml` にルールを足してもこの面
は塞がらず、commit-msg surface を別立てで用意する必要がある (spec の「走査面」表が正しい)。

したがってこの Issue のスコープには「どこまでを走査面にするか」を決めることが入る。tree の
外で git が公開する面は他にもある (注釈付きタグのメッセージ、ブランチ名、`git notes` など)。
列挙は網羅ではないので、決めるときは列挙を作るのではなく**どの面を実際に数えたか**で判定する。

**この面は push 前にしか直せない。**push 済みのコミットメッセージを書き換えるとハッシュが
変わり、既存の参照がすべて外れる。下の「既知の限界」が tree について述べているのと同じ制約が、
メッセージにはより強い形でかかる。

## 設計上の問い

単に消すだけだと同じことが繰り返される。次を決める必要がある。

1. **消すのか、一般化するのか。** 引用は「一般化できる知見」を支える根拠として置かれている。
   出所を落とすと根拠が弱くなる箇所があるので、記述ごとに判断が要る
2. **検査に落とせるか。** `.gitleaks.toml` に custom rule を足せば機械的に捕捉できる。
   ただし禁止する固有名詞をこの PUBLIC リポジトリの検査ルールに literal で書くと、
   **ルールファイル自身が露出になる**。この自己言及をどう解くかが設計の中心
3. **今後の流入をどこで止めるか。** skill を private プロジェクトから切り出すときが
   流入点なので、切り出しの手順側に検査を置くほうが効く可能性がある

### 走査面を 4 回漏らした

これがこの作業でいちばん重い結果である。

| 回 | 走査の形 | 出した結果 | 実際に見つけた経路 |
|---|---|---|---|
| 1 | 4 パターン (プロジェクト名の語幹 / ホスト名 / API パス / 日本語 UI ラベル) | 0 件・陽性対照 True | レビューが全文を読んで 3 箇所 |
| 2 | 走査語を広げた | 0 件・陽性対照 True | 自分で読み直して 2 箇所 |
| 3 | 6 パターンへ拡張 | 0 件・陽性対照 True | 全文スイープが 14 件 |
| 4 | `sed` による一括置換 | 置換完了 | テストが赤くなって残存 2 件 |

1 回目が漏らしたのは、API パスを `/api/v\d+/<ドメイン語>` の形で書いたため、同じ語を
ハイフン付きの識別子として使う書き方に届かなかったこと。

3 回目が漏らしたのは、VM 名・UUID・他リポジトリの CI 参照・書き手のメモ置き場パスという、
どのパターンにも入れていなかったカテゴリ。**語を知らないものには、どんなパターンも届かない。**

4 回目は 2 つの取りこぼしが同時に出た。大文字で書かれた UUID リテラル (`sed` が大小を
区別するため) と、リスト形式で分割された文字列 (`["cargo", "xtask", "check-*"]` は連続
文字列としてマッチしない)。**この Issue 自身が「大文字小文字を無視した再計測」を教訓として
挙げているのに、それを直している最中に踏んだ。**

**陽性対照は走査器が生きていることしか示さず、走査面が十分かは何も示さない。**
1〜3 回目はすべて「0 件 + 陽性対照 True」という、手続きとしては完璧に見える緑を出している。

### 捕まったのは検査層のあるものだけだった

4 回目の 2 件はテストが赤くして教えた。コードには検査層があるからである。1〜3 回目の漏れは
すべてドキュメントとコメントで、そこには検査層が無い。同じ取りこぼしが静かに残る。

この非対称は「## 設計上の問い」の 3 番目 (今後の流入をどこで止めるか) に効く。コードへ
混入した固有値はテストが捕まえうるが、散文へ混入したものは何も捕まえない。散文の側にこそ
検査が要る、という順序になる。

### 検索キーは外側から機械的には作れない (射程に注意)

「## 設計上の問い」の 2 番目 (検査に落とせるか) への入力。実測で分かったのは 3 つ。

- **ディレクトリ名をそのまま検索キーにしても届かない。**文書中の表記はディレクトリ名の語幹
  だけで、`\b<ディレクトリ名>\b` ではマッチしない
- **機械的に語幹へ割ると偽陽性の山になる。**開発機のディレクトリ名 32 件をそのままキーにした
  走査は 280 件と 18 件の偽陽性を返した。一般名詞がディレクトリ名になっているため。件数が
  多いぶん「情報のある結果」に見えるので、キーの質を疑わないと本物が偽陽性に埋もれる
- **内部コンポーネント名は外側から列挙できない。**落とした 2 出現はプロジェクト内部の
  コンポーネント名で、開発機のどのディレクトリ名にも現れない。ディレクトリ構造を定義元に
  する方法では原理的に届かない

**ただしこの結論の射程は「キーの列挙から regex を導出する」方向に限る。**上の 3 箇所は
全文を読んで見つかったもので、どのキーリストからも出てこない。全文レビューはキーを必要と
しないので、3 つの理由のどれにも当たらない。「機械的にキーを作れない」を「自動検出は
不可能」と読むと、実際に機能した手段を捨てることになる。

検出の候補は少なくとも 2 系統ある。regex による走査 (キーの入手が未解決) と、触ったファイル
または全追跡ファイルの全文レビュー (キーが要らない代わりに毎回コストがかかる)。後者は今回
2 回とも前者を上回った。

## 既知の限界

- **履歴からは消せない。**現在のツリーを直しても、過去のコミットと closed PR の diff は
  公開のまま残る。本 Issue が回復できるのは「これから読む人が見る状態」だけである
- 同じカテゴリの棚卸しが別リポジトリでも進行中で、そちらと重複しうる

## 設計

残タスク 6 件の設計は [ISSUE-15-spec.md](ISSUE-15-spec.md) が持つ。露出のカテゴリを
機械検査との相性で 3 層に分け、層ごとに置き場所を変える形になっている。層 1 が形の
決まっているもの (`.gitleaks.toml` に置ける)、層 2 が固有名詞 (禁止語リストをリポジトリの
外に置く)、層 3 が読解を要するもの (`skills/meta/` の skill)。

着手の順序は spec の「## 実装順序」が持つ。**層 1 と層 2 は入った** (下の適用節)。
残っているのは層 3 の skill と、PR 本文の検査を `commit-and-pr-message` skill の手順へ
組み込む分。次に触る人は spec を読んでから層 3 に着手すれば良い。

## 適用: 層 1 (2026-09-10)

`.gitleaks.toml` へ `vm-uuid` と `email-address` を足し、対照を
`scripts/check-leak-guard-rules.py` へ入れた。ハーネスは 1 ルール前提だったので複数ルールへ
広げてある。検出側は対象ルールで絞り、許可側はルールを問わず見る非対称にした。前者は別ルールに
拾われて壊れたルールが隠れる形を、後者は対象外のルールが撃ってコミットが止まる形を落とす。

対照の件数はここへ書かない。canonical は `scripts/leak-guard-cases-manifest.txt` で、増減は
その diff に現れる。変異注入で全部が狙った機構を通って赤くなること、注入後に対象 3 ファイルが
sha256 一致で無傷であることを確かめている。

**対照が痩せたことは対照自身には見えない**ので、pin を 2 段構えにした。1 つはルール集合の一致で、
`.gitleaks.toml` の `[[rules]]` id・`RULE_IDS`・検出ケースが名指しするルールの 3 集合が一致する
ことを要求する。もう 1 つはケース ID 集合の manifest で、件数ではなく ID を pin して消えた側も
未記録側も名指しで赤にする。片方向だけだと、toml へルールを足して `RULE_IDS` を触らない形も、
`RULE_IDS` へ足して検出ケースを書かない形も、「ルール N 本を検査した」と名乗ったまま緑で通る
(どちらも変異注入で再現した)。同型の先例は `scripts/run-python-tests.py`。

**免除は値で持ち、パスでは持たない。** 元の露出は `test_winvm.py` の中で起きたので、テスト
ファイルを免除すると見つけた穴をそのまま作り直す。新しい fixture を足すときは免除を触ることに
なり、その手間が「その値は公開してよいか」を一度考えさせる。

実測を記録する。

- 着手時点の追跡下の UUID は 16 出現あり、全部が合成 fixture だった。メールは 8 出現で
  全部が `.invalid`
- 全履歴 52 コミットを走査すると `vm-uuid` が 9 件出た。scrub 前の `test_winvm.py` で、
  ツリー側は 2026-08-24 に置換済み。`.gitleaksignore` へ fingerprint を記録した
- **単語境界 `\b` を使うと素通りする形が 3 つあった。** `seed_<UUID>` (`_` が単語文字なので
  先頭の境界が成立しない)、`<UUID>9`、`<UUID>z` (末尾 12 桁の直後が単語文字だと末尾の境界が
  成立しない)。1 つ目は仮想の話ではなく、同梱している security plugin が
  `<接頭辞>_<UUID>` を seed の既定形式として文書化している。境界を外しても免除は縮まない
  (免除は match 全体へ `^...$` で掛かるので、接頭辞が付いても fixture は fixture のまま)
- **allowlist の `(?i)` はエントリごとに独立しない。** gitleaks は `regexes` を 1 本へ束ねて
  評価するので、先頭エントリの `(?i)` が後続すべてへ前方に漏れる (順序を入れ替えた 3 通りの
  対照で確定)。どのエントリの `(?i)` が効いているかは書いた場所では決まらない
- **`gitleaks dir` は既定で cwd の `.gitleaksignore` を読む。** 対照ハーネスは cwd が
  リポジトリルートなので、指定しないと免除ファイルが検査に効く。危険な向きは片側だけで、
  許可ケースが免除されると allowlist が壊れて誤検出している状態が緑で通る。
  `--gitleaks-ignore-path` をケース側へ固定して切った
- **`.gitleaks.toml` はファイル名で走査対象から外れる** (別名へコピーすると同じ内容が
  12 件検出される)。ルールの説明に実物の形を literal で書けるのはこのため。対照ケース側には
  この免除が無いので、あちらは値を変数から組み立てる
- **gitleaks が走査するのはファイル内容だけ。** コミットメッセージ (subject / body / trailer)・
  author / committer・注釈付きタグの tagger と message は、いずれも面の外だった。注釈付きタグに
  tagger のメールアドレスがあるので `email-address` が発火すると予想したが、全履歴走査で 0 件。
  走査バイト数がファイル内容の合計と一致することで確かめている。走査すると推測したまま免除を
  足していれば、届きすぎる免除を 1 つ抱えていた

## 適用: 層 2 (2026-09-11)

`scripts/check-leak-guard-denylist.py` を足し、追跡ファイルとコミットメッセージの 2 入口を
1 ファイルで持たせた (先例は `issue-id.py` の `--check` / `--check-text`)。禁止語リストは
PUBLIC なこのリポジトリへ置けないので環境変数で外から指す。設計も変数名も canonical は
スクリプトの docstring で、ここでは再掲しない。

spec が設計した 3 分岐 (未設定 / ファイルあり / ファイル無し) では足りなかった。
**「ファイルはある」と「比較に使えるエントリが取れる」は別の検査**で、後者が 0 でも前者は
通る。着手前に失敗モードを 5 角度で列挙したところ、緑のまま何も見ていない形が 30 通り出た
(env-branching / tracked-surface / matching-rules / output-redaction / commit-msg-surface)。
分岐表は実装の docstring が canonical で、spec の表は設計時点の見立てとして残す。

**照合対象は worktree ではなく index の blob にした。** コミットされるのは blob で、worktree は
symlink 追従・smudge filter・sparse-checkout の 3 経路で blob と食い違う。`git ls-files` が
cwd 相対なので、サブディレクトリから起動すると配下しか返さない面もある。0 件ではなく部分欠落
なので「追跡 0 件なら止める」ガードを素通りし、数字が揃った健全に見える要約で緑になる。

**パスも走査面に含めた。** spec は走査面を「追跡ファイル全体」としか書いておらず、内容だけを
読む実装になりやすい。実際に効いた: live smoke で `prlctl` を禁止語に置くと、
`docs/issues/ISSUE-10_SSH 断時に prlctl exec を...` の**ディレクトリ名**が捕まった。内容走査
だけなら素通りしていた形で、しかもこのパスは非 ASCII を含むので `-z` が無ければ壊れていた。

**リストが効いているかを毎回の実行で自己照合する。** 各エントリについて「そのエントリを本文へ
埋めた合成テキストが自分で検出できるか」を照合の前に確かめ、1 件でも失敗したら検査不能で止める。
BOM 付き・NFD・末尾空白・fold の片側適用はどれも「エントリ数は非 0 なのに 1 件も当たらない」
という静かな緑で出るので、要約を読んでも異常が見えない。

実測を記録する。

- 追跡 140 件。symlink 0 / gitlink 0 / バイナリ 0 / UTF-8 で読めないもの 0。**非 ASCII パスは
  59 件 (42%)** で、`git ls-files` の `-z` を外すとこれが C クォートで壊れる
- **変異注入が 7 件の dead pin を暴いた。** テスト 56 件は全緑だったのに、壊しても緑のものが
  7 つあった。内訳は (a) docstring の主張を支える対照が無い 2 件、(b) テストが production の
  入口を通らず内部関数を直接呼んでいた 2 件、(c) 対照が後段のガードに守られていて単独では
  何も pin していない 1 件、(d) 対照の選び方が変異を素通りさせる 2 件
- **(d) の 2 件は「対照として成立しない」形だった。** `--che` は `--check` と `--check-text` の
  両方の接頭辞なので `allow_abbrev` の有無に関わらず ambiguous エラーになる。C クォートの対照に
  ASCII の禁止語を使うと、クォートが非 ASCII バイトだけをエスケープするので `-z` を外しても
  当たる。どちらも「置いた」だけで対照になっていなかった
- **fold の前後の NFKC は別のものを守っていた。** 当初どちらも「casefold が NFKC 正規形へ
  戻さない code point のため」と書いたが、どちらを外してもテストが赤くならなかったので測り
  直した。先頭は冪等性を守る (照合結果は変えない)。末尾は照合結果を変える —
  Cf 除去がゼロ幅文字を落とすと base と結合文字が隣り合うので、そこで合成をやり直す必要が
  ある (`ｶ` + ZWSP + `ﾞ` が `ガ` に一致するかどうかの差)
- pre-commit 経由で 3 状態を通した。禁止語なしで `status=checked`、ありで exit 1 と座標のみ、
  環境変数なしで `status=skipped`。`verbose: true` が無いと 3 つとも `Passed` の 1 行になる
- **座標に `#<数字>` を使ったら in-repo Issue の記法検査に捕まった。** 当初の出力形式は
  `entry #5` で、意味は GitHub の Issue 番号と別物だが機械検査に区別はできない。免除を
  広げる (検査を緩める) のではなく、衝突しない形 (`denylist line 5` / `tracked file 37`) へ
  変えた。既存の検査が禁じている記法を新しい出力が踏むと、緩める方向の圧力が掛かる
- **git のメタデータ面の内訳** (spec と下のタスクが実態より広く書いていたので測り直した)。
  author は 53 出現すべてが実ドメインの 1 種。committer は 2 種で、45 出現が GitHub web UI の
  マージ由来の予約形、8 出現が実ドメイン。タグの tagger 5 本は実ドメイン。つまり露出面は
  author 53 + committer 8 + tagger 5 で、**相異なり 1 種**。開発機の `user.email` は既に
  noreply 形へ変わっているので、これから作る分は予約形になる

### マージ前レビューで見つかった是正

5 角度の並列レビューと角度ごとの反証を通し、8 件の指摘が実測付きで確定した。反証側が
id を返さなかった 4 件は自分で判定した (相関キーの失敗は例外ではなく「全件未検証」という
静かな結果で返るので、件数を数え直して初めて気づける)。

- **メッセージ入口が走査対象のパスを無加工で印字していた。** 通常の worktree では
  `.git/COMMIT_EDITMSG` と相対だが、**linked worktree からのコミットでは git が絶対パスを
  渡す** (実測)。その先頭はホームディレクトリなので、層 1 が守っているユーザー名が
  pre-commit の Failed ブロックへ出る。パスは照合対象ではないので、パスに禁止語が入る経路も
  同時に開いていた。1 起動で走査するのは 1 ファイルなので、パスを出さず行番号だけにした
- **自己照合ガードの「取り付け」が未 pin だった。** `failed = self_check(entries)` を
  `failed = []` にしても全テストが緑。機構本体を壊す変異は既存の対照が捕まえるが、
  取り付けを外す変異は誰も捕まえていなかった。正しい fold の下では自己照合が失敗する
  エントリをリストから作れない (BMP 全域を走査して 0 件) ので、到達性は注入で作るしかない
- **確認コマンド自体が、見たい失敗を消していた。** `LEAK_GUARD_DENYLIST=<パス> ... --check`
  は変数をその場で注入するので必ず `status=checked` になる。確かめたいのはスクリプトが
  動くことではなく変数が起動元に届くことなので、inline 代入を外した
- **argparse が余分な引数をそのまま印字していた。** 配線から `pass_filenames: false` が
  落ちると追跡パスが引数で渡り、汚染パスの置き換えが隠すはずのパスが Failed ブロックへ並ぶ。
  配線と実装の 2 層で塞いだ
- **座標の序数が走査した index に対するものだった。** `commit -a` と `commit -- <pathspec>` は
  hook へ一時 index を渡すので、序数は運用者が後から引く `git ls-files` とずれる (実測)。
  oid を併記し、どちらの index を走査したかを要約に出すようにした
- **`stages: [manual]` を 1 行足すと追跡ファイル面が消える。** Skipped の表示すら出ず、
  `pre-commit run --all-files` にも現れないまま全テストが緑 (実測)。stage の束縛と、
  許可キー集合の外のキーを赤にする pin を足した
- docstring の分岐表が canonical を名乗りながら exit 2 の分岐を落としていた件と、
  `#<数字>` の排除が検査不能の文言に 1 箇所残っていた件も直した。後者には負の pin を置いた
