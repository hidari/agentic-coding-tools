# fix: PUBLIC リポジトリに private プロジェクト由来の記述が残っている

## 背景

このリポジトリは PUBLIC で、CLAUDE.md が次を MUST にしている。

> private リポジトリの内部事情 (未公開の設計、社内固有の運用) を書かない。一般化できる
> 知見だけを、出所を伴わない形で書く

skill の多くは private プロジェクトでの実運用から一般化して切り出したものなので、切り出しの
過程で出所が残った箇所がある。ISSUE-14 の作業中に、新しく書いた Issue 本文へ同種の記述を
入れかけたことをきっかけに発見した (そちらは push 前に落とした)。

本 Issue が扱うのは**既にマージ済みで公開されている分**である。

## 検査が捕捉しなかった理由

**`gitleaks` は全 hook 緑のままこれらを通している。** 誤りではなく設計どおりで、検出集合の
canonical は `.gitleaks.toml` にあり、プロジェクト名・リポジトリ名・ホスト名はそこに無い
カテゴリだからである。CLAUDE.md 自身が「gitleaks の緑を安全の根拠にしない」と警告している
とおりの形で起きた。

発見の経路も偶然だった。ISSUE-14 のレビューが「参照に使った owner 名が未検証」と指摘し、
確認しに行った先で visibility が PRIVATE だと分かった。owner 名を検証していなければ
気づかずに push していた。

**数え方でも一度取りこぼした。**最初は小文字で検索して 2 ファイルと数えたが、3 ファイルは
大文字始まりで書かれていた。case を無視して数え直すと 5 ファイルだった。

## 設計上の問い

単に消すだけだと同じことが繰り返される。次を決める必要がある。

1. **消すのか、一般化するのか。** 引用は「一般化できる知見」を支える根拠として置かれている。
   出所を落とすと根拠が弱くなる箇所があるので、記述ごとに判断が要る
2. **検査に落とせるか。** `.gitleaks.toml` に custom rule を足せば機械的に捕捉できる。
   ただし禁止する固有名詞をこの PUBLIC リポジトリの検査ルールに literal で書くと、
   **ルールファイル自身が露出になる**。この自己言及をどう解くかが設計の中心
3. **今後の流入をどこで止めるか。** skill を private プロジェクトから切り出すときが
   流入点なので、切り出しの手順側に検査を置くほうが効く可能性がある

## 既知の限界

- **履歴からは消せない。**現在のツリーを直しても、過去のコミットと closed PR の diff は
  公開のまま残る。本 Issue が回復できるのは「これから読む人が見る状態」だけである
- 同じカテゴリの棚卸しが別リポジトリでも進行中で、そちらと重複しうる
