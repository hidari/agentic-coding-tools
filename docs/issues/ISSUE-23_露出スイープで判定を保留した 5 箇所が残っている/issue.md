# fix: 露出スイープで判定を保留した 5 箇所が残っている

## 背景

ISSUE-15 の全文スイープが 14 箇所を挙げ、確信の持てた分は PR で落とした。残ったのが
本 Issue の 5 箇所で、「このリポジトリ固有の記述なのか、一般化された記述なのか」を
読解でも機械的にも決められなかったものである。

保留したという事実は、前セッションの引き継ぎ書にしか残っていなかった。引き継ぎ書は
`.cache/` 配下にあって ignore され、消費後に削除される。ISSUE-15 の本文にも記録が無い。
この Issue が無いと、保留したこと自体が次のスイープまで誰にも見えない。

## この Issue に literal を書かない

対象がリポジトリの PUBLIC 性そのものなので、露出の疑いがある文字列をここへ再掲すると
Issue 自身が同じものを公開する。ISSUE-15 が「禁止語を PUBLIC なルールファイルに literal で
書けない」という設計上の問いを抱えているのと同じ構造で、解き方も同じにする。

以下は場所と「何の種類の情報か」だけを書く。実物は各行を読むこと。行番号は起票時点の
ものなので、あわせて節や表の位置でも指す。

## 保留した 5 箇所

判断基準が 3 種類に分かれている。1 本の Issue にまとめてあるが、A を落とす判断と B を
直す判断は別の基準で下すことになる。

### A. 他リポジトリの運用実績を名指ししている

ISSUE-15 と同じ軸。「一般化できる知見だけを、出所を伴わない形で書く」に反する。

| 場所 | 種類 |
|---|---|
| `plugins/dev-workflow/skills/in-repo-issue/SKILL.md:345` (`## Red flags` 表の最終行) | 他リポジトリで実際に起きた Issue 重複の事例を、対象の名前を挙げて書いている |
| `docs/issues/closed/ISSUE-14_.../issue.md:60` (`### 既存の対策が破綻した機序`) | 他リポジトリで運用が止まった時点を、特定の年月日で書いている |

どちらも「実際にこうなった」という体験の重みが記述の説得力を支えている。出所ごと落とすと
主張の根拠が浮く。ISSUE-22 の棚卸し数値を残すと決めたときと同じトレードオフで、あちらは
残す判断になった。同じ結論になるとは限らないが、判断の型は共通している。

### B. 配布先に存在しない前提を断定形で書いている

これは露出ではない。**配布物として成立していない**という別の欠陥である。このリポジトリの
中では前提が満たされているので、ここで動かしても気づけない。

| 場所 | 種類 |
|---|---|
| `plugins/dev-workflow/skills/e2e-scenario-impact-check/SKILL.md:26,45,57,68,79,101,159` | 特定のディレクトリ構成とテスト配置を、早期 skip 判定の条件そのものに使っている |
| `skills/meta/session-handoff/SKILL.md:3,18` | 配布物に含まれない hook スクリプトへの依存 |

`session-handoff` の側は実測で裏付いている。このリポジトリは hook の実体を追跡下に持たず
(`git ls-files` で 0 件)、`.claude/hooks` も存在しない。apm 経由で skill だけを受け取った
配布先には依存先が無いので、手順 4 が失敗する。しかもこの手順は provenance の記録で、
記録が無いと次のセッションで注入されない fail-closed 設計になっている。つまり失敗は
エラーとしてではなく「引き継ぎが静かに効かない」という形で出る。

`e2e-scenario-impact-check` の側は判断が割れる。Playwright の一般的な配置とも読めるが、
断定形で書かれていて、条件分岐がその名前に直接依存している。

### C. 単独の開発者しかいない配布物に、複数人の運用を前提にした語がある

| 場所 | 種類 |
|---|---|
| `skills/tooling/chrome-devtools-debugger/SKILL.md:162` | 組織的な運用を前提にした語で、skill の責務範囲を説明している |

露出とまでは言えないが、配布先の読み手にとって指示対象が存在しない語である。

## 棄却したもの

スイープは他に 2 箇所を挙げていたが、実物を読むと露出ではなかった。記録として残す。

- `plugins/security-blue-red-team/README.md:19` — 通知手段の名前は出るが、`e.g.` と `etc.` に
  囲まれた例の列挙の一員である
- `plugins/security-blue-red-team/skills/security-vulnerability-assessment/SKILL.md:21` —
  同じ名前が出るが「など」付きの例示である

スイープの報告は両方について「例ではなく実際こうしていると読める」だった。実物は逆で、
どちらも例として書かれている。**列挙をそのまま起票していれば、露出でないものを露出として
直していた。**報告を再現せずに着手すると外れる、という ISSUE-15 と同じ型の失敗である。

ISSUE-22 の棚卸し数値も同じスイープが挙げているが、こちらは判断済みで残すと決めてある。
件数と分布がそのまま判断の根拠になっているため。
