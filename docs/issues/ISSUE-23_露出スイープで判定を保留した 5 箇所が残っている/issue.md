# fix: 露出スイープで判定を保留した 5 箇所が残っている

## 背景

ISSUE-15 の全文スイープが 14 箇所を挙げ、確信の持てた 7 箇所は PR で落とした。残る 7 箇所を
本 Issue が引き取る。うち 5 箇所が判断対象で、2 箇所は実物を読んで棄却した (「## 棄却したもの」)。
判断対象の 5 箇所は「このリポジトリ固有の記述なのか、一般化された記述なのか」を読解でも
機械的にも決められなかったものである。

保留したという事実は、前セッションの引き継ぎ書にしか残っていなかった。引き継ぎ書は `.cache/`
配下にあって ignore され、消費後に削除される。ISSUE-15 の本文にも記録が無い。この Issue が
無いと、保留したこと自体が次のスイープまで誰にも見えない。

## この Issue に literal を書かない

対象がリポジトリの PUBLIC 性そのものなので、露出の疑いがある文字列をここへ再掲すると Issue
自身が同じものを公開する。ISSUE-15 が「禁止語を PUBLIC なルールファイルに literal で書けない」
という設計上の問いを抱えているのと同じ構造で、解き方も同じにする。

以下は場所と「何の種類の情報か」だけを書く。実物は各行を読むこと。行番号は 2026-08-24 時点の
ものなので、辿れなくなったとき用に節や表の位置を併記してある。

## 保留した 5 箇所

判断基準が 3 種類に分かれている。1 本の Issue にまとめてあるが、A を落とす判断と B を直す判断は
別の基準で下すことになる。

### A. 他リポジトリの運用実績を名指ししている

ISSUE-15 と同じ軸。「一般化できる知見だけを、出所を伴わない形で書く」に反する。

| 場所 | 種類 |
|---|---|
| `plugins/dev-workflow/skills/in-repo-issue/SKILL.md:345` (`## Red flags` 表の最終行) | 他リポジトリで実際に起きた Issue 重複の事例を、対象の名前を挙げて書いている |
| `docs/issues/closed/ISSUE-14_.../issue.md:60` (`### 既存の対策が破綻した機序`) | 他リポジトリで運用が止まった時点を、特定の年月日で書いている |

1 つ目が他リポジトリの記述であることは確定している。挙げられているパッケージマネージャを使う
構成をこのリポジトリは持たない (`package.json` が 1 件も無い)。

どちらも「実際にこうなった」という体験の重みが記述の説得力を支えている。出所ごと落とすと主張の
根拠が浮く。

### B. 配布先に存在しない前提を断定形で書いている

これは露出ではない。**配布物として成立していない**という別の欠陥である。このリポジトリの中では
前提が満たされているので、ここで動かしても気づけない。

用途ごとに行が分かれている。1 つの塊として扱うと、判定条件だけを直して残りを取りこぼす。

| 場所 | 種類 |
|---|---|
| `plugins/dev-workflow/skills/e2e-scenario-impact-check/SKILL.md:26,27,45,57` (`### 使わない / 早期スキップする`、`### Phase 1: 早期スキップ判定`) | 特定のディレクトリ構成を、早期 skip の判定条件そのものに使っている |
| 同 `:68,101` (`### Phase 2: agent 起動による静的検査`、`### Phase 3: 結果整形`) | 同じ構成を、入力収集の対象と出力フォーマットの例に使っている |
| 同 `:79` (`#### agent への検出パターン hint`) | 特定のルート名と画面パスを、検出パターンの例に使っている |
| 同 `:159` (`## 既知の改善余地`) | 同じ構成を、改善余地の説明に使っている |
| `skills/meta/session-handoff/SKILL.md:3,9` (frontmatter の description、冒頭の導入段落) | hook が存在する前提で挙動を断定している |
| 同 `:18` (`## 手順` の 4) | 配布物に含まれない hook スクリプトを実行する手順 |
| 同 `:31` (`## 書き方の要点`) | 配布先に存在しないファイルを canonical として名指ししている |

`session-handoff` の側は実測で裏付いている。このリポジトリは hook の実体を追跡下に持たず
(`git ls-files` で 0 件)、`.claude/hooks` も存在しない。apm 経由で skill だけを受け取った配布先には
依存先が無いので、手順 4 が失敗する。しかもこの手順は provenance の記録で、記録が無いと次の
セッションで注入されない fail-closed 設計になっている。つまり失敗はエラーとしてではなく
「引き継ぎが静かに効かない」という形で出る。

31 行はさらに重い。canonical の所在を名指ししているので、配布先ではその canonical が存在しない。
参照を辿った先が無いことは、手順の失敗と違って実行時にすら現れない。

`e2e-scenario-impact-check` の側は判断が割れる。Playwright の一般的な配置とも読めるが、断定形で
書かれていて、条件分岐がその名前に直接依存している。

### C. 単独の開発者しかいない配布物に、複数人の運用を前提にした語がある

| 場所 | 種類 |
|---|---|
| `skills/tooling/chrome-devtools-debugger/SKILL.md:162` (`## 他スキルとの使い分け` の末尾段落) | 組織的な運用を前提にした語で、skill の責務範囲を説明している |

露出とまでは言えないが、配布先の読み手にとって指示対象が存在しない語である。

## 棄却したもの

スイープは他に 2 箇所を挙げていたが、実物を読むと露出ではなかった。記録として残す。

- `plugins/security-blue-red-team/README.md:19` (`## Two-layer architecture` の箇条書き 2) —
  通知手段の名前は出るが、`e.g.` と `etc.` に囲まれた例の列挙の一員である
- `plugins/security-blue-red-team/skills/security-vulnerability-assessment/SKILL.md:21`
  (`## 起動経路` の 4) — 同じ名前が出るが「など」付きの例示である

スイープの報告は両方について「例ではなく実際こうしていると読める」だった。実物は逆で、どちらも
例として書かれている。**列挙をそのまま起票していれば、露出でないものを露出として直していた。**
報告を再現せずに着手すると外れる、という ISSUE-15 と同じ型の失敗である。

## ISSUE-22 の棚卸し数値について

同じスイープが挙げているが、こちらは残す判断になっている。件数と分布がそのまま判断の根拠に
なっているため、落とすと判断が浮く。

ただし **ISSUE-22 の本文にはその判断が記録されていない**。実測すると、あちらの本文に露出や公開の
観点は 1 件も出てこない (対照として件数・記法・rename はいずれも非 0 でヒットするので、ファイルが
読めていないわけではない)。判断が引き継ぎ書にしか残っていないという、この Issue が背景節で挙げた
構造そのものである。だから理由をここに残し、あちら側への書き戻しをタスクに含める。
