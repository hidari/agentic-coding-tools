# fix: Phase D.3 の射程がルートからのパス表記を含まない

## 背景

SKILL.md の Phase D.3 は Issue を `closed/` へ移したときのリンク補正を担当する。射程を
「壊れる相対リンクを補正する。方向は 3 つあり、3 つとも見ること」と宣言し、表の 3 行はすべて
`../` で始まる形になっている。

実際には**リポジトリルートからのパス表記** (`docs/issues/<ID>_<title>/issue.md`) で書かれた参照が
あり、これが射程の外に落ちる。移動しても補正されず、リンクが stale のまま残る。

## 実測 (2026-08-27)

配布先で docs 配下を全走査したエージェントからの報告。

| 分類 | 件数 |
| --- | --- |
| 実在するルートからのパス (対照。0 なら検査自体が壊れている) | 19 |
| 省略記法 (元々解決不能なので対象外) | 32 |
| stale (実在しない) | 10 |

stale の 10 件は全部 `closed/` を 1 段挟めば実在する。つまり全件が移動に追随できなかった参照
である。

### 表の 3 方向に該当しないケースがある

10 件のうち 3 件は「**移動対象の中の補助資料が、自分と同じディレクトリをルートからのパスで
参照している**」形だった。参照元も参照先も移動対象の内側にあるので、「外部と移動対象のあいだ」
という軸で探すと構造的に見つからない。

残る 7 件は方向としては 1 つ目 (外部から移動対象へ) だが、表記がルートからのパスなので表の
Before / After に当てはまらない。

### 検出コマンドは半分だけ効いている

D.3 が併記する 2 本のうち、識別子で引く方 (`grep -rn "${ID}_"`) はルートからのパスも実際に拾う。
`../` で始まる Markdown リンクを探す方は当然拾わない。

つまり「手順を実行しても検出できない」のではなく、**1 本目の出力に出ているのに、表に対応する
行が無いので補正対象として分類されない**。列挙が網羅でないときの典型で、出力を最後まで見れば
気づける形をしている。

### リンク記法ですらない形もある

1 件はバッククォートのコードスパン内だった。リンク記法を前提にした検出は原理的に届かない。
射程の話にはこれも含まれる。

## 提案 (報告元より)

表に 4 行目を足すより、**見出しの射程宣言そのものを広げる**方が canonical が 1 つで済む。
「壊れる相対リンクを補正する」を「壊れる相対リンクと、リポジトリルートからのパス表記を補正する」
にして、識別子で引く grep の出力を最後まで見ることを促す一文を添える形である。

表を 4 行に増やすと「方向」の軸と「パス表記」の軸が混ざって読みにくくなる。

## 数え方の注意

報告元が 2 度数え直している。どちらも件数が着手の根拠になる場面だった。

- 省略記法に半角と全角の両方が使われていた。半角しか除外しないと 13 件に見え、全角を
  除外して 10 件に落ち着いた。3 件の差は「壊れたリンク」ではなく「元々解決不能な省略記法」で、
  混ぜると過大報告になる
- 並列調査に出した agent の最初の報告は 5 件だった。移動対象の内側を走査していなかったための
  過小評価で、自分で数え直して 10 件になった
