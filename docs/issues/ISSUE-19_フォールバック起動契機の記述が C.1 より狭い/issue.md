# fix: フォールバック起動契機の記述が C.1 より狭い

## 背景

`dev-workflow:in-repo-issue` の「いつ使うか > 必ず使う」節の最後の bullet が、gate を経由しない
フォールバック起動の契機を次のように書いている。

> ユーザーから「マージしたよ」「閉じて」と指示された時、 また次セッション開始時に main の
> CI 成功 + `Closes <ID>` を検出した時 (フォールバック)

ここには 2 つの問題がある。

### 1. キーワード集合が C.1 より狭い

Phase C.1 が抽出するのは `Closes` と `Fixes` の両方である。契機の記述は `Closes` しか挙げて
いないので、**`Fixes` だけを書いた PR は「起動する条件を満たしていない」と読める**。実際には
C.1 へ渡せば抽出されるので、契機の記述だけが実態より狭い。

実測: SKILL.md 内で `Fixes` を含む行は 6 行あり、その内訳は frontmatter の description、
C.1 の見出し文、抽出コマンドの 2 行、C.1 の解説 bullet 2 本である。「いつ使うか」節には
1 件も無い (照合は行番号ではなく文字列で行った)。

同じ集合を 2 箇所に literal で持つ形そのものが、ISSUE-14 が `pre-merge-quality-gate` の
Phase 5 で潰したのと同型である。あちらは起動条件を gate 側から削除して C.1 へ委譲する形で
解いた。**呼ばれる側の中にも同じ二重管理が残っている**。

なお frontmatter の description は `Closes <ID>` / `Fixes <ID>` の両方を持っており、こちらは
狭くない。description は本文なしで読まれる surface なので literal を許すという判断が
ISSUE-14 の作業中に置かれている。**description は本 Issue の対象ではない**。

### 2. 「main の CI 成功」が C.2 と二重管理

同じ bullet が起動条件として「main の CI 成功」を持つ。これは Phase C.2 が持つ条件と同じ
ものである。C.2 側には「gate 経由ならスキップ」という分岐と `gh run list` の具体があるので、
契機側の 1 行はその要約になっている。要約は元が変わっても赤くならない。

C.2 の記述自体にも別の問題があり、そちらは ISSUE-17 が扱う。**本 Issue が消すのは重複であって、
C.2 が何を確認すべきかは決めない**。

## タスク

- [ ] 「main の CI 成功」の条件も C.2 を参照する形にする
- [ ] 書き換えた側を 4 点で検算する

      (4) 足した注記自身が値を再掲していないか
