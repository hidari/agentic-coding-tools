# fix: Phase E の子探索が空振りしたとき親の close 提案側へ倒れる

## 背景

`dev-workflow:in-repo-issue` の Phase E は、親の `children` を読んで各子の所在を探し、
「1 行でも出れば active な子が残っている → 終了。出力が空なら全件 closed で親も close 可能」
と判定する。

この読み方は、探索が空振りした理由を区別しない。子が本当に全て closed で空になったのか、
`children` を読めずに空になったのかが同じ観測値になる。空は提案側へ倒れるので、**active な
子が実在するのに親を閉じる提案が出る。**

ISSUE-43 が同梱経路へ D.5 を足したことで Phase E は既定の経路から起動するようになった。
それまでは Phase E 自体がどの経路からも到達不能だったので、この空虚さは症状を持たなかった。

## 実測 (2026-08-31)

スニペットを SKILL.md から抜き出して fixture へ流した。親は active、子は ISSUE-2 (closed) と
ISSUE-3 (active) の 2 件で、**正しい答えは全ケース「提案しない」**。

| 親の `children` の書かれ方 | 結果 |
| --- | --- |
| 対照: `[ISSUE-2]` で子が全て closed | 親の close を提案する (正しい) |
| 対照: `[ISSUE-2, ISSUE-3]` で ISSUE-3 が active | 提案しない (正しい) |
| キーが無い | **提案する** |
| `children: []` | **提案する** |
| ブロックリスト形 (`children:` の下に `- ISSUE-2` を並べる) | **提案する** |
| `[ISSUE-02, ISSUE-03]` (ゼロ埋め) | **提案する** |
| `[ISSUE-2, ISSUE-9]` (ISSUE-9 は実在しない) | **提案する** |
| `[ISSUE-2, ISSUE-3]  # 子の識別子` (末尾コメント) | 提案しない (正しい) |

6 形のうち 5 形で誤った提案が出る。対照 2 行が正しく出ているので、スニペット自体は生きている。

ゼロ埋めが倒れるのは、抽出した識別子をそのまま `-path "*/${child}_*/issue.md"` に使うため。
`ISSUE-02` は `ISSUE-2_*` に一致しない。`scripts/check-issue-closure.py` は同じ識別子を
int へ正規化して同一視すると決めているので、**同じ 2 つの識別子について検査と手順が逆の
答えを出す**状態になっている。

ブロックリスト形が倒れるのは、`sed -E 's/.*\[(.*)\].*/\1/'` が角括弧を持たない行を素通しし、
`children:` という文字列がそのまま子の識別子として扱われるため。

## ISSUE-38 との違い

| | 機序 | 現れ方 |
| --- | --- | --- |
| ISSUE-38 | frontmatter のキー名が規約と別 | 抽出 0 件 |
| 本 Issue | キー名は規約どおりだが値の書式か解決が合わない | 抽出が空か、実在しない子を引く |

どちらも「空を親不在 / 全件 closed と即断する」ところで同じ結末になるが、直す場所が違う。
ISSUE-38 は 0 件の解釈と規約外キーの報告、本 Issue は値の読み取りと空の扱いを持つ。

編集が衝突する。両者とも Phase E の同じ bash フェンスへ手を入れることになるので、**着手の
順序を決めてから片方ずつ触ること。**

## 検討の起点

- 空の理由を区別する。子を 1 件も解決できなかったときと、解決した子が全て closed だった
  ときを別の結末にする。解決件数を数えて `children` の宣言数と突き合わせる形が素直
- 値の読み取りを識別子の実在まで含めて行う。`scripts/check-issue-closure.py` が既に
  int 正規化と実在検査を持つので、判定の canonical をどちらに置くかを決めること。
  今は同じ規則が 2 箇所にあって答えが食い違っている
- ブロックリスト形を規約として許すかを決める。許さないなら、素通しではなく落ちる形にする
