# perf: commit-and-pr-message を呼ぶたびに払うコストが大きい

## 背景

dotfiles のマージ前ゲートからの提案 (2026-09-25) のうち2つを引き取る。どちらも `commit-and-pr-message` を使うたびに払うコストで、1つは skill を呼んだときに載る SKILL.md の大きさ、もう1つは送る前の検査が本文を送るたびに引く `gh repo view --json visibility` である。

SKILL.md は ISSUE-58で送る前の漏洩検査を入れたときに約2倍になった。提案は、次の3つを必要なときだけ読む reference へ移せるとしている。

- 落とし穴の表のうち、本文の言い直しになっている行
- 「既知の限界」のうち、入口 (`check-outgoing-text.py`) の docstring と重なる部分
- hook の無い環境でも払う、Tirith に固有の根拠の節 (ISSUE-58より前からある)

公開範囲の判定については、同じセッションの同じリポジトリなら最初の判定を使い回せるとしている。使い回す値は最初に入口を呼ぶ前に決めたものなので、「rc 1 を見てから判定し直さない」は保てる、という見立てである。

提案に添えられた所要時間は dotfiles 側の環境での実測で、ここへは引き写していない。下の「確かめたこと」の数値は、このリポジトリで測り直したものである。

## 確かめたこと (2026-09-27、origin/main が cbb555d の時点)

- SKILL.md は24,656 B で、ISSUE-58の変更が入る直前 (a126db2) は12,335 B だった。その間にこのファイルを変えたコミットは ISSUE-58の squash (66231ad) だけで、倍増はこの1コミットで起きている。frontmatter を除いた本文は23,754 B で、呼ぶたびに載るのはこちらである。Skill ツールで読み込むと frontmatter は載らず、先頭に skill のディレクトリを示す行が付く (2026-09-27 に観測)
- 落とし穴の表は「落とし穴 (Red flags)」節にあり、12行で、見出しの行を含む表全体が2,796 B (ISSUE-58の直前は1,102 B)。起草時に12行を本文と突き合わせた限りでは、どの行も右の列の規定が本文のどこかにあり (理由の一部を入口の docstring から引いた行を含む)、本文に無いのは左の列の思考の罠の言い回しだった。どの行を言い直しとみなすかは、着手時に現物で決める
- 既知の限界は「送る前の検査」節の下の小節で、6項目1,286 B。入口の docstring の「既知の限界」と同じことを書いているのが3項目331 B、一部が重なるのが1項目650 B で、残る2項目は手順の側の限界なので docstring に対応が無い。一部が重なる項目は、入力が大きすぎて止まったときに踏む分け方の手順で、限界の記述ではない。既知の限界は、目的の箇条 (当たらないと分かっている形) と、終了コード2の行 (`reason=input-too-large` のとき) の2箇所から名前で指されている
- Tirith の根拠は「前提: なぜファイル経由なのか」節で、2,944 B (ISSUE-58の直前は2,434 B)。hook の仕組みと発火条件を書いた範囲が2,535 B で、hook に依らない内容は冒頭の理由の段落 (検査と受け渡しが同じファイルを読む) のほか、この範囲の中にも混ざっている (1行の値を `"$(cat <file>)"` の形で渡したときに届く値の説明)。ISSUE-58の前の description は Tirith の hook が有効な環境で使うものとしていたが、ISSUE-58で hook の有無を問わない形へ広げたので、hook の無い環境でもこの skill を呼び、この節も一緒に載るようになった。ISSUE-58の spec は、Tirith に由来する理由をこの節に閉じ込めると決めている。本文にはこの節を名前で指す箇所が5つある。また dotfiles のユーザー向けの指示 (CLAUDE.md と git-workflow の reference) は、本文をファイル経由で渡す理由について、機構と発火条件の canonical としてこの skill を名指している
- 移設の判断と手順は context-loading-mechanics が持つ (「移設先の 3 択」「判定基準」「手順」)。ただし同 skill が対象にしているのは常時ロード層で、skill の本文は呼んだときに載る側にある (同 skill の「何が常時ロードされるか」の表)
- 公開範囲の判定を指示しているのは「送る前の検査」節の1箇所で、A.2 と C.2 はどちらもこの節の手順を踏む。git / gh へ1回渡すごとに1回引くので、コミットと PR を1回ずつ作る流れでは2回になる。rc 1 のやり直しでは引き直さない。判定の結果で入口に `--target-private` を付けるかが決まる形なので、書かれたとおりに踏むと入口とは別のツール呼び出しになる。`--target-private` を付けるのは結果が PRIVATE のときだけで、PUBLIC、INTERNAL、コマンドの失敗、空の出力では付けない
- 「判定し直さない」の規定は4箇所ある (「送る前の検査」節の判定の段落とやり直しの段落、落とし穴の表の2行)。どれもワークフローの2手目、つまり本文ごとの手順の中に置かれているが、「最初に入口を呼ぶ前に1回だけ」の「最初に」が本文ごとかセッションごとかは文面に書かれていない。判定を述べる箇所はほかに、ワークフローの2手目の要約、送る前の検査の冒頭、既知の限界の項目がある
- `gh repo view --json visibility --jq .visibility` の所要時間は、5回の中央値で0.524秒 (0.434〜0.758秒)。別のプロセスでもう5回測ると中央値は0.464秒だった。ネットワークに依存する値である

## 決めること

- 3つの候補それぞれを、reference へ移すか、SKILL.md から消して既にある canonical (入口の docstring など) を指すか、残すか。移すと呼ぶたびに載る本文は減るが、移した先が読まれるのはエージェントが読むと決めたときだけになる。消して canonical を指すと、二重の記述と drift する面が消える。残すと今のコストが続く
- 移した先がいつ読まれるか。3つの候補すべてにかかる問いで、context-loading-mechanics の「判定基準」と同じ問いになる
- 既知の限界を移すなら、名前で指す2箇所をどう直すか。終了コード2の行は、入力が大きすぎたときの分け方の手順をそこから読ませている
- Tirith の節を移すなら、節を名前で指す5箇所をどう直すか。ISSUE-58の spec の「この節に閉じ込める」との関係をどう扱うか。外から canonical として名指されているので、移しても skill の中には残す必要がある。移すと、skill を呼んだだけでは発火条件が載らなくなる
- 移した先を読む条件の書き方と、移した先の指し方。同梱物を指す既存の書き方は、skill のディレクトリを指す変数 (入口の呼び出しのコードブロック) と、skill のディレクトリからの相対パスの2通りある。後者はこの SKILL.md 自身が、入口と層 2のスクリプトの docstring を必要なときに読ませるために散文で使っている (単体 skill の `references/` も同じ形)。変数の置換は Skill ツールで読み込んだ本文にだけ起きる (ISSUE-58の spec の前提 8)
- 公開範囲の判定を使い回すか。使い回すなら次を決める
  - 範囲: 同じセッションの同じリポジトリ。「同じリポジトリ」を何で見分けるか (`-R` で渡す値と、cwd から gh が解決する送り先)
  - 置き場所: エージェントの文脈に持つと、subagent へは渡らず、compact で落ちうる。`.cache/` のファイルに持つと、セッションを越えて残り、同じ作業ツリーで動く subagent とは共有され (別の worktree からは見えない)、書き換えれば判定し直しと同じことになる
  - 判定の失敗と空の出力 (今は PRIVATE と扱わない) も使い回すか
  - 古くなる向き: セッションの途中で送り先が PRIVATE から PRIVATE 以外 (PUBLIC、INTERNAL) へ変わると、使い回した PRIVATE のまま層 2を外して送る。逆向きは層 2が余分に当たり、検出で書き直しになるか、環境変数が届かない環境では rc 3 で止まる
  - 「判定し直さない」の4箇所と、判定を述べるほかの箇所 (ワークフローの2手目の要約、送る前の検査の冒頭、既知の限界の項目) を、使い回す範囲の規定へどう揃えるか
