# fix: pre-merge-quality-gate の出力が全レーン skipped でも Merge OK を許す

## 背景

`dev-workflow:pre-merge-quality-gate` は、消費側プロジェクトの CLAUDE.md が
「PR のマージ前には必ず実行する」と定めているゲートである。
その完了判定が、書式の自己申告だけで成立している。

## 実測 (2026-08-27)

SKILL.md の「出力フォーマット」節を逐語で確認した。

- 4 レーンすべてが `[completed / skipped (reason)]` を許す
- Findings applied が `no findings` を許す
- Re-verification が `N/A` を許す
- 末尾の合格宣言はテンプレート上**無条件**で、上のどれとも連動しない

したがって全レーン skipped かつ再検証 N/A の状態が、書式上まったく正当な合格になる。

唯一の関門は次行の散文「合格を出力していない状態で PR をマージしない」で、
機械が見る経路ではない。skip の理由が妥当かを見る層もない。

## 何が問題か

ゲートの目的は「CI が捕捉できない欠陥を人間の判断の前に潰す」ことなので、
**skip の妥当性こそが判定の本体**になる。その本体が自由文字列 1 個に置かれている。

`skipped` や `N/A` を許す書式は、「見た結果ゼロだった」と「そもそも見ていない」を
同じ出力に潰す。これは本リポの検査群が繰り返し塞いできた失敗の形と同型で、
`issue-id.py` が「違反 0 件で緑にすると何も見ていないが合格に化ける」として
走査対象ゼロを exit 2 にしているのと同じ問題である。

なお全レーンを常に必須にはできない。フロントエンドを持たないリポジトリでは
E2E 影響の検出に見るものが無く、そこを必須にすると別の嘘を強いる。
必要なのは「skip してよいレーン」と「skip したら合格を出せないレーン」を分けることで、
一律の必須化ではない。

## タスク

- [ ] skip を許すレーンと許さないレーンを分ける。許さないレーンが skipped のとき
      合格を出せない形にする
- [ ] skip の理由を自由文字列から列挙型へ寄せられるか検討する。
      寄せられれば「見ていない」と「見た結果ゼロ」を書式で区別できる
- [ ] ゲートの結果を機械が見られる形にできるか検討する。
      この skill は agent の出力しか持たないので、消費側に何かを置かずに済む形を探す
