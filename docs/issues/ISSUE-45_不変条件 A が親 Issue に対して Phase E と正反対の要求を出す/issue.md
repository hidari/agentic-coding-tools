# fix: 不変条件 A が親 Issue に対して Phase E と正反対の要求を出す

## 背景

`scripts/check-issue-closure.py` の不変条件 A は「`## タスク` の箱が全て `[x]` なのに active に
居る Issue」を違反とする。箱の中身は見ない。

一方 `dev-workflow:in-repo-issue` の A.5 は、親 Issue の `## タスク` を子 Issue へのリンクを
並べた箱にすると定めている。そして Phase E は「親のチェック状態は判定に使わない」と明記し、
親を閉じる条件を子が全て closed になったことに置いている。

つまり親 Issue について、2 つの規則が正反対の要求を出す。

| | 親を閉じる条件 | 親の箱 |
| --- | --- | --- |
| 不変条件 A | 箱が全て `[x]` | 判定に使う |
| Phase E | 子が全て closed | 判定に使わないと明記 |

## 実測 (2026-08-30)

fixture を組んで現行の検査に通した。対照を並べて、検査自体が生きていることも確認している。

| fixture | rc | 出力 |
| --- | --- | --- |
| 親の箱が全て `[x]` / 子は active | **1** | `タスクが全て消化済みなのに active に居る。クローズを同じ PR へ同梱する` |
| A.5 どおり (親の箱は未) / 子は全て closed | 0 | 違反なし |
| 対照: 正常な active 1 件 | 0 | 違反なし |
| 対照: 箱が全て `[x]` で active | 1 | 違反あり |

1 行目が問題で、**子がまだ active なのに親を閉じろと要求している**。Phase E に従って親を開けた
ままにすると、コミットできない。

2 行目は ISSUE-43 が足す不変条件 C の担当なので本 Issue の射程ではない。

## なぜ今まで出ていないか

`parent` / `children` を持つ Issue が 0 件で、A.5 の分割手順が一度も使われていないため。
使われた瞬間に、親の箱を消化した時点で踏む。

## 検討の起点

どちらへ寄せるかで意味が変わる。決めてから実装すること。

- **A の射程から親を外す**: `children` を持つ Issue は箱を判定に使わない。Phase E の明記に
  揃う。ただし親の箱が「子の俯瞰」以外の用途で使われている場合に、その完了漏れを見なくなる
- **A.5 の親テンプレートを変える**: 親の `## タスク` を箱にしない。A の射程は触らないが、
  俯瞰の書式が変わるので配布物の変更になる
- **Phase E を A に合わせる**: 親のチェック状態を判定に使う。ただし Phase E が「使わない」と
  明記した理由がどこかにあるはずなので、先に理由を探すこと

## 注意

不変条件 A は出荷済みで、このリポジトリのコミットを実際にゲートしている。射程を変えるのは
意味変更にあたるので、`check-issue-closure.py` の docstring が持つ「この検査を入れると
クローズは実装 PR へ同梱することが強制される」という取引の記述も併せて読み直すこと。
