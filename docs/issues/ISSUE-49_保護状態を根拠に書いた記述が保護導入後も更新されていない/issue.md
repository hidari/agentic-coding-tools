# fix: 保護状態を根拠に書いた記述が保護導入後も更新されていない

## 背景

このリポジトリの main は当初どちらの系統でも保護されていなかった。その後 `protect-main` ruleset が
入り、default branch には `pull_request` を含む 4 rule が効いている。ところが「保護が無い」ことを
根拠に書いた記述が、active な Issue の成果物に残ったままになっている。

古い根拠は「間違った結論」としてではなく「もっともらしい前提」として読まれるので、次に着手する人が
そこから別の判断を積む。ISSUE-48 が dotfiles 側の同型の記録に訂正注記を付けていたのと同じ問題が、
リポジトリの内側では誰にも見られていない。

## 実測 (2026-09-02)

対象は 2 箇所。どちらも active な Issue の spec で、closed 配下の歴史的成果物ではない。

| 位置 | 記述 | 現況との差 |
| --- | --- | --- |
| `ISSUE-15-spec.md` | 「main は保護されていない (classic branch protection が 404、repository ruleset が空。両系統を確認した)」 | ruleset は空ではない。classic 404 は今も同じ |
| `ISSUE-32-spec.md` | 「実測時点で `rulesets` は空配列、classic の protection は 404 で、両系統とも保護が無い」 | 同上。タスクの前提そのものが済んでいる |

ISSUE-15 側はこの記述を「**CI は防御層にならない**」「唯一の push 前の関門は pre-commit である」と
いう PUBLIC リポジトリの露出設計の根拠として使っている。**結論そのものは今も成立する** (PUBLIC な
ので push した時点で公開され、CI は push 後に走るので防げない)。成立しなくなったのは根拠の 1 文で、
直すのはそこだけでよい。結論まで書き換えると露出設計の判断が変わってしまう。

ISSUE-32 側は「repository ruleset を入れる」がタスクとして書かれている。これは既に入っているので、
ISSUE-48 が dotfiles の ISSUE-50 について観測したのと同じ「展開ではなく既に入っているものの確認」に
なる。

走査の述語と射程: `docs/issues/` 配下の `*.md` を `ruleset` と `保護されていない` の 2 つの述語で
走査した。closed 配下のヒットは対象から外している (ISSUE-41 の plan と spec が古い判定式の写しを
持つが、同 Issue の本文が訂正を記録済みで、歴史的成果物として残す判断が ISSUE-48 に書かれている)。
述語も射程も自分で選んだものなので、着手時に数え直すこと。

## タスク

- [ ] 走査の述語と射程を変えて数え直す。上の 2 件は述語 2 つの結果なので、増えないことを確かめる
- [ ] `ISSUE-15-spec.md` の根拠の 1 文を現況へ直す。結論 (CI は防御層にならない / 唯一の関門は
      pre-commit) は成立したままなので触らない
- [ ] `ISSUE-32-spec.md` の前提を現況へ直し、ruleset 導入のタスクが済んでいることを反映する
- [ ] 直した記述に日付を持たせるか、記録した時点が読める形にする。日付の無い断言は次も同じ形で古びる
- [ ] 保護状態のような「外部にあって変わりうる事実」を根拠に書くときの作法を決めるかを判断する。
      決めるなら canonical をどこへ置くかも併せて決める
