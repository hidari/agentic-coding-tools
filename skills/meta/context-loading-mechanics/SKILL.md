# Context Loading Mechanics

Claude Code がいつ何をコンテキストへ載せるかは、公式ドキュメントに書かれていない部分が
多い。ここに置くのは live probe で確定させた機構と、常時ロード層が膨らんだときの移設判断。

**推測で置き場所を決めない。** 「たぶん条件付きでロードされるだろう」で移した規範は、
発火しないまま静かに死ぬ。しかも死んだことは何のエラーにもならない。

## 何が常時ロードされるか

| 対象 | いつロードされるか |
|---|---|
| User スコープの CLAUDE.md | session_start で必ず |
| プロジェクトの CLAUDE.md | session_start で必ず |
| `~/.claude/rules/*.md` のうち `paths` frontmatter を持たないもの | session_start で必ず |
| `~/.claude/rules/*.md` のうち `paths` を持つもの | 一致するパスのファイルを Read したときだけ |
| skill の description | session_start で必ず (本文は呼んだときだけ) |

**常時層のコストは session_start だけで払うものではない。** subagent を dispatch する
たびに同じだけ払う。subagent がツールを一切使わずに CLAUDE.md の本文を引用できることで
実測した。この経路は InstructionsLoaded フックには現れないので、フックのログを見て
「載っていない」と判断すると量を過小評価する。

## paths 付き rules の発火条件

実測で確定した点。どれも直感に反する側があるので、推測で代用しないこと。

- **発火するのは Read だけ。** Edit / Write / Bash 経由の書き込みでは発火しない。
  一致するファイルを書き換えても、読んでいなければ規範は届かない
- **追跡状態を問わない。** バージョン管理の外にあるファイルでも、一致すれば発火する
- **dedup のキーは (agent 文脈, rule) で、セッション単位ではない。** subagent は親の
  dedup を継承せず、兄弟どうしも独立して発火する。同じ rule が並列 subagent の本数だけ
  注入される
- **compact で dedup がリセットされる。** `paths` 付き rules 自体は compact 時に
  再注入されないが、dedup が消えるので次の一致 Read で復活する
- **セッション途中に作った rules も発火する** (rules ディレクトリが既に存在する場合に
  限って実測した。ディレクトリごと新設した場合は未確認)

`paths` を持たない rules と CLAUDE.md は compact 時に再注入され、Memory files として
置かれる。これは会話履歴とは別勘定なので、compact による圧縮の対象にならない。

## 移設先の 3 択

| 行き先 | 何を置くか | ロードされるとき |
|---|---|---|
| `paths` 付き rules | 特定の種類のファイルを触るときだけ要る規範 | 一致ファイルの Read |
| 参照だけ残して別ファイルへ | 手当ての詳細・機序の説明・事例 | エージェントが読むと決めたとき |
| skill | 手順そのもの。呼ぶ判断ができるもの | 明示的に呼んだとき |

常時層に残すのは **トリガ文と判定文だけ** にする。「何をしたときに効くか」と
「どう判定するか」があれば、詳細は参照先で読める。逆に詳細だけを常時層に置くと、
いつ効くのかが分からないまま毎回コストを払う。

**移設は無料ではない。** `paths` 付き rules へ移した分は、一致ファイルを読んだ
agent 文脈ごとに払っている。常時層の数字だけを見ていると「移せば必ず勝ち」に見えるので、
条件付き層の合計も並べて見ること。

## 判定基準: トリガが失敗側に無い規範はスコープできない

`paths` 付き rules へ移せるかは、**その規範が回避したい失敗の側で、一致するファイルの
Read が起きるか** で決まる。

- **移せる**: 「テストが緑であることを、仕様を守れている証拠にしない」。回避したい失敗は
  「弱いテストを書くこと」で、その失敗の側ではテストファイルを読んでいる
- **移せない**: 「テストを書き始める前に順序と方式を決める」。回避したい失敗は
  「テストを書かないこと」で、その失敗の側ではテストファイルの Read が起きない

同じカテゴリの中でも項目ごとに判定が割れる。カテゴリ単位で移そうとすると、移せない項目まで
一緒に持っていって沈黙させる。**判定は項目単位で行うこと。**

シェルの使い方やコマンドの組み立てに関する規範も移せない。効くのは「`.sh` を編集するとき」
ではなく「シェルを実行するとき」で、後者ではファイルの Read が起きない。

## 手順

### 1. 内訳を測る

減らす前にどこが重いかを見る。見出し単位で区切ってバイト数を出し、重い順に並べる。

**文字数ではなくバイト数で測る。** 日本語主体の文書を文字数で測ると 3 倍近く過小評価する。

### 2. 候補を判定する

重い順に上の判定基準を当てる。項目単位で、その規範が回避したい失敗を言葉にしてから、
その失敗の側で何を読んでいるかを考える。

### 3. 移す

`paths` は実際に使っているファイル名の規約から決める。**推測で書いたパターンは
一致しないまま静かに終わる。** 手元のリポジトリ群を実際に走査して、どのパターンが
どれだけ拾うかを数えてから決めること。

拾えないパターンがあることも受け入れる。glob の集合は走査した範囲の形をしているので、
その範囲に無い規約 (別の言語圏のテスト命名など) は沈黙する。

### 4. 発火を実測する

**移した先が本当に発火するかは、新しいセッションでしか確かめられない。**
実行中のセッションは session_start 時点の内容をキャッシュしており、subagent もそれを継承する。
編集した直後に「発火しない」と判断すると、キャッシュを機構の挙動と取り違える。

確かめ方は 2 つ。

- **新セッションで一致ファイルを Read し、規範が注入されるかを見る。** 注入されると
  システムからの通知として本文が現れる
- **対照を並べる。** 移した先にしか無い語を検索キーにして、常時層で 0 件・移設先で 1 件を
  確かめる。片側だけでは「消えた」と「そもそも見ていない」を区別できない

## 落とし穴

- **編集は実行中のセッションに反映されない。** 上記のとおりキャッシュされる。subagent も
  親のキャッシュを継承するので、subagent に確認させても同じ古い内容を見る
- **フックのログは注入ログであって一致ログではない。** dedup で抑制された一致は記録されない。
  増分 0 から言えるのは「注入されなかった」までで、「一致しなかった」ではない
- **観測ログはマシン全体で共有される。** 総行数の増分は他のセッションの活動で汚染される。
  自分の測定だけを取り出す手がかり (時刻・対象ファイル名) を先に決めてから測ること
- **強度ラベルが静かに降格する。** 移設で 2 項目を 1 項目へ統合すると、片方の強度
  (MUST / SHOULD 等) が消える。識別子の照合では出ないので、ラベルを突き合わせる検算が別に要る
- **列挙を親へ引き上げると射程が広がる。** 「直前の数例」だった列挙が「族全体」の主張に化ける。
  移した先で「列挙は網羅ではない」を明示するか、判定基準を形の一致から外す
- **二重管理を消す作業が同型の欠陥を作る。** 散文を参照へ書き換えたら、(1) 消した列挙が
  部分集合でなかったか (2) 指名した参照先が本当にその情報を持つか (3) 書いた宣言の範囲が
  実態より広くないか (4) 足した注記自身が値を再掲していないか、の 4 点を検算する。
  散文の真偽はどの検査も見ないので、4 つとも緑で通ってしまう

## 上限を機械で固定する

一回きりの削減は追記で食われる。実測で 9 日のうちに 44% 増えたことがある。
削減量ではなく上限を検査で固定するほうが本体になる。

上限を作るなら、**上限そのものが動かせないこと** まで含めて設計すること。超えたときに
上限のほうを書き換えれば通る形だと、上限は上限として働かない。

厳格な単調非増加は、余裕が無い状態で入れると詰む。防ぎたいのが「上げること」ではなく
「無音で上げること」なら、引き上げに記録 (日付・値・理由) を要求する形で目的を満たせる。

検査の実装はこの skill の責務の外。ここが持つのは「何を測るか」と「どう判定するか」まで。
